# 会话工作区与产物隔离修复方案

## 目标

为每个会话使用独立的受管理工作区后，保证以下不变量：

1. 一个 manifest artifact 只能在它记录时所属的工作区根目录中解析；根位于默认 workspace 内时，才允许在该根中预览。
2. 压缩恢复产生的 continuation 会话继承原会话的工作区语义；原会话为 `managed` 时，恢复会话仍不可修改工作区。
3. 本部署已确认的历史 artifact 统一以 `HERMES_WEBUI_DEFAULT_WORKSPACE` 为根；历史空根记录在运行时逻辑映射到该根，不能自动追加 `sessions/` 前缀。
4. 同一 compression lineage 的每条 artifact 和 empty decision 都带有自己的根目录身份，不能用当前 session root 覆盖，也不能让跨根 empty decision 错误抑制其它根的 turn。
5. 文件 artifact 的预览继续使用现有 `/api/integration/workspace/file`，不新增接口或请求参数；只有位于
   `HERMES_WEBUI_DEFAULT_WORKSPACE` 内的记录才进入可预览的 `file` artifact，默认根之外的记录必须
   fail-closed。

本方案只处理会话 manifest 与压缩恢复链路，不改变 manifest 数据库中的历史行，不移动或删除历史会话数据。历史空根通过运行时兼容逻辑解释，不执行数据库回填。

新建 managed 会话的目录布局由《会话独立工作区改造方案》定义为：

```text
HERMES_WEBUI_DEFAULT_WORKSPACE/sessions/<session_id>
```

该命名空间将新会话文件与默认根目录中的历史共享文件区分开，但不能替代本方案的数据库根目录身份：external 会话从 `A` 切换到 `B` 后，旧 artifact 仍必须按记录的 `A` 解析；`A` 位于默认根内时从 `A` 预览，位于默认根外时不可预览，绝不能从当前的 `B` 读取。已有 `<base>/<session_id>` managed root 继续按持久化的 `Session.workspace` 使用，不迁移。

历史与新 managed artifact 的 wire path 必须保持可区分：

```text
历史记录：workspace_root=<base>                  + report.md
新 managed：workspace_root=<base>/sessions/<sid> + sessions/<sid>/report.md
```

历史记录的相对路径 `report.md` 不能被兼容逻辑重写成 `sessions/<sid>/report.md`；后者只属于新 managed session 的记录。
`/api/integration/workspace/file` 只能解析默认 workspace 根，因此默认根之外的 external/worktree artifact
不能继续以裸 `report.md` 返回，也不能通过绝对路径绕过该接口的根目录限制。

## 问题一：manifest 写入根目录，但预览忽略根目录

### 当前数据流

写入 manifest 时，`integration/session_manifest/store.py` 会为每条记录保存：

```text
session_id + lineage_key + profile + workspace_root + turn_key + path
```

读取时，`load_manifest_records()` 会返回不同 root 的 lineage 记录；但
`integration/session_manifest/manifest.py` 在 wire 投影阶段统一用当前 `session.workspace` 解析相对路径，未使用行内
`workspace_root`。empty decision 和 decided turn key 也只返回裸 `turn_key`：

```text
lineage_key + profile + turn_key
```

这使“记录属于哪个根”和“应当从哪个根预览”脱节。

### 失败场景

1. 历史 external 会话在默认 workspace 下的工作区 `A` 的 `turn:1` 生成 `report.md`，manifest 记录为：
   `workspace_root=A, path=report.md`。
2. 该会话后来通过更新接口切换到工作区 `B`。
3. `B` 恰好也存在一个 `report.md`。
4. 打开历史 `turn:1` 的 artifact 时，虽然读到的是 `workspace_root=A` 的记录，wire 投影却使用
   当前 `session.workspace=B`，预览解析成 `B/report.md`。

结果不是单纯的“旧文件丢失”，而是用户会看到另一份文件，同时 UI 仍将它标记为旧 turn 的产物。
这会造成错误内容展示，且可能对错误文件进行后续编辑、下载或引用。

同一遗漏还会影响 empty decision：来自 `A` 的“本轮无 artifact”记录若仅以裸 `turn_key` 表示，
可能让 `B` 中同名 turn 的派生结果被错误抑制。

### 修复设计

#### 1. 运行时兼容已确认的历史根目录

本部署已确认：引入 `workspace_root` 前的所有 manifest artifact 都相对于
`HERMES_WEBUI_DEFAULT_WORKSPACE`。因此读取现有 `workspace_root=""` 行时，将其逻辑解释为该环境变量
解析后的规范化绝对路径；数据库中的空值保持不变，也不是把它们解释为当前 `session.workspace`。

```text
历史行：workspace_root=""                 -> 运行时逻辑根：<canonical DEFAULT_WORKSPACE>
新 managed 行：workspace_root="" 不允许写入 -> <base>/sessions/<session_id>
```

运行时兼容必须满足：

1. 集中实现 `effective_manifest_workspace_root(row)`：非空 `workspace_root` 使用记录自身的
   canonical root；空值仅在本部署确认历史文件统一位于默认根时映射到 canonical
   `HERMES_WEBUI_DEFAULT_WORKSPACE`。
2. 读取兼容逻辑不能由 `GET /api/session/manifest` 改写数据库，也不能把空根持久化成当前
   `session.workspace`。
3. 普通 upsert/replace 写入遇到空或无法规范化的 session root 时拒绝写入，而不是再产生新的
   `workspace_root=""` 行。
4. 其它部署若不能确认“所有历史 artifact 均在默认根”，不得启用该兼容映射；应保留空根记录并走
   不可预览的保守降级。

运行时兼容后的历史记录 wire projection 必须使用默认根作为 integration root：`report.md` 仍返回为
`report.md`，而不是 `sessions/<session_id>/report.md`。只有 `workspace_root` 已明确指向
`<base>/sessions/<session_id>` 的新 managed 记录才添加该前缀。

#### 2. 按记录根确定预览资格，而非按当前 session 根预览

`load_manifest_records()` 对同一 lineage 保留历史根不同的记录，不能简单过滤为“当前 root”。否则会
把 external 会话切换 workspace 前的真实 artifact 隐藏掉。manifest build 将每个 store row 的 canonical
`workspace_root` 传给 `_row_to_wire()`；后者以该根执行安全路径解析、存在性检查，并先判断该根是否位于
canonical `HERMES_WEBUI_DEFAULT_WORKSPACE` 下。

workspace 文件预览保持现有接口和请求形状：

```text
GET /api/integration/workspace/file?path=<integration-root-relative-path>
```

当记录根位于 integration root 内时，才将 session-relative path 投影为该接口可解析的相对路径：

```text
历史默认根：<base> + report.md                  -> report.md
新 managed：<base>/sessions/<sid> + report.md    -> sessions/<sid>/report.md
默认根子目录：<base>/project-a + report.md       -> project-a/report.md
```

当记录根位于 integration root 外时，不能返回裸相对路径，因为现有接口会错误地从默认根解析同名文件。
这类记录保留在 manifest store 中用于历史归属、empty decision 和审计，但不进入可预览的 file artifact
wire 列表；不能新增参数、放宽 integration root 或把绝对路径传给该接口来规避限制。

有效根和 file 预览资格如下：

| 记录类型 | effective root | `file` 预览 |
| --- | --- | --- |
| 空根历史 store row（运行时兼容后） | canonical `HERMES_WEBUI_DEFAULT_WORKSPACE` | 可预览 |
| 新 managed store row | 该行的 `<base>/sessions/<session_id>` | 可预览 |
| 新 external/worktree store row | 该行保存的 canonical root | 仅 root 位于 `<base>` 内时可预览 |
| 仅由当前 transcript 临时派生、尚未持久化的行 | 当前 `session.workspace` | 仅 root 位于 `<base>` 内时可预览 |

只有预览根位于 canonical integration root 内时，记录才可以生成 `preview=file` wire row；根目录之外的
记录必须在 wire projection 阶段 fail-closed。文件不存在、根无法规范化或根发生 symlink 逃逸时，同样不得
生成可预览 row。artifact 的持久化归属不因不可预览而被删除。

empty decision 和 decided turn 判断也必须携带 `(turn_key, workspace_root)`，或在取裸 key 前先证明该
turn 的根相同。跨根 decision 不得影响其它根的同名 turn；同根 compression continuation 则继续共享。

## 问题二：压缩恢复会话丢失 `workspace_mode`

### 当前数据流

压缩恢复入口 `/api/session/compression-recovery/start` 在 `api/routes.py` 中基于 source
创建新的 `Session`。它复制了 source 的 `workspace`、worktree 元数据和 compression lineage，
但没有传入 `workspace_mode`。

`Session.__init__` 在缺少该参数时会采用兼容旧数据的默认：有 `worktree_path` 时为 `worktree`，
否则为 `external`。因此 source 是 `managed` 的普通会话时，恢复会话会变成 `external`。

### 失败场景

1. 新会话创建为 `managed`，工作区为
   `HERMES_WEBUI_DEFAULT_WORKSPACE/sessions/<source_session_id>`。
2. 会话触发压缩，用户选择“focused continuation”。
3. 恢复会话沿用同一个目录，但因缺少 `workspace_mode` 变成 `external`。
4. `/api/session/update` 或 `/api/chat/start` 不再执行 managed 工作区的不可变校验，调用方可以将它
   指向 `B`。
5. 新旧会话仍属于同一 compression lineage，随即触发前述跨根 artifact 混入和同名文件误预览风险。

### 修复设计

在创建 recovery `Session` 时显式传入：

```python
workspace_mode=getattr(source, "workspace_mode", None)
```

`Session` 仍保留现有缺省逻辑，以兼容真正缺少该字段的历史 sidecar：没有明确 mode 的历史会话
继续按 `external` 处理，不能因为本修复被自动升级为 `managed`。

需要验证的语义：

| source `workspace_mode` | recovery `workspace_mode` | workspace 是否可更新 |
| --- | --- | --- |
| `managed` | `managed` | 否，返回既有冲突错误 |
| `external` | `external` | 是，维持既有行为 |
| `worktree` | `worktree` | 遵循既有 worktree 规则 |
| 缺失（历史数据） | `external` | 是，兼容旧行为 |

## 实施步骤

1. 新增统一的运行时 effective-root 解析器：已确认部署中的历史空 root 逻辑映射到 canonical `DEFAULT_WORKSPACE`，不修改数据库；正常新写入使用会话的 canonical workspace root。
2. 调整 manifest 构建与 wire 投影：store row 始终使用自身的 effective root，不能使用当前 session root；历史默认根 row 不得追加 `sessions/` 前缀。仅当该 root 位于 canonical integration root 内时才生成 `preview=file`，并继续复用 `/api/integration/workspace/file?path=...`；默认根外的 row 保留存储归属但不生成可预览 wire row。
3. 将 empty decision 和 decided turn 的内部身份扩展为包含 workspace root，检查 repair/backfill 路径不跨根覆盖。
4. 在 compression recovery 创建 `Session` 时继承 source 的 `workspace_mode`。
5. 仅在全部回归测试通过后提交。该改动涉及 core manifest 和 session 恢复逻辑，不应放入
   `integration/`；不修改根目录 `CHANGELOG.md`。

## 回归测试

### workspace 隔离

1. 创建 external 会话，根目录为默认 workspace 下的 `A`，写入 `turn:1/report.md` manifest 记录。
2. 将同一会话的 workspace 改为 `B`，并在 `B` 创建同名 `report.md`。
3. 构建 manifest：`turn:1` 必须预览 `A/report.md`，绝不能预览 `B/report.md` 或直接丢失 artifact。
4. 用 `workspace_root=""` 的旧 schema fixture 执行读取，断言数据库中的 root 仍为空；逻辑 root 为
   canonical default workspace，且 `report.md` 能通过 manifest 与 integration 文件接口预览，返回路径
   仍为 `report.md`，不包含 `sessions/`。
5. 以同一 `lineage_key`、不同 root 构造同名 `turn_key` 的 empty decision 与 artifact，断言 empty decision
   不抑制另一根的 artifact。
6. 以同一 `lineage_key`、不同 profile 或不同 workspace root 创建同名路径，断言预览和 profile 索引完全隔离。
7. 创建默认 workspace 之外的 external/worktree artifact，断言记录仍可持久化和归属，但 GET manifest 不返回
   可预览的 `file` row，且不会尝试通过 `/api/integration/workspace/file` 读取默认根中的同名文件。

### compression recovery

1. 创建 `managed` source，启动 compression recovery，断言 child 的 `workspace` 和
   `workspace_mode` 都等于 source。
2. 对该 child 调用 workspace 更新或在 chat start 中传不同 workspace，断言被拒绝且已持久化的
   workspace 不变。
3. 为 `external`、`worktree` 和缺少 mode 的历史 source 分别建例，断言保持上表定义的兼容语义。
4. 使用 managed source 与 recovery child 的同一 lineage 写入 manifest，断言同根产物仍正常跨
   continuation 展示，不会因新增过滤损失合法记录。

## 发布与回滚

该修复不移动文件系统目录，也不修改 manifest DB 的历史行，因此无需数据库回填或迁移备份。回滚
代码后，空根记录仍保持原值；上线后应抽样检查历史 artifact 成功预览率、默认根外 artifact 的
fail-closed 数量、空根兼容命中量、同一 lineage 中的 effective root 数量，以及 compression recovery
会话的 `workspace_mode` 分布。若发现
部署事实不成立，应关闭空根到默认根的兼容映射并对这些记录 fail-closed，而不是把记录改为当前
workspace。
