# 轮次级文件事务与归档方案

## 目标、范围与最终行为

目标是在 `/api/chat/stream` 会话中，为每个 `turn_id/stream_id` 生成权威文件 ChangeSet，不解析 assistant 文本、命令文本或工具结果。

权威口径如下：

- 记录 workspace 与 Profile 知识资产范围内，经过 include/exclude 规则筛选后的最终变化。
- 包含 `created`、`modified`、`metadata_changed`、`deleted`、`type_changed`。
- 创建后又删除的临时文件不记录；重命名按 `deleted + created` 表示。
- 新增和修改后的内容、修改和删除前的内容都归档到 SHA-256 CAS。
- 取消、模型错误和进程异常也尽力生成 ChangeSet，但默认进入 `pending_review`，不自动写回真实目录。
- 新功能只在独立进程形式的 supervised runner 下提供严格保证，不静默降级到 WebUI 进程内推测。
- 部署只支持 WebUI/Agent 全本地或位于同一外层容器。Runner 的监督所有者由步骤 0 的 G2 决定；不能一边绑定 WebUI 生命周期，一边声称支持 WebUI-only restart/reattach。
- Hermes Agent 的 `terminal.backend=local|docker` 是工具执行后端选择，不改变 WebUI/Agent 的共置部署边界；两种 backend 都必须操作同一轮 shadow workspace。

兼容矩阵：

| WebUI/Agent 部署 | Terminal backend | strict 支持条件 |
| --- | --- | --- |
| 全本地 | `local` | 完成步骤 0 的 OS 级隔离门禁后支持；只有 cwd/env 重定向时不属于 strict |
| 全本地 | `docker` | 终端容器直接 bind mount shadow workspace/Profile，禁止跨轮复用 |
| 同一容器 | `local` | 完成步骤 0 的 mount namespace/沙箱门禁后支持；真实 `/workspace` 不得对 worker 可写 |
| 同一容器 | `docker` | 必须挂载 Docker socket，mount broker 能转换外层挂载且 sentinel 验证成功 |

约束与非目标：

- 首版部署仅支持 WebUI/Agent 全本地或位于同一外层容器；Gateway、SSH、Modal、Daytona 后续通过相同 ChangeSet 协议接入。
- 首版 Terminal backend 仅支持满足隔离门禁的 `local`，以及通过 shadow mount 校验的 `docker`。
- 单容器 Docker backend 要求可访问 Docker daemon，并能安全转换承载 state/shadow 的外层挂载；否则 strict 明确不可用。
- 完整性口径限定为冻结 policy 纳入的 workspace 与 Profile 知识资产，不覆盖整个主机文件系统。
- CAS 内容随会话生命周期保留；删除、清空或截断会话后，按步骤 7 的 tombstone 与 GC 协议回收。
- 默认排除规则属于产品口径；“无遗漏”指规则纳入范围内无遗漏。

## 步骤 0：关闭设计门禁

本方案的总体方向成立：以隔离的 shadow workspace 承载本轮执行，以 baseline/work 的最终状态生成 ChangeSet，以 SHA-256 CAS 保存前后版本，再通过逐路径 compare-and-swap 合并到真实目录。

以下问题不否定该方向，但当前文本尚未形成闭合契约；其中标记为“阻断”的事项在作出明确决策并同步修改后续章节前，不应进入真实聊天链路实现。


### 0.1 门禁清单

| 编号 | 问题 | 当前风险 | 实施门禁 |
| --- | --- | --- | --- |
| G1 | Local backend 没有操作系统级文件隔离 | 修改 `cwd`、`HOME` 和 `HERMES_HOME` 不能阻止 shell、Python、MCP 或子进程通过绝对路径写入真实 workspace/Profile；当前“strict”名称与保证不一致 | 首版 strict 仅支持具备 mount namespace/容器沙箱的 backend，或先为 local 增加可验证的 OS 级文件系统隔离；只有环境重定向时必须降级命名和承诺 |
| G2 | Runner 生命周期与现有 restart/reattach RFC 冲突 | Runner 是 `server.py` 子进程且 WebUI 停止时会被终止，无法满足“仅重启 WebUI 后 run 继续执行并可重新发现、回放和取消” | 二选一：让 Runner 由独立 supervisor 管理并跨 WebUI 生命周期存活；或正式修订 RFC 和验收口径，明确 WebUI 重启会中断 Agent，只恢复文件事务 |
| G3 | 取消、模型错误和进程异常仍自动应用文件 | work 中可能是半写文件、未完成迁移或被取消的用户意图；“取消”反而触发真实目录写入 | 默认改为 `completed` 自动应用非冲突变化；`cancelled/errored/interrupted` 只捕获到 CAS 并进入 `pending_review`，经用户明确确认后再应用全部或指定路径 |
| G4 | run 状态、执行结果和文件处理状态混在同一状态机 | `interrupted` 被描述为终态，但异常轮次又要继续 `quiescing/captured/applying`；文中还有有界队列，却没有 `queued` 状态 | 拆分 `run_phase`、`outcome`、`capture_status`、`apply_status`，并枚举每种退出路径的合法转换后再编码 |

### 0.2 G1：Local backend 的严格隔离边界

进程的当前目录和环境变量只是默认解析上下文，不是权限边界。

例如 local worker 即使从 shadow workspace 启动，仍可能执行 `cd /真实/workspace`、访问外部绝对 symlink、扫描宿主机目录，或调用一个已经持有真实路径的常驻 MCP 服务。

同一容器的 local backend 还可能直接看到挂载在 `/workspace` 的真实目录。


因此，“模型不知道真实路径”不能作为隔离证明。

strict 的判定必须基于操作系统实际限制：执行进程只能看到 shadow workspace、shadow Profile 和显式只读输入，真实根在其 mount namespace、sandbox profile 或容器文件系统中不可写。

远程 MCP、常驻 MCP 和不能证明继承隔离环境的文件写入型工具应禁用，或明确排除在 strict 保证之外。


### 0.3 G2：Runner 存活语义必须先统一

现有 Runner RFC 的关键验收条件是：启动长任务后只重启 WebUI，Runner 继续持有执行，新的 WebUI 能按 durable run identity 重新发现状态、从 cursor 回放事件，并在任务仍活跃时继续取消。

当前方案中 Bearer key、Runner 端口和 Runner 进程都从属于一次 WebUI 生命周期，WebUI drain 会终止 Runner 和 worker，只能做到“中断后从 work 捕获文件”，不能做到“执行继续”。


如果选择独立存活，必须补充稳定的 Runner discovery、跨 WebUI key 轮换/交接、单实例选主、旧 WebUI 凭证失效和新 WebUI reattach 协议。

如果选择中断恢复，则应删除“执行所有权已满足 restart/reattach”的表述，并把 `interrupted` 作为明确用户可见结果；外层容器整体重启和仅 WebUI 进程重启也必须分开定义。


### 0.4 G3：异常轮次的文件处理语义

捕获和应用是两个不同决策。

异常轮次仍应尽力收敛子进程、稳定扫描 work、写入 CAS 和生成可审计 ChangeSet，避免丢失已经产生的内容；但“成功捕获”不代表“适合自动写回”。

建议默认规则固定为：

| outcome | capture | 默认 apply |
| --- | --- | --- |
| `completed` | 完整捕获 | 自动应用非冲突路径 |
| `cancelled` | 尽力完整捕获 | `pending_review`，不自动写真实目录 |
| `errored` | 尽力完整捕获 | `pending_review`，不自动写真实目录 |
| `interrupted` | 恢复后能证明完整才提交 | `pending_review`，不自动写真实目录 |
| capture 不完整 | 标记失败并保留诊断目录 | 禁止 apply |

手工确认接口需要支持 ChangeSet 级和单路径级选择，并继续执行 baseline/expected hash compare-and-swap；确认不能绕过冲突检测。

### 0.5 G4：正交状态模型

建议状态拆分如下，避免用一个枚举同时表达四种含义：

```text
run_phase:
  queued -> preparing -> prepared -> running -> quiescing
         -> capturing -> captured -> applying|pending_review -> terminal

outcome:
  unknown | completed | cancelled | errored | interrupted

capture_status:
  not_started | in_progress | complete | failed

apply_status:
  not_started | pending_review | applying | applied
  | partially_applied | conflicted | failed
```

必须为正常完成、用户取消、Provider 错误、worker SIGKILL、Runner SIGKILL、WebUI 重启、锁等待超时、磁盘不足、会话删除和手工 resolve 分别列出转换表。

浏览器终态、Run Journal、`transaction.jsonl` 和 `turn_files.db` 发生分歧时，也要规定哪一层是各字段的权威来源以及如何修复派生状态。


### 0.6 关闭顺序与完成标准

1. 先决定 G1 local strict 支持范围和 G2 Runner restart/reattach 语义。这两项决定部署架构与安全边界。
2. 再确定 G3 异常轮次 apply 策略，并完成 G4 正交状态机。
3. 将门禁决策同步回步骤 1、2、4、5、7、8 的契约和测试。
4. G1-G4 均有明确选择、失败语义和验收用例后，才允许接入真实 `/api/chat/start`。

门禁未关闭时，只能在纯临时目录中实现 policy、diff 和 CAS 原型，不得对外声明 strict 保证。

## 步骤 1：确定身份、状态与 Runner 契约

### 1.1 进程职责和调用边界

严格模式下，WebUI 不再直接持有 Agent 执行过程。

WebUI 负责 `/api/chat/start`、`/api/chat/stream`、SSE 转发、会话元数据和 Session Inspector；Runner 是 Agent 执行、事务工作区、文件捕获、CAS 归档和合并的唯一入口。


```text
WebUI /api/chat/stream
        |
        | Runner HTTP API + Bearer
        v
Hermes Runner
        |-- 本轮 Agent/Terminal/MCP 子进程
        |-- baseline/work 事务目录
        |-- ChangeSet + SHA-256 CAS
        `-- 非冲突文件合并到真实目录
```

### 1.2 如何理解 `Runner HTTP API + Bearer`

这条箭头表示 WebUI 与 Runner 之间的**内部控制通道**：浏览器仍然只访问 WebUI 的 `/api/chat/*`，WebUI 再作为 HTTP 客户端调用同机 Runner 的 `/v1/*` 接口。

Runner HTTP API 不是另一套面向用户的聊天接口，也不应直接暴露到局域网或公网；它用于把“启动一轮、读取事件、查询状态、取消、提交审批/澄清”等运行控制从 WebUI 进程传给 Runner。


`Bearer` 是这条内部通道的临时访问凭证。WebUI 调用受保护的 Runner 接口时，在 HTTP 请求头携带：

```http
Authorization: Bearer <本次启动随机生成的 key>
```

Runner 收到请求后先校验 key，匹配才处理；缺失或错误则返回 `401/403`。

可以把它理解为 WebUI 进入 Runner 控制面的临时门禁，但它只证明“请求来自持有本次 key 的调用方”，不能替代 session/path 授权、run 标识校验和参数校验。


一次典型调用链如下：

1. 浏览器请求 WebUI 开始对话，WebUI 完成用户认证、会话授权并生成 `session_id`、`turn_id`、`stream_id`。
2. WebUI 携带 Bearer key 调用 Runner 的 `POST /v1/runs`；Runner 幂等创建对应 run 和独立 worker。
3. WebUI 携带同一 key 按 cursor 读取 `/v1/runs/<stream_id>/events`，再把允许公开的事件转换为浏览器 SSE；浏览器不会看到 Runner 地址或 key。
4. 用户点击取消时，浏览器仍请求 WebUI；WebUI 校验会话归属后，携带 key 调用 Runner 的 cancel 接口，Runner 只终止该 `stream_id` 对应的 worker、进程组和容器。

这个 Bearer key 与三类凭证必须严格区分：它不是用户登录 cookie，不是模型 Provider API Key，也不是 Agent 工具凭据。

它由 `server.py` 每次启动随机生成，只保存在 WebUI/Runner 内存或受控子进程环境中；不持久化、不写日志、不放入命令行、不返回浏览器，也不传给 Agent worker、Terminal、MCP 或普通工具。

即使 Runner 只监听 `127.0.0.1`，仍要求 Bearer 校验，以防同机其它进程直接调用取消、审批、读取事件或启动 run 等控制接口。


- WebUI 创建并传递 `session_id`、`turn_id`、`stream_id`，Runner 不重新生成这些标识；首版 Runner 的 `run_id` 固定等于 `stream_id`，避免维护第二套映射。
- Runner 复用现有 `runner-local` HTTP 契约：创建 run、事件游标、状态、取消、审批、澄清和追加消息。
- Runner 的运行文件只写 `STATE_DIR/turn_files/`、`STATE_DIR/runner/` 和 CAS；WebUI 继续独占认证、设置和会话数据库。`turn_files.db` 的所有读写统一经过 store 模块，避免两个进程直接修改同一 JSON 或复制状态。
- 开启 `HERMES_WEBUI_TURN_FILES=strict` 后，所有会改变文件的 Agent 执行必须经过 Runner，不允许回退到 `legacy-direct`。

### 1.3 身份与幂等规则

- `session_id` 标识会话，`turn_id` 标识一次用户提交，`stream_id/run_id` 标识一次运行，`turn_key` 标识 Manifest 中的轮次投影。
- `POST /v1/runs` 以 `stream_id` 为幂等键。相同 payload hash 重试返回原 run；相同标识但 payload 不同返回 `409 idempotency_conflict`。
- Runner 的每个状态、事件、控制请求、事务目录和 ChangeSet 都必须携带并校验同一组身份，不能依赖字符串前缀推断归属。
- Run Journal 是浏览器事件和 cursor 的权威来源；`transaction.jsonl` 只记录文件系统恢复 intent；`turn_files.db` 是 ChangeSet、capture 和 apply 状态的权威来源。

步骤 1 完成标准：身份字段、幂等语义、Bearer 边界和三层状态所有权形成版本化契约；相同请求重试不启动第二个 worker，错误身份不能读取或控制其它 run。

## 步骤 2：启动并监督 Runner

### 2.1 启动共置 loopback Runner

现有 `bootstrap.py --foreground` 会通过 `os.execv` 将自身替换为 `server.py`。步骤 0 的 G2 必须先决定 Runner 是否跨 WebUI 生命周期存活，再选择监督拓扑。

若选择“WebUI 重启中断 Agent”，可由 `server.py` 创建 `RunnerSupervisor`：

```text
ctl.sh / launchd / systemd
            |
            v
        server.py
            |
            `-- runner_service
                    `-- 每轮独立 Agent 进程组
```

该分支的启动流程为：

1. `server.py` 检测到 strict 模式后，使用 `secrets.token_urlsafe(32)` 生成仅本次 WebUI 生命周期有效的 256-bit Bearer key。
2. 使用与 WebUI 相同的 Python 解释器执行 `python -m integration.turn_files.runner_service --host 127.0.0.1 --port 0`，并创建独立进程组。
3. Bearer key 仅通过子进程环境或继承控制管道传递，不写入命令行、全局环境、配置文件或日志。
4. Runner 绑定系统分配的随机端口，通过 readiness pipe 返回 `port`、`pid`、`instance_id` 和 `protocol_version`。
5. WebUI 在限定时间内携带 Bearer key 探测 `/v1/health`，校验协议版本和 `instance_id` 后，在内存中创建 `HttpRunnerClient`。
6. Runner 未按时就绪时，WebUI 仍可提供设置和诊断页面，但新的 strict 会话返回结构化 `503 runner_unavailable`。

Runner 只监听当前主机或当前 WebUI 容器的 `127.0.0.1`，并拒绝非 loopback 来源。

除最小存活探针外，run、events、status、cancel、approval、clarify 和深度健康接口全部要求 `Authorization: Bearer <key>`。

日志必须过滤 Authorization、请求中的凭据、完整环境和 key；每次 WebUI 重启自然轮换 key。


`RunnerSupervisor` 持续监控子进程，异常退出后按 `1、2、5、10、30` 秒退避重启；超过失败上限后进入 degraded。worker 使用 parent-death 管道，Runner 意外退出时收敛本轮进程组。

Runner 重启后扫描非终态 journal，清理残留进程，再继续 capture 或标记失败。WebUI 必须校验新的 `instance_id`，不能复用旧连接状态。

该分支中，WebUI 停止时先拒绝新 run，再请求 Runner drain，最后按超时执行 `TERM/KILL`。所有活跃 run 记录为 `interrupted`，完成 capture 后进入 `pending_review`。

若选择“Runner 跨 WebUI 存活”，Runner 必须由 WebUI 之外的 supervisor 管理。

步骤 2 还需实现稳定 discovery、单实例选主、key 交接、旧 key 失效和新 WebUI reattach；`server.py` 只连接和观察，不负责终止 Runner。


### 2.2 单容器部署

单容器部署中，WebUI、Hermes Agent 代码、Runner 和每轮 worker 全部位于同一个外层容器：

```text
Docker / Compose
    `-- hermes-webui container
          |-- server.py :8787
          |-- loopback runner :random-port
          `-- per-turn Agent worker
                 |-- terminal backend=local：同容器进程
                 `-- terminal backend=docker：宿主机 Docker sibling container
```

`docker_init.bash` 继续只执行 `python server.py`，不增加 `HERMES_WEBUI_PROCESS_ROLE` 分支。

`server.py` 在容器内启动 Runner 子进程，因此两者天然看到相同的 `/workspace`、Hermes home 和 `HERMES_WEBUI_STATE_DIR`，也可以直接通过父子进程传递随机 Bearer key。


Runner 端口不通过 Compose `ports` 或 `expose` 发布。

WebUI 使用 supervisor 返回的内存 base URL，不配置 `http://hermes-runner:8790`。

外层容器停止时 Runner 与 local worker 随之退出；未完成事务由下一次容器启动时的新 Runner 从 state volume 恢复。


外层容器继续使用现有挂载：

| 逻辑根 | 容器路径 | 用途 |
| --- | --- | --- |
| Workspace | `/workspace` | baseline、work 和最终文件合并 |
| Hermes home | `/home/hermeswebui/.hermes` | Agent 配置及允许捕获的 Profile 知识资产 |
| WebUI state | `/home/hermeswebui/.hermes/webui` | journal、ChangeSet DB、CAS 和恢复状态 |

WebUI state 已位于 Hermes home 子目录，沿用同一个外层挂载即可，不新增可能遮蔽历史会话的 state volume。Runner 与 WebUI 使用同一 UID/GID；事务目录、CAS 和 DB 都由同一容器用户创建。

当 Terminal backend 为 `local` 时不需要额外挂载。

当 Terminal backend 为 `docker` 时，外层容器必须具备 Docker CLI，并显式挂载 `/var/run/docker.sock`；该能力等同于允许容器控制宿主机 Docker，必须作为管理员明确启用的部署选项，而不是默认开启。


单容器 Docker backend 的 Compose 变化只是在现有 `hermes-webui` service 上增加 socket，不新增 service：

```yaml
services:
  hermes-webui:
    volumes:
      - ${HERMES_HOME:-${HOME}/.hermes}:/home/hermeswebui/.hermes
      - ${HERMES_WORKSPACE:-${HOME}/workspace}:/workspace
      - /var/run/docker.sock:/var/run/docker.sock
```

该 socket 挂载只出现在明确选择 Docker Terminal backend 的部署示例中；默认 Compose 继续不挂载。

单容器不使用共享 `control.key` 文件：

- `server.py` 每次启动生成随机 key，只传给 Runner 子进程和内存中的 `HttpRunnerClient`。
- key 不进入 Compose、外层容器公共环境、state volume、日志或 Agent worker 环境。
- 中断恢复分支中，WebUI 重启时 key 与 Runner 一起轮换。跨 WebUI 存活分支必须使用步骤 0 要求的安全 key 交接，不能直接套用本条。

Compose 只保留 WebUI 容器的 `restart: unless-stopped` 和 `/health`；deep health 内嵌 Runner 状态。

strict 模式不会修改现有 two-container/three-container Gateway 拓扑，因为本方案只支持 WebUI 与 Agent 共置的单容器或全本地部署。


### 2.3 健康状态、故障语义和可观测性

- `/health?deep=1` 增加 Runner readiness、PID、`instance_id`、协议版本、重启次数、活跃 run 数、事件 cursor 延迟、事务恢复次数和最后错误，不返回 key。
- 当冻结的 Profile backend 为 Docker 时，deep health 额外报告 Docker CLI/daemon、socket 权限、外层容器 inspect、state mount 转换、UID/GID 和最近一次 sentinel 结果；local backend 不因缺少 Docker socket 降级。
- Runner 日志写入 `STATE_DIR/logs/runner.log`，按大小和保留数量轮转；不得记录 Authorization、CAS 文件内容或 Agent 凭据。
- 新轮次开始前 Runner 不可用时返回 `503 runner_unavailable`；运行中断连时 WebUI 按事件 cursor 重连，不能直接宣布成功。
- Runner 无法恢复 Agent 时仍要收敛残留进程，并尝试从现有 work 目录生成最终 ChangeSet；捕获不完整则标记 `capture_status=failed`，禁止合并和正常 `done`。
- 取消、模型错误和 Runner 异常采用同一收敛与捕获流程；capture 完整后进入 `pending_review`，不因捕获成功而自动合并。
- strict 模式绝不静默切换到正则、工具结果解析或旧进程内执行；诊断信息必须明确区分 unavailable、degraded、capture failed 和 apply conflict。

### 2.4 代码改动顺序

1. 新建 `integration/turn_files/models.py`，定义 `RunIdentity`、`RunState`、`RunEvent`、`ChangeSet` 和可序列化枚举；这些类型不能依赖 `api/routes.py` 的进程内全局变量。
2. 新建 `integration/turn_files/runner_service.py` 和 `worker.py`：service 实现 `/v1/health`、`POST /v1/runs`、events、status、cancel、approval、clarify 和 message 控制，每个响应包含 `instance_id` 与 `protocol_version`；worker 在独立进程中构造 AIAgent 并持有该轮进程组。
3. 复用 `api/turn_journal.py` 生成并持久化 `turn_id`，复用 `api/run_journal.py` 保存供浏览器 replay 的有序事件、sequence 和 cursor；`turn_files/runs/<stream_id>/transaction.jsonl` 只记录文件事务恢复 intent，不再创建第三套浏览器事件账本。
4. 扩展 `api/runtime_adapter.py` 的 `StartRunRequest`，增加 `stream_id`、`turn_id`、`turn_key` 和 `file_capture_mode`；扩展 `api/runner_client.py`，支持 supervisor 注入的内存 base URL/key、健康检查、禁止重定向和实例校验。
5. 将 `api/routes.py` 的 runner 分支调整为“健康预检 -> 在 session lock 内创建 pending user message 和三个轮次标识 -> 写 submitted journal -> 幂等提交 Runner”。submitted journal 未能持久化 `turn_id` 时必须中止并回滚，不能启动无权威轮次标识的 Runner run。
6. `POST /v1/runs` 以 `stream_id` 为幂等键：首次请求持久化后返回 `201`；相同 payload hash 重试返回原 run；同一 `stream_id` 携带不同 payload 返回 `409 idempotency_conflict`。
7. WebUI 提交超时后先调用 `GET /v1/runs/<stream_id>`：存在则继续连接，不存在才回滚 pending 状态并返回 `503`，避免“Runner 已启动但 WebUI 重试又生成一轮”。
8. 新建 `integration/turn_files/supervisor.py` 并接入 `server.py` 的启动、deep health 和 `finally`；Docker 不新增 service 或 process role，只在启用 Docker Terminal backend 时为单容器 Compose 增加可选 Docker socket 挂载和预检说明。

步骤 2 完成标准取决于步骤 0 的 G2 决策。

若 Runner 独立存活，WebUI-only 重启后必须重新发现并继续控制原 run；若选择中断恢复，重启后必须明确终结执行并恢复文件事务。

两种语义不能同时存在。


## 步骤 3：确定捕获根和策略

### 3.1 模块和数据结构

新增 `integration/turn_files/policy.py` 和 `integration/turn_files/roots.py`：

- `roots.py` 调用现有 `resolve_trusted_workspace()` 获取 workspace，调用 `get_hermes_home_for_profile()` 获取该会话绑定的 Profile home；所有路径在 Runner 内再次 `resolve()`，不能信任 WebUI 直接传来的绝对路径。
- `policy.py` 定义版本化 `CapturePolicyV1`，负责读取固定规则和 workspace 根目录的 `.hermes-turn-files.json`，将 glob 规范化为 POSIX 相对路径规则。
- Runner 在创建事务前生成不可变 policy snapshot，将完整 JSON 和 `policy_hash=sha256(canonical_json)` 同时写入 `run.json` 和 `change_sets`。

policy snapshot 固定为以下结构：

```json
{
  "version": 1,
  "roots": [
    {"kind": "workspace", "logical_root": "/workspace"},
    {"kind": "profile", "allow": ["memories/**", "skills/**", "SOUL.md"]}
  ],
  "include": ["**/*"],
  "exclude": ["coverage/**"],
  "default_exclude": [".git/**", "node_modules/**", ".venv/**", "dist/**", "build/**", "**/__pycache__/**"],
  "metadata": ["type", "mode", "symlink_target"]
}
```

### 3.2 规则优先级

每个候选路径只执行一次统一判定，优先级从高到低为：

1. 固定安全拒绝：出根路径、解析后进入 `STATE_DIR`/事务目录、Profile 非白名单资产、凭据和认证状态；任何项目配置都不能覆盖。
2. 用户 `exclude`：同时命中 include 和 exclude 时，以 exclude 为准。
3. 用户 `include`：可以重新纳入默认降噪目录，但不能越过固定安全拒绝。
4. 产品默认排除：VCS 元数据、依赖、缓存和构建输出。
5. 其余路径默认纳入。

固定安全规则至少覆盖 Profile 的 `.env`、`auth.json`、`config.yaml`、数据库、日志、sessions、WebUI state 和 Runner state。

workspace 的凭据规则单独维护并允许安全样例文件例外，例如 `.env.example`；规则列表必须有单元测试，不能散落在多个模块中。


### 3.3 路径、目录和文件类型语义

- 数据库只保存 `{root_kind, relative_path}`；`relative_path` 使用 `/`，禁止空路径、NUL、绝对路径和 `..`。
- 遍历使用 `lstat()`，不跟随 symlink；symlink target 作为元数据保存，指向根外也只记录链接本身，不读取目标内容。
- 首版处理 UTF-8 可表示路径下的普通文件、symlink 和内部目录状态。FIFO、socket、block/char device 或不能稳定序列化的文件名标记为 `unsupported`，并使对应路径捕获失败。
- 权威元数据限定为文件类型、POSIX mode bits 和 symlink target；mtime、ctime、uid、gid、ACL、xattr 和 inode/hardlink 关系明确不属于 ChangeSet。
- capture/apply 内部为目录建立 `DirectoryPathState`，记录存在性和 mode，用于空目录、目录删除、文件与目录互换及父子依赖排序。
- 是否把目录变化投影为用户可见 `file_changes` 由 API 契约决定，但内部不能忽略目录状态。创建后删除且最终不存在的临时节点不记录。
- snapshot 启动时探测根文件系统的大小写和 Unicode normalization 语义。不同相对字符串若指向同一节点，必须规范化为唯一键或 fail closed。
- 原 workspace 中的 hardlink 关系不在首版保真范围。检测到纳入路径共享 inode 时，应拒绝 strict 或把限制明确记录到 ChangeSet，不能无提示地改变语义。

### 3.4 配置校验和失败处理

`.hermes-turn-files.json` 只允许 `version`、`include`、`exclude`。

未知字段、非字符串数组、绝对 pattern、`..` 或超过数量/长度限制时，strict 模式在 Agent 启动前返回 `400 invalid_turn_files_policy`，不能忽略错误继续执行。

policy 文件在一轮开始后即使被修改，也只作为本轮普通文件变化处理，不改变本轮 snapshot。


步骤 3 完成标准：给定同一根、文件系统语义和 policy snapshot，本地与 Docker 得到相同纳入结果；安全拒绝不可被覆盖；目录/type change 和路径别名有确定结果；统计信息不泄露被拒绝凭据。


## 步骤 4：创建 baseline、work 和隔离环境

### 4.1 事务目录布局

新增 `integration/turn_files/snapshot.py` 和 `integration/turn_files/run_layout.py`。每轮先在 `STATE_DIR/turn_files/runs/.tmp-<stream_id>` 准备，全部元数据落盘后原子 rename 为：

```text
STATE_DIR/turn_files/runs/<stream_id>/
  run.json
  transaction.jsonl
  state
  roots/
    workspace/baseline/
    workspace/work/
    profile/baseline/
    profile/work/
  runtime_home/
  backend/
  apply/
  errors/
```

全局 CAS 不放在单轮目录内，而是位于 `STATE_DIR/turn_files/blobs/<前两位>/<sha256>`。

`run.json` 保存真实根路径、shadow 根路径、三个轮次标识、policy snapshot/hash、冻结的 Terminal backend、Runner instance、创建时间和当前状态；`backend/` 保存 Docker mount identity、container ID 与 sentinel 结果等可恢复元数据。

权限为目录 `0700`、元数据和 blob `0600`。


### 4.2 创建顺序

1. 校验根路径、policy、磁盘空间和根重叠关系，对 workspace/Profile 加共享 snapshot lock，防止另一个 apply 正在替换文件。
2. 若 `STATE_DIR`、事务目录、CAS、真实 Profile 与 workspace 存在危险父子重叠，直接拒绝 strict，不能依赖普通 exclude 避免递归复制。
3. 使用独立的 `runtime-copy deny` 排除事务状态、socket、device、凭据和不能安全复制的节点。该规则与 capture policy 分离，用户配置不能覆盖。
4. 为 workspace 构造运行副本，使必要的 `.git`、依赖和默认排除目录仍可被构建命令读取；为 Profile 构造 Agent 所需的隔离运行副本。
5. policy 只控制 `baseline.index`、diff、CAS 和 merge，不控制普通依赖是否出现在运行视图。
6. 每个源文件执行 `lstat -> clone/copy -> lstat`，确认类型、size、mtime/ctime 等稳定性标记未变化；变化时有限重试，仍不稳定则 snapshot 失败。
7. macOS 优先 `clonefile(2)`，Linux 优先 `FICLONE`；单文件不支持 CoW 时只对该文件回退 `copy2`，禁止硬链接。
8. baseline 完成后遍历纳入路径并写 `baseline.index`，记录原始 mode 和 hash；再从 baseline 克隆 work。
9. baseline 递归移除写位且不能作为 cwd。diff 使用 index 中的原始 mode；捕获前重新验证 baseline hash。
10. 数据库进入 `prepared` 后才启动 Agent。准备错误必须清理临时目录或保存明确错误标记，不能启动不完整 run。

本方案首版承诺“每条 PathState 来自一个经过稳定性校验的源版本”，不承诺整个目录是文件系统级同一时点快照。

需要全目录原子快照时，必须依赖 APFS/Btrfs/ZFS 等明确能力并另行扩展契约。


### 4.3 Agent 运行环境重定向

- workspace cwd、File Tool 根目录和 Terminal cwd 指向 `roots/workspace/work`。
- 创建 `runtime_home`，设置 `HOME=<run>/runtime_home`、`HERMES_HOME=<run>/runtime_home/.hermes`；Profile work 映射到该 `.hermes`，使 shell 对 `~/.hermes` 的写入也落入事务视图。
- Profile 中运行所需的配置和凭据可以以 `0600` 复制到 shadow home 供读取，但固定安全拒绝文件不进入 baseline diff、CAS 或最终合并；真实 Profile home 不传给 Agent 子进程。
- `HERMES_WEBUI_STATE_DIR`、Runner journal/CAS 路径和控制面 Bearer key 只保留在 Runner 自身环境，不传给 Agent worker、Terminal、MCP 和普通工具。
- attachment 使用显式只读输入路径，不自动归入 ChangeSet；Agent 将其复制或转换到 work 后，目标文件按正常规则记录。
- Runner 为每轮启动独立 worker 进程，而不是在线程中修改全局 `os.environ`；worker 再创建独立进程组，Terminal 增加 `isolation_id=stream_id`，所有 Agent 子进程继承同一事务环境。禁止复用 `SESSION_AGENT_CACHE` 中绑定真实 workspace/Profile 的 Agent。
- workspace 内相对 symlink 会自然解析到 work；指向真实 workspace 内部的绝对 symlink 在 work 中改写为对应 shadow target，并在 `baseline.index` 记录逻辑 target，diff 时归一化回原 target，防止未修改链接被误报且避免通过链接写回真实 workspace。

### 4.4 Terminal backend 适配

新增 `integration/turn_files/terminal_backend.py`，提供统一的 `TurnTerminalBackend`，根据该轮 Profile 配置解析出的 `TERMINAL_ENV=local|docker` 创建执行环境。

backend 选择必须作为 `run.json` 的冻结字段保存，不能在一轮中途切换。


#### 4.4.1 Local backend

- Local 只有在步骤 0 的 G1 已通过 OS 级隔离验收时才能标记 strict。仅设置 cwd/env 的实现必须拒绝 strict 启动。
- Terminal、execute_code 和后台进程在隔离后的 worker 进程组中运行，cwd 固定为 `roots/workspace/work`。
- worker 显式传递 shadow `HOME/HERMES_HOME`，不修改 Runner 或 WebUI 进程的全局环境。
- 全本地部署时进程运行在宿主机；单容器部署时进程运行在 WebUI 外层容器内。二者使用同一代码路径。
- 轮次结束通过进程组执行 `TERM -> bounded wait -> KILL`，全部退出后才能进入 capture。

#### 4.4.2 Docker backend

Docker backend 不能使用 Hermes Agent 默认的独立 `/workspace` tmpfs、sandbox workspace 或跨进程持久容器。strict 模式由 `TurnTerminalBackend` 覆盖为以下事务配置：

```text
task_id / isolation_id = stream_id
shadow workspace work  -> terminal container /workspace:rw
turn runtime_home      -> terminal container /root:rw
shadow profile work    -> terminal container /root/.hermes:rw
container_persistent   = false
persist_across_processes = false
```

- 一轮只创建一个 Terminal 容器并在本轮工具调用之间复用；下一轮必须创建新容器，禁止使用 Hermes 默认的跨会话/跨进程容器复用。
- File Tool、Agent 内置写入、Terminal、execute_code 和本地 MCP 最终都必须读写相同的 `roots/workspace/work`；不能通过事后解析命令或 `docker cp` 猜测发生了哪些变化。
- Terminal 容器使用与 Runner 相同的数值 UID/GID，或在启动前验证其生成的 `0600` 文件可由 Runner 读取；验证失败则不启动 Agent。
- 用户 `docker_volumes`、`docker_extra_args` 不得覆盖 `/workspace`、`/root`、`/root/.hermes` 或暴露真实 workspace/Profile；冲突配置返回 `400 strict_docker_volume_conflict`。额外只读输入挂载可保留。
- 容器增加 `hermes-turn-files=1`、`hermes-stream-id=<stream_id>` 和 profile 标签；container ID 和最终 mount spec 写入 `transaction.jsonl`，供取消、崩溃恢复和孤儿清理。
- 轮次终止时先停止调度工具，再执行 `docker stop -> bounded wait -> docker kill -> docker rm`；确认容器不再运行且 bind mount 已可稳定读取后，才写 `quiesced` 并进入 diff。

全本地部署使用 Docker backend 时，Runner 可直接把宿主机 shadow 绝对路径 bind mount 到 Terminal 容器。

启动前创建双向 sentinel：Runner 创建文件后容器必须可见，容器创建文件后 Runner 必须可见；探针文件验证后立即删除。


### 4.5 单容器 Docker mount broker

当 WebUI/Agent 位于同一个外层容器且通过 `/var/run/docker.sock` 启动 Terminal sibling container 时，容器内 shadow 路径不能直接作为 Docker daemon 的宿主机 bind source。

新增 `integration/turn_files/docker_mount_broker.py`：

1. 读取当前外层容器 ID，必要时允许使用受控配置显式指定；通过 Docker API/CLI inspect 获取外层容器 `Mounts[]`。
2. 找到覆盖 `HERMES_WEBUI_STATE_DIR` 中 shadow 路径的最长 `Destination`，计算其相对 subpath。
3. 外层挂载为 bind 时，转换为 `host Source + relative subpath`，再挂载到 Terminal 容器 `/workspace` 或 `/root/.hermes`。
4. 外层挂载为 named volume 时，优先使用 volume name + `volume-subpath`；Docker/Podman 版本不支持安全 subpath 时拒绝 strict Docker backend，不退化为挂载整个 Hermes home。
5. 对转换结果做 canonical path、允许根和 mount type 校验；不得根据请求中的任意路径拼接 Docker mount 参数。
6. 启动最小探针容器执行双向 sentinel 验证，确认 Terminal 容器和 Runner 能互相观察到创建、内容更新、原子 rename 与删除；不要求 Docker Desktop 等虚拟化文件系统返回相同 inode。验证成功结果按 mount identity 缓存，但每轮仍验证目标 subpath。
7. inspect、路径转换、Docker socket 权限、UID/GID 或 sentinel 任一失败时，在 Agent 启动前返回 `503 strict_docker_mount_unavailable`，绝不改用 Docker 自有 workspace。

单容器启用 Docker backend 的部署前提是外层容器安装 Docker CLI 并显式挂载 `/var/run/docker.sock`。

Docker socket 具备近似宿主机 root 的控制能力，必须在部署文档和 deep health 中明确展示；未启用 Docker backend 时不挂载 socket。


### 4.6 一致性边界

snapshot 不是全主机快照。strict worker 必须在 OS 隔离边界内无法写入真实根或其它宿主机目录。外部编辑器在 baseline 后修改真实 workspace 不进入 work，并在步骤 8 被识别为冲突。

步骤 4 完成标准：四种部署/backend 候选组合必须先通过各自隔离门禁。

Agent、File Tool、Terminal、execute_code 和允许的 MCP 只能写 shadow；真实根在执行阶段不可写；snapshot 对不稳定源文件 fail closed。


## 步骤 5：运行 Agent、处理并发并完成进程收敛

每轮进入 `running` 前必须已经完成步骤 4。Runner 只调度绑定本轮 `stream_id/isolation_id` 的 worker、工具进程和容器，不复用上一轮执行环境。

### 5.1 多会话并发模型与锁协议

多会话可以同时执行，但并发单位是“隔离的 run”，不是让多个 Agent 直接写同一真实目录。

每轮都拥有独立的 baseline、work、runtime home、worker 进程组和 Docker 容器；`session_id`、`turn_id`、`stream_id` 与 `isolation_id` 必须绑定到同一 run，任何控制操作都先校验该绑定关系。


并发行为固定为：

| 场景 | 执行阶段 | 应用阶段 | 预期结果 |
|---|---|---|---|
| 不同 workspace，且不共享 Profile 根 | 可并行 | 不同真实根可并行 | 各自独立完成，只竞争全局 CPU、内存、磁盘和 Docker 配额 |
| 同一 workspace，修改不同路径 | 可基于各自 baseline 并行 | 同一 workspace 的 apply 串行 | 通常均成功；后应用者仍逐路径校验 baseline |
| 同一 workspace，修改同一路径 | 可基于各自 baseline 并行 | 同一 workspace 的 apply 串行 | 先应用者成功；后应用者发现真实 PathState 已偏离 baseline，标记 `conflict`，不得覆盖 |
| 不同 workspace，但共享同一 Profile | workspace 部分可并行 | Profile 根的 apply 串行 | workspace 变化互不阻塞；同一 Profile 文件按 baseline 规则成功或冲突 |
| workspace 或 Profile 正被外部程序修改 | 不阻塞 Agent 在 shadow 中运行 | apply 时重新校验 | 外部变化保留，本轮对应路径标记冲突 |

锁协议如下：

1. 每个真实 workspace 和 Profile 根都以 `canonical root path` 的 hash 映射到同一套跨进程读写锁；不能按未经规范化的请求路径建锁。
2. snapshot 对本轮涉及的真实根获取共享锁，只持有到 baseline 副本及 `baseline.index` 完成；apply 对会被写入的真实根获取独占锁，只持有到该批路径写入、状态落盘和目录 `fsync` 完成。
3. 一个阶段涉及 workspace 与 Profile 两个根时，先按 canonical root path 的字节序排序，再依次取锁，释放时逆序执行；所有恢复、手工 resolve 和 GC 中会触碰真实根的流程都遵循同一顺序，避免死锁。
4. Agent 在 shadow work 中运行以及 capture/CAS 写入期间不持有真实根锁。长时间工具调用不能阻塞其它会话 snapshot 或 apply；capture 只读本轮已收敛的 shadow。
5. 同一真实根的 apply 即使修改路径集合互不相交也保持串行，首版不做路径级锁。冲突判断仍逐路径执行，锁只消除 apply 之间的检查后写入竞态，不能替代 baseline 比较。
6. 锁等待必须有超时、取消检查和可观测指标；超时返回可重试状态并保留已捕获 ChangeSet，不能绕过锁直接写入。进程异常退出后锁由操作系统释放，恢复流程依据 apply intent 判断继续、回滚单路径或标记冲突。

取消和故障必须按 run 隔离：取消某个 `stream_id` 只设置该 run 的取消状态，并终止其 worker 进程组、Terminal 子进程及带相同 `hermes-stream-id` 标签的容器；不得使用按 profile、workspace 或容器镜像批量停止的方式。

一个 run 的捕获、应用或恢复失败不能取消同 workspace 的其它 run，也不能释放其它 run 持有的锁。


Runner 必须执行步骤 10 定义的背压和资源上限。达到并发上限时 run 进入有界 `queued` 状态；达到单轮安全上限或磁盘余量不足时 fail closed，不能跳过文件后声称 ChangeSet 完整。

### 5.2 终止屏障

新增 `integration/turn_files/capture.py`、`diff.py` 和 `cas.py`。

`capture.py` 负责终止屏障和稳定遍历，`diff.py` 负责 PathState 比较，`cas.py` 只负责 blob 校验、原子写入和读取。

收到最终回答、取消或错误后，Runner 按以下顺序执行：

1. 将 run 状态从 `running` 原子更新为 `quiescing`，拒绝新的 tool/approval/message 控制。
2. 通知 Agent 停止调度新工具，等待当前工具限定时间完成。
3. Local backend 对本轮进程组发送 `TERM`，等待后发送 `KILL`；Docker backend 根据 transaction journal 中的 container ID 执行 `docker stop/kill/rm`，并按 `hermes-stream-id` 标签复查不存在仍运行的同轮容器。
4. 等待所有已知 PID 被回收、Docker bind mount 写入可稳定读取，并重新确认双向 sentinel 对应的 mount identity 未变化。
5. 写入 `quiesced` transaction journal 并 fsync；只有到达该屏障后才允许扫描 work。

如果仍检测到 work 文件持续变化，读取采用“`lstat -> 流式读取/hash -> lstat`”校验并最多重试三次；仍不稳定则整轮 `capture_status=failed`，不能把不一致快照标记为完整。

### 5.3 确定 outcome 与后续动作

- 正常完成设置 `outcome=completed`，进入步骤 6；capture 完整后可自动进入步骤 8。
- 用户取消设置 `outcome=cancelled`，完成终止屏障后仍进入步骤 6；capture 完整后进入 `pending_review`。
- 模型或工具错误设置 `outcome=errored`；Runner/worker 非预期退出设置 `outcome=interrupted`。两者 capture 完整后也进入 `pending_review`。
- capture 无法证明完整时设置 `capture_status=failed`，禁止 apply，并保留受限诊断目录供恢复或人工检查。

步骤 5 完成标准：所有本轮进程和容器均已停止，work 可稳定读取；取消只影响目标 run；不同 root 可并行，同一 root 的 snapshot/apply 遵守锁顺序；每种退出都有唯一 outcome。

## 步骤 6：计算 diff 并写入 CAS

### 6.1 PathState 和 diff 矩阵

对 baseline 与 work 分别完整遍历纳入范围，构造：

```text
PathState(root_kind, relative_path, file_type, sha256, size, mode, symlink_target)
```

比较规则固定为：

| baseline | work | action |
| --- | --- | --- |
| 不存在 | 普通文件或 symlink | `created` |
| 存在 | 不存在 | `deleted` |
| 类型不同 | 存在 | `type_changed` |
| 类型相同、内容或链接目标不同 | 存在 | `modified` |
| 内容相同、mode 不同 | 存在 | `metadata_changed` |
| 全部相同 | 存在 | 不生成记录 |

目录使用步骤 3 定义的内部 `DirectoryPathState` 参与同一矩阵。目录创建、删除、mode 和 file/directory type change 必须进入依赖排序，即使最终不投影为用户可见 artifact。

不做 rename 猜测，因此重命名稳定表示为 `deleted + created`。普通文件必须完整读取并计算 SHA-256；mtime/size 只能用于展示和稳定性校验，不能跳过最终 hash。

### 6.2 CAS 写入与完整性校验

- `created/modified/type_changed` 的新普通文件写 after blob；`modified/deleted/type_changed` 的旧普通文件写 before blob；metadata-only 可让 before/after 引用同一 hash。
- blob 写入同一 CAS 目录下的随机临时文件，边读边 hash，完成后执行 `fsync(file) -> chmod 0600 -> rename -> fsync(parent)`。
- 目标 hash 已存在时必须重新计算现有 blob 的 SHA-256，不能只校验类型和大小。复用、下载和 apply 时校验失败均应隔离损坏 blob 并 fail closed。
- CAS 可增加后台 scrub，定期验证 blob 文件名、内容 hash、权限和数据库引用；scrub 不能与在途 capture/GC 竞态。
- symlink 不读取目标，target 直接保存在 `file_changes`；下载内容接口对 symlink 返回结构化元数据而不是目标文件内容。
- 单个文件读取失败、磁盘不足、CAS rename 失败或遍历错误都会让整轮 capture 失败。事务目录和错误码保留供恢复，不能进入步骤 8。

步骤 6 完成标准：相同 baseline/work 得到相同 ChangeSet；临时节点和同内容重写不出现；目录、mode、删除和 type change 准确归类；损坏或不完整 blob 永不用于 apply。

## 步骤 7：持久化账本、恢复和 GC

### 7.1 Store 所有权和连接策略

新增 `integration/turn_files/store.py`、`recovery.py` 和 `gc.py`。

数据库固定为 `STATE_DIR/turn_files.db`；`recovery.py` 只处理非终态事务和 apply intent，包括依据 container ID/stream label 停止 Docker backend 的遗留容器；`gc.py` 只处理已失去引用的 blob/complete 事务目录。

所有进程只能通过 store 模块访问数据库，连接启用 `journal_mode=WAL`、`foreign_keys=ON`、`busy_timeout=5000`；Runner 是运行期主写入方，WebUI 只执行查询以及会话删除/截断产生的生命周期事务。


state volume 必须是支持 SQLite 文件锁的本地 bind/named volume；NFS、SMB 等不能可靠提供锁语义的目录不属于 strict 首版支持范围，启动 deep health 必须检测并明确报错。

### 7.2 数据表

`change_sets` 至少包含：

| 字段 | 作用 |
| --- | --- |
| `id` | 随机不可猜测 ChangeSet ID，主键 |
| `session_id/turn_id/stream_id/turn_key` | WebUI 轮次关联；`stream_id` 唯一 |
| `workspace_root/profile_name` | 恢复和授权校验，不直接返回前端 |
| `state/outcome` | 事务状态与 `completed/cancelled/errored/interrupted` |
| `policy_json/policy_hash` | 本轮冻结规则 |
| `capture_status/apply_status` | 独立表示捕获与合并结果 |
| `runner_instance_id` | 故障诊断和恢复所有权 |
| `started_at/captured_at/completed_at` | 生命周期时间 |
| `error_code/error_detail` | 可诊断但已脱敏的错误 |

`file_changes` 至少包含 `change_set_id`、`root_kind`、`relative_path`、`action`、before/after type、hash、size、mode、symlink target、`apply_state`、`conflict_reason`、时间戳，并建立 `UNIQUE(change_set_id, root_kind, relative_path)`。

外键删除采用 cascade；按 `session_id+turn_id`、`stream_id` 和 CAS hash 建索引。


### 7.3 状态机与事务边界

数据库分别持久化步骤 0 定义的正交状态：

```text
run_phase:
  queued -> preparing -> prepared -> running -> quiescing
         -> capturing -> captured -> applying|pending_review -> terminal

outcome:
  unknown | completed | cancelled | errored | interrupted

capture_status:
  not_started | in_progress | complete | failed

apply_status:
  not_started | pending_review | applying | applied
  | partially_applied | conflicted | failed
```

- `run_phase` 只能通过 `compare-and-set(expected_phase, next_phase)` 前进；outcome 一旦离开 `unknown` 不得被普通重试改写。
- `captured` 必须在全部 `file_changes` 和 CAS 文件持久化后，用一个 SQLite transaction 提交。
- 每条 apply 前先写 `apply_state=applying` 和 intent；文件系统操作完成后再写 `applied/conflict/failed`。崩溃恢复根据真实文件 hash 判断 intent 是否已完成。
- 完整 ChangeSet 查询只读取 `captured` 之后的记录；`preparing/running` 只能返回状态摘要，不能伪装成空变更集。
- Run Journal、`transaction.jsonl` 和 `turn_files.db` 分歧时，分别按步骤 1 的所有权修复派生状态，不能让任一派生账本覆盖另一层的权威事实。

### 7.4 会话删除、CAS 租约和 GC

CAS 引用通过 `file_changes.before_sha256/after_sha256` 查询派生，不维护手工 refcount。prepare/capture、下载和 scrub 中的 blob 使用有期限租约，GC 必须忽略有效租约对象。

会话删除、清空或按 turn 截断时，固定执行：

1. 在 store 中写 session/turn tombstone，并拒绝对应范围的新 run 和新 CAS 引用。
2. 取消或明确终结活跃 run，等待 capture/apply 到达允许删除的状态。
3. 在同一生命周期事务中删除对应 ChangeSet 和 Manifest 投影。
4. Runner 恢复流程看到 tombstone 时不得重新提交引用或恢复 apply。
5. 最后启动 GC。

GC 执行顺序：

1. 获取 GC lock，并创建当前被引用 hash 的临时集合。
2. 合并有效租约，只删除未被引用、无租约且早于安全窗口的 blob。
3. blob 删除后 fsync 所在目录；空 prefix 目录可清理。
4. 最后清理 complete 且超过保留期的 baseline/work，非终态事务永不由普通 GC 删除。

步骤 7 完成标准：Runner 在任一非终态被 SIGKILL 后可幂等恢复；异常 outcome 仍能完成 capture 而不自动 apply；删除会话后不会复活引用；GC 只回收无引用且无租约 blob。

## 步骤 8：应用文件、检测冲突和人工确认

### 8.1 自动应用门槛、锁和冲突判断

新增 `integration/turn_files/apply.py` 和 `safe_fs.py`。

`safe_fs.py` 集中实现 anchored directory fd、`O_NOFOLLOW`、同目录临时文件和 fsync，不能在 handler 中散落普通 `Path.write_*`；`apply.py` 按真实 root 的 canonical path hash 获取跨进程独占 apply lock，使同一 workspace/Profile 一次只合并一个 ChangeSet，不同 root 可并行。


只有 `outcome=completed` 且 `capture_status=complete` 的 ChangeSet 默认进入自动 apply。`cancelled/errored/interrupted` 必须保持 `apply_status=pending_review`，不能因路径无冲突而自动写回。

每条变化应用前重新读取真实路径并与 baseline `PathState` 比较：

- `created`：真实路径仍不存在才可应用。
- `modified/metadata_changed/deleted`：真实类型、内容 hash、mode 和 symlink target 与 baseline 完全一致才可应用。
- `type_changed`：真实旧类型和旧内容仍与 baseline 一致才可替换。
- 路径任一父级变为 symlink、解析后出根、无法读取或已被外部修改，一律冲突，不覆盖当前文件。

### 8.2 应用顺序和原子操作

1. 先按深度从深到浅处理删除，避免父目录影响子路径检查。
2. 再创建所需父目录，按浅到深处理 created/modified/type_changed。
3. 普通文件从 CAS 写入真实目标同目录临时文件，恢复目标 mode，执行 `fsync -> os.replace -> fsync(parent)`。
4. symlink 在同目录创建临时链接后原子 rename；创建前再次通过 anchored directory fd 校验父路径。
5. metadata-only 使用 fd 操作 mode；删除使用 `dir_fd` + 不跟随链接的 API。
6. type change 先写 apply intent，再安全移除旧节点并原子放入新节点；恢复时依据 before/after 状态决定继续或标记冲突。

首版不承诺整个 ChangeSet 全有或全无，而是“所有非冲突路径都应用”。

单路径 IO 失败标记 `failed`，继续处理其它已经验证安全的路径，最终 `apply_status` 为 `applied`、`partially_applied`、`conflicted` 或 `failed`。


### 8.3 人工确认和解决冲突

人工接口同时支持 ChangeSet 级确认和单路径 resolve。单路径请求包含 `session_id`、`turn_id`、`root_kind`、`path`、`resolution=apply_archived|keep_current` 和可选 `expected_current_sha256`：

- `apply_archived` 必须重新授权会话和路径，并使用 expected hash 做 compare-and-swap；当前文件再次变化返回 `409 current_file_changed`。
- `keep_current` 只更新该条 `apply_state=kept_current`，不修改磁盘。
- 已解决请求按相同参数重试返回原结果；不同决策再次提交返回 `409 already_resolved`。

异常轮次经用户确认后仍执行完整锁、授权和 compare-and-swap 流程。确认只改变 apply 门槛，不能绕过冲突检测，也不能覆盖 tombstone 会话。

步骤 8 完成标准：外部修改不被覆盖；同路径后应用者冲突；异常轮次未经确认不写真实目录；apply 崩溃可依据 intent 恢复且不重复覆盖或删除。

### 9.3 Manifest 投影

新增 `integration/turn_files/manifest_projection.py`，只把 ChangeSet 投影到现有 `session_manifest.db`：

- `created/modified/metadata_changed/type_changed` 生成 artifact；`deleted` 只保留在详细 ChangeSet。
- workspace path 保存 workspace 相对路径。Profile artifact 的 `path` 保存 Profile 根内相对路径，并使用现有独立 `profile` 字段，禁止编码成 `profile:<path>`。
- 已应用且仍存在的 workspace 文件可继续使用 `preview=file`。Profile、冲突、删除和归档版本使用新增 `preview=turn_file`，由 ChangeSet 内容接口预览。
- `source_tool` 固定为 `turn_files`，不伪造具体写入工具。新增可选 `turn_file` 元数据包含 `change_set_id`、`root_kind`、`apply_state`，不得把内部真实根或 CAS hash 返回前端。
- `preview=turn_file` 和 `turn_file` 属于版本化 Manifest wire contract 扩展，必须先同步修改 `docs/api/session-manifest-api.md`、artifact RFC、后端 projection 和前端 preview gate，不能宣称旧 schema 原样兼容。
- strict 新轮次以 ChangeSet 为唯一 artifact 权威来源，关闭 `_extract_turn_artifact_entries`、assistant prose 和 diff 正则回填；历史轮次及 off 模式继续使用原 backfill。
- ChangeSet 即使包含零条变化，也作为该 strict 轮次的 authority marker；Manifest 构建看到该标记后必须返回空 artifacts，不能因为 store 中没有 artifact 行而触发旧 backfill。
- 投影失败不能反向改变已提交 ChangeSet；记录 repair-needed，`GET /api/session/manifest` 可从 ChangeSet 幂等修复缺失 artifact。

### 9.4 前端接入

- `static/messages.js` 监听 `turn_files`，按 `stream_id + change_set_id` 去重，保存状态摘要，并在终态后拉取权威查询接口。

- SSE 仅作即时提示；页面刷新、SSE 重放或切换会话后始终以 GET 结果覆盖本地缓存。

步骤 9 完成标准：新 strict 轮次的 artifact 与 ChangeSet 投影一致；Profile 不污染 path 语义；冲突和历史版本通过授权接口读取；旧会话、旧 Manifest schema 和 off 模式不回归。

### 10.1 功能开关与部署配置

- 增加 `HERMES_WEBUI_TURN_FILES=off|strict`，初始默认 `off`；`strict` 强制使用 runner，不允许 best-effort fallback。
- strict 模式下若 `HERMES_WEBUI_RUNTIME_ADAPTER` 未设置，则内部按 `runner-local` 处理；若操作者显式设置为 `legacy-direct` 或 `legacy-journal`，启动健康检查报配置冲突并拒绝 strict 新会话，不能由配置优先级意外绕过捕获。
- strict 使用步骤 0 的 G2 所选 Runner 拓扑。中断恢复分支由 `server.py` 注入内存 base URL/key；跨 WebUI 存活分支使用受保护的 discovery 和 key 交接机制。
- 操作者显式设置外部 `HERMES_WEBUI_RUNNER_BASE_URL` 时，若不满足当前 strict 拓扑和协议校验，应拒绝新会话；off 模式保留既有外部 Runner 兼容行为。
- Bearer 不得进入 Compose 明文、日志或 worker 环境。是否使用受权限保护的短期 key 文件，由 G2 的跨生命周期方案决定并接受独立安全评审。
- 每轮 worker 从 Profile 配置冻结 `TERMINAL_ENV=local|docker`。strict Docker backend 强制关闭 `TERMINAL_CONTAINER_PERSISTENT` 和跨进程复用，并覆盖 workspace/Profile mount；不能由用户环境变量重新打开。
- 单容器使用 Docker backend 时，Compose 由管理员选择性增加 `/var/run/docker.sock:/var/run/docker.sock`；可增加 `HERMES_WEBUI_OUTER_CONTAINER_ID` 作为自动 inspect 失败时的受控显式标识。未配置 socket 时 local backend 仍可正常使用。
- 增加有界参数 `HERMES_WEBUI_RUNNER_START_TIMEOUT`、`HERMES_WEBUI_RUNNER_DRAIN_TIMEOUT`，使用安全默认值且限制取值范围；重启退避和失败窗口使用代码常量，首版不暴露无限可调配置。
- `.hermes-turn-files.json` 只接受版本号、`include`、`exclude`，规则在轮次开始时冻结。
- `turn_files` SSE 和查询响应均带 `capture_status`、`apply_status`、`outcome`，调用方不得将 `failed/degraded` 展示为完整结果。
- 新增接口同步更新 integration Swagger、路由表和运行架构文档。

### 10.2 背压与资源上限

Runner 必须提供有界安全默认值，并允许管理员在受控范围内配置：

- 全局活跃 worker 数、同时 prepare/snapshot 数、同时 capture/hash 数和同时启动 Docker 容器数。
- 队列长度、排队超时、单轮执行超时、锁等待超时和 drain 超时。
- 单轮文件数、单文件大小、总捕获字节数、事务目录空间和最低磁盘余量。

达到并发上限时进入可取消的 `queued`；队列满返回稳定错误码。达到单轮配额或磁盘门槛时 fail closed，保留可诊断状态，不得跳过内容后报告完整。

G2 若选择 Runner 跨 WebUI 存活，队列也由 Runner 持久拥有；若选择中断恢复，WebUI 重启必须明确终结排队 run。两种行为需分别测试。

### 10.3 可观测性和安全检查

- 指标至少包含 `prepare_ms`、`queue_ms`、`hash_ms`、`bytes_hashed`、`cas_new_bytes`、`apply_ms`、锁等待、冲突数、恢复次数和 GC 数量。
- deep health 报告 Runner、协议版本、backend、Docker mount、磁盘余量和最近错误，但不返回 Bearer、凭据、真实 CAS 内容或完整环境。
- 日志对 Authorization、Provider 凭据、session cookie、路径中的敏感片段和错误详情执行集中脱敏。

步骤 10 完成标准：所有资源都有所有者、上限、超时、取消和清理路径；不支持的部署在启动前明确失败；运维指标能区分 unavailable、degraded、capture failed、pending review 和 apply conflict。


## 步骤 11：测试、灰度、回滚和验收

### 11.1 实施批次和灰度

1. **基础存储批次**：先落 `models/policy/snapshot/diff/cas/store/apply` 及纯临时目录测试，不接真实聊天路由。该批次可独立验证 ChangeSet 准确性。
2. **Runner 契约批次**：按 G2 选定的生命周期实现 runner、幂等 start、journal/cursor 和 restart/reattach 或中断恢复测试。
3. **Local backend 批次**：先实现并证明 G1 要求的 OS 级隔离；不能证明时保持 unsupported，不得只靠 cwd/env 开启 strict。
4. **Docker backend 批次**：实现每轮 Terminal 容器、固定 shadow mounts、禁用复用、UID/GID、双向 sentinel、停止屏障和孤儿恢复，先打通全本地 Docker。
5. **单容器 Docker 批次**：实现 outer-container inspect、bind/named-volume subpath 转换、Docker socket preflight 和 mount broker 失败诊断。
6. **API/UI 批次**：接入 turn_files SSE、查询/内容/冲突接口和 Manifest authority marker，再增加 Session Inspector 展示。
7. **灰度批次**：保持默认 `off`，分别灰度四种部署/backend 组合，观察 prepare/hash/apply 延迟、Docker mount 失败、恢复率和磁盘增长后再扩大范围。

### 11.2 回滚

回滚将 `HERMES_WEBUI_TURN_FILES` 设为 `off` 并恢复 `legacy-direct`，但不删除 `turn_files.db`、CAS 或历史 ChangeSet。

已产生的 strict 历史轮次继续可读。回滚不能对这些轮次重新启用正则 artifact 回填；人工 resolve 在 Runner 不可用时明确返回不可用状态，不能由 WebUI 直接写 workspace。

### 11.3 测试矩阵

- 单元测试覆盖 CoW/full-copy 回退、规则优先级、安全 deny、symlink 逃逸、内容 hash、CAS 去重和原子写入。
- 差异测试覆盖新增、覆盖、同内容重写、权限变化、删除、类型变化、重命名、Unicode 路径、二进制和大文件。
- 集成测试分别通过 `write_file`、shell 重定向、Python 脚本、构建命令、MCP 和 Docker 创建文件，断言 ChangeSet 与磁盘最终状态完全一致。
- 后端矩阵覆盖“全本地/单容器 × local/docker”。local 只有通过 OS 隔离门禁才运行成功用例，否则必须断言 strict 在启动前拒绝。
- Docker backend 测试覆盖默认 sandbox 被禁止、跨轮容器不复用、custom volume 冲突、UID/GID、双向 sentinel、外层 bind 路径转换、named volume subpath 不支持、Docker socket 缺失和遗留容器恢复。
- 并发测试覆盖不同根并行、同一 workspace 不同路径并行执行且串行应用、两个会话修改同一路径、外部编辑器中途修改、Profile 共享资产冲突、workspace 与 Profile 多根锁顺序、锁等待取消/超时和部分合并状态。
- 隔离测试覆盖取消一个 run 时同 workspace 的其它 run 继续执行，且只清理匹配 `stream_id/isolation_id` 的进程组和 Docker 容器。
- 背压测试覆盖 prepare/capture/hash/Docker 并发上限、队列上限、单轮文件/字节/时间配额、磁盘余量不足，以及 CAS GC 不删除带在途租约的 blob。
- 生命周期测试覆盖成功、取消、模型错误、worker/Runner SIGKILL、应用中崩溃、WebUI-only 重启、外层容器重启、后台进程持续写入和 tombstone 删除竞态。
- outcome 测试断言只有 `completed` 默认自动 apply；`cancelled/errored/interrupted` 完整捕获后保持 `pending_review`，未经确认不修改真实目录。
- API 安全测试覆盖越权 session、路径穿越、直接 hash 猜测、已删除会话、截断轮次和凭据文件不入 CAS。
- UI 回归测试验证普通、Profile、冲突、历史归档和文件已删除后的 artifact chips；桌面与移动端均不出现溢出。
- 性能指标记录 `prepare_ms`、`hash_ms`、`bytes_hashed`、`cas_new_bytes`、`apply_ms` 和冲突数，不允许因性能优化跳过最终内容校验。

### 11.4 最终验收

所有步骤完成标准均通过后，才允许在灰度环境开启 strict。验收报告必须列出 G1-G4 的最终决策、四种 backend 组合的支持状态、未验证范围、失败注入结果和回滚演练结果。

## 附录：特殊名词与缩写

本节解释方案中反复出现的工程术语。这里有两个容易混淆的“CAS”：单独写作 **CAS 存储**时指内容寻址存储；写作 **compare-and-swap** 时指比较后再更新。两者不是同一概念。

### 文件事务与归档

- **ChangeSet（变更集）**：一轮 Agent 执行结束后，由 `baseline` 与 `work` 的最终状态比较得到的权威文件变更清单。它记录路径、变更类型、变更前后内容引用、合并结果和冲突原因。
- **文件事务**：先在隔离副本中执行文件操作，结束后统一捕获差异并尝试合并到真实目录的过程。本方案不承诺整个 ChangeSet 全有或全无，而是逐路径安全应用。
- **baseline（基线）**：本轮开始时 workspace 或 Profile 资产的冻结副本，用来判断本轮改了什么，以及合并时真实文件是否已被外部程序修改。
- **work / shadow workspace（工作副本 / 影子工作区）**：Agent、File Tool、Terminal 和 MCP 在本轮实际读写的隔离目录。执行期间产生的文件先留在这里，不直接写入真实 workspace。
- **PathState（路径状态）**：某个相对路径在某一时刻的结构化状态，包括文件类型、内容哈希、大小、权限 mode 和 symlink target。diff 和冲突判断都以它为输入。
- **diff（差异计算）**：比较 baseline 与 work 的最终 PathState，生成 `created`、`modified`、`metadata_changed`、`deleted` 或 `type_changed` 记录。
- **CAS（Content-Addressed Storage，内容寻址存储）**：以内容的 SHA-256 哈希作为存储地址的归档区。相同内容只保存一份，ChangeSet 通过哈希引用变更前后的文件内容。
- **SHA-256**：一种密码学哈希算法，把任意长度内容映射为固定长度摘要。本方案用它标识文件内容、校验 CAS blob，并判断内容是否相同；它不是加密，不能隐藏内容。
- **blob（二进制大对象）**：CAS 中保存的一份原始文件内容。blob 名称来自内容哈希，不包含原文件名；读取前仍须通过 session、turn 和 path 做授权。
- **GC（Garbage Collection，垃圾回收）**：删除已不再被任何 ChangeSet 引用的 CAS blob 和过期事务目录。GC 必须避开仍在捕获或尚未提交引用的在途数据。
- **policy snapshot（策略快照）**：本轮开始时冻结的 include、exclude 和固定安全规则。执行期间即使配置文件变化，本轮仍使用原快照，以保证捕获口径稳定。
- **hard deny（固定安全拒绝）**：无论项目配置如何都不能捕获或归档的路径规则，例如凭据、认证状态和 WebUI 内部状态。它的优先级高于用户 include。

### 一致性、持久化与恢复

- **RFC（Request for Comments）**：用于评审重要设计和行为契约的设计文档。RFC 先说明目标、非目标、状态机、兼容性和验收条件，再由后续代码实现；它不是 HTTP 请求。
- **状态机**：只允许对象沿预先定义的状态和方向变化。本方案把 `run_phase`、`outcome`、`capture_status` 和 `apply_status` 分开持久化，非法转换应被拒绝。
- **幂等**：同一个请求或恢复步骤执行一次与重复执行多次，最终效果相同。例如相同 payload 的 `POST /v1/runs` 重试应返回原 run，而不是再启动一轮。
- **journal（事务日志）**：按顺序记录已经发生的关键 intent 和状态变化，用于进程崩溃后的判断与恢复。`transaction.jsonl` 服务于文件事务恢复，不等同于浏览器 SSE 事件流。
- **WAL（Write-Ahead Logging，预写日志）**：SQLite 的一种日志模式。数据库先把修改写入 WAL，再合并到主数据库文件，可改善并发读写和崩溃恢复，但仍要求底层文件系统提供可靠锁语义。
- **fsync**：要求操作系统把文件或目录的关键修改刷新到持久存储。只调用 `write` 或 `rename` 不代表断电后一定可见，因此关键状态和原子替换后还要执行 fsync。
- **原子 rename / replace**：文件系统对外只显示操作前或操作后的完整名字绑定，不暴露中间的半写文件。它通常只在同一文件系统、同一挂载内成立。
- **compare-and-swap（比较后更新）**：应用归档版本前，先确认真实文件仍等于预期 baseline 或 `expected_current_sha256`；只有比较成功才更新，否则返回冲突。
- **apply intent（应用意图）**：真正修改文件系统前先持久化的记录，说明准备对哪个路径执行什么操作。崩溃恢复据此判断操作未开始、已完成还是状态不确定。
- **capture / apply（捕获 / 应用）**：capture 从 baseline 与 work 生成 ChangeSet 并写入 CAS；apply 把 ChangeSet 中的非冲突结果合并到真实目录。两者状态必须分开记录。
- **fail closed（失败闭合）**：无法证明捕获完整、路径安全或当前文件未变化时，选择不合并并明确报错，而不是按成功或允许处理。

### 文件系统安全

- **CoW（Copy-on-Write，写时复制）**：创建副本时先共享底层数据块，只有文件被修改时才复制相关内容。macOS `clonefile` 和 Linux `FICLONE` 可降低副本的时间与空间成本。
- **symlink（符号链接）**：保存另一个路径作为目标的特殊文件。遍历时使用 `lstat()` 读取链接本身，不跟随目标；否则可能越过 workspace 边界读取或覆盖其它位置。
- **anchored fd（锚定目录文件描述符）**：先安全打开可信目录，再用 `dir_fd` 相对操作子路径。它减少“检查路径安全后，父目录被替换成 symlink”的检查与使用时间差。
- **`O_NOFOLLOW`**：打开路径时拒绝跟随符号链接的操作系统标志。它与 anchored fd 配合，用于降低 symlink 调包和路径逃逸风险。
- **TOCTOU（Time of Check to Time of Use）**：路径通过安全检查后、真正使用前被并发替换的竞态。合并逻辑应尽量持有已验证句柄，并在使用点再次校验。
- **mode bits（权限位）**：POSIX 文件的读、写、执行权限，例如 `0644`。本方案记录 mode 变化，但不把 uid、gid、ACL、xattr 等扩展元数据纳入首版权威口径。

### Runner、容器与通信

- **Runner**：位于 WebUI 与 Hermes Agent 之间的独立执行进程，负责 run 生命周期、Agent worker、事件、取消控制、事务目录、ChangeSet、CAS 和合并。
- **Supervisor（监督器）**：负责启动 Runner、健康检查、监控退出、退避重启和关闭收敛的生命周期组件。它由 `server.py` 还是独立服务承担，取决于步骤 0 的 G2 决策。
- **worker**：Runner 为单轮会话启动的 Agent 执行进程。每轮 worker 使用独立环境和进程组，避免不同轮次共享 cwd、HERMES_HOME 或后台进程。
- **TERM / KILL**：TERM 请求进程自行清理后退出；超过限定时间仍未退出时使用 KILL 强制终止。KILL 无法执行进程内清理，因此恢复必须依赖已落盘状态。
- **loopback**：仅本机可访问的网络地址，通常是 `127.0.0.1`。Runner 绑定 loopback，避免其控制接口直接暴露到局域网或公网。
- **Bearer key**：WebUI 调用 Runner HTTP API 时携带的临时认证密钥。它只用于控制面认证，不应写入日志、命令行、持久配置或 Agent worker 环境。
- **SSE（Server-Sent Events）**：服务器通过一个长期 HTTP 连接按顺序向浏览器推送事件的机制。这里用于 token、工具状态、终态和 `turn_files` 摘要，不承载完整文件内容。
- **cursor（事件游标）**：客户端已经消费到的事件位置。断线重连时从 cursor 之后继续读取，用于避免漏事件或重复投影 transcript。
- **mount broker（挂载转换器）**：单容器通过宿主机 Docker daemon 创建 sibling container 时，把外层容器路径安全转换为 daemon 可识别的宿主机 bind 或 named-volume subpath。
- **sentinel（哨兵探针）**：为验证挂载是否确实指向同一目录而临时创建的测试文件。Runner 与容器双向创建、修改、rename 和删除均可见后，才允许启动 Agent。
- **Docker socket**：Docker daemon 的控制接口，常见路径为 `/var/run/docker.sock`。把它挂入 WebUI 容器近似授予宿主机 root 级控制能力，因此必须由管理员显式启用。
- **sibling container（同级容器）**：由外层 WebUI 容器通过宿主机 Docker daemon 启动的另一个容器。它不是 WebUI 容器的真正子容器，看到的是宿主机挂载命名空间。
- **deep health（深度健康检查）**：除“进程仍在”外，还检查 Runner 协议、Docker daemon、挂载转换、权限和最近一次 sentinel 等依赖是否可用的诊断接口。

### 状态标识与界面投影

- **`session_id`**：会话身份，关联 transcript、Profile、workspace 和授权范围。
- **`turn_id`**：一次用户提交及其 Agent 响应的持久身份，用于 turn journal、ChangeSet 和恢复关联。
- **`stream_id` / `run_id`**：一次运行及其 SSE 事件流的身份。本方案首版令 `run_id == stream_id`，减少额外映射。
- **`turn_key`**：Session Manifest 中一轮消息的稳定键，通常形如 `turn:42`。它与 `turn_id` 用途不同，不能依赖字符串相等进行关联。
- **Session Manifest**：从会话活动派生的 Tasks、Artifacts、References 和 per-turn 轻量索引。它不是 transcript、运行 journal 或完整 ChangeSet。
- **projection（投影）**：把 ChangeSet 中适合界面消费的部分转换成 Session Manifest artifact 行。ChangeSet 是文件变更事实，Manifest 是面向 UI 的派生视图。
- **authority marker（权威标记）**：表示某个 strict turn 已由 ChangeSet 作出“有成果”或“零成果”决定。即使零变化也要保留标记，避免旧文本回填逻辑再次猜测 artifact。
- **backfill / read-repair（历史回填 / 读取修复）**：backfill 从旧会话证据补建缺失索引；read-repair 在读取时修复可确定的缺失派生数据。它们不能覆盖已有权威 ChangeSet 决定。
