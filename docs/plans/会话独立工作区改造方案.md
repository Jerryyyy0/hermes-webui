# 会话独立工作区改造方案

## 结论

可以将每个由 WebUI 创建的普通会话分配到独立目录：

```text
HERMES_WEBUI_DEFAULT_WORKSPACE/sessions/<session_id>/
```

但 `HERMES_WEBUI_DEFAULT_WORKSPACE` 必须继续表示**共享根目录**，不能在环境变量中拼接或展开 `${session_id}`。后端生成可信 `session_id` 后，在受控的 `sessions/` 命名空间创建目录，并将绝对规范化路径持久化为 `Session.workspace`。根目录中的既有文件和 external workspace 保持原有布局；仅新建的 managed 会话使用 `sessions/`。

此方案不会破坏 turn artifact 对齐；固定的 session workspace 反而消除共享目录中同名文件互相覆盖的风险。前提是：一旦后端分配了该目录，`Session.workspace` 必须成为不可变的会话身份字段。当前允许在 `/api/chat/start`、`/api/session/update` 等入口重写 workspace 的行为，必须按本文收紧。

本阶段只增加后端能力，不改前端。显式指定 workspace、现有浏览器发送的继承 workspace、Git worktree 会话、导入的 CLI 会话、复制/分叉、压缩恢复、cron 和后台临时会话均须按下文的分类规则处理，不能用“每个 session”一概覆盖。

## 目标与非目标

## 实施状态

- 已实现：无显式 `workspace` 的本机和 Docker API 新会话创建并持久化 `<base>/sessions/<session_id>` managed root；显式 workspace、worktree 和旧会话保持兼容。
- 已保持：既有 `<base>/<session_id>` managed root 不移动，也不按新目录规则重解释。
- 前端不在本次改动范围内，现有浏览器仍会发送继承 workspace，继续走 external 语义。
- 已实现 managed root 的聊天/同步聊天/goal/Gateway/streaming 根固定和 integration 路径投影；manifest 的按根读取范围与 compression recovery 的 mode 继承按《会话工作区与产物隔离修复方案》处理。
- 不做自动删除、marker 或所有权注册表。删除会话不删除目录。

### 目标

- 未传 `workspace` 的 `POST /api/session/new` 为新会话创建专属 workspace。
- 同一会话的聊天、上传、文件浏览、终端与 artifact 解析始终使用同一个不可变根目录。
- 保留调用方显式传入 workspace 的现有能力，作为 opt-out。
- 对 Git 项目保留现有 worktree 隔离语义，不将一个空目录错误地当成 Git 项目。
- 允许未使用的空 managed workspace 保留在磁盘上；本方案不自动删除任何 workspace。
- 通过自动化测试证明 turn artifact 的 session/turn 归属与文件解析根一致。
- 保持现有前端与旧会话兼容，不改变其请求形状或 workspace 继承行为。

### 非目标

- 不迁移既有会话的 workspace，也不移动其文件。
- 不在本阶段修改 `static/` 下的新会话、聊天或 workspace UI。
- 不改变 Hermes Agent 的 workspace 或远程终端协议；远程 workspace 继续由远端 profile 的 `terminal.cwd` 契约处理。
- 不在本次把 workspace 文件的版本化、快照或回滚改造成 session 文件系统。
- 不自动复制任意项目目录到每个新会话。代码项目隔离使用 Git worktree，而不是无边界复制。

## 术语

| 术语 | 含义 |
| --- | --- |
| workspace base | `HERMES_WEBUI_DEFAULT_WORKSPACE` 解析出的共享根目录；历史共享文件与 external workspace 可继续位于此处。 |
| managed workspace | 后端为新 session 创建的 `<workspace base>/sessions/<session_id>` 目录。 |
| external workspace | 调用方或用户显式选择的现有目录。 |
| workspace mode | `managed`、`external` 或 `worktree`，记录 workspace 来源及可变性。 |
| session root | 某一 session 的规范化绝对 `Session.workspace`。 |
| turn artifact | 一个 `turn_key` 下、相对 session root 的已验证产物记录。 |

## 当前行为与问题

当前 `POST /api/session/new` 未提供 `workspace` 时，`new_session()` 会走 `get_last_workspace()`，其回退包含 profile 最近目录、profile 配置、`terminal.cwd` 与服务默认目录。浏览器的新对话流程会将当前会话或 profile workspace 显式传给接口。因此，单改默认目录不能让现有浏览器的新对话获得会话隔离；本阶段只让省略字段的 API 请求触发该分支。

现有路径写入口包括：

- `POST /api/session/new`：创建时可指定 workspace；
- `POST /api/chat/start` 及同步/目标等聊天入口：请求 body 可重写 `session.workspace`；
- `POST /api/session/update`：可修改 workspace，并更新全局最近目录；
- Gateway chat 路径：执行前写入 session workspace；
- 前端 `newSession()`：默认继承当前 session workspace；
- 上传、文件树、预览、压缩/恢复与终端：从 `session.workspace` 取得根目录。

Manifest 的 turn owner 是 session/lineage 与 `turn_key`，但文件 `path` 通常是相对于当时 `session.workspace` 的路径。Manifest 记录和部分 profile 索引不保存完整 workspace 根。若历史会话后来改根，`report.md` 会在新根中重新解析，造成 artifact 丢失、错指或无法预览。

## 对外契约

### 配置

保留环境变量名与含义：

```text
HERMES_WEBUI_DEFAULT_WORKSPACE=/srv/hermes/workspaces
```

它表示共享 workspace 根目录，而不是某个会话的直接工作目录。无需新增配置项：请求没有显式 `workspace` 且不请求 worktree 时，后端在该目录下创建 `sessions/<session_id>` 子目录。Docker terminal backend 仅在容器挂载同一绝对 workspace base 时走此分支；其它远程 terminal backend 保留目标侧 cwd。

已有 managed 会话可能仍使用早期布局 `<workspace base>/<session_id>`。不移动这些目录，也不根据路径形状推断 session mode；唯一权威来源仍是已持久化的 `Session.workspace` 和 `workspace_mode`。

现有浏览器当前会传递 workspace，故保持 `external` 语义。服务启动时仍验证 workspace base 可读、可写、可执行；无法验证时启动失败或在新会话请求中明确报错，不能悄悄改用其它目录。

### `POST /api/session/new`

请求语义如下：

| 条件 | `workspace_mode` | 最终 workspace |
| --- | --- | --- |
| `workspace` 非空 | `external` | 经 `resolve_trusted_workspace()` 验证的显式目录。 |
| `worktree: true` | `worktree` | 现有 worktree 工厂生成的目录。 |
| 未传 workspace | `managed` | `<workspace base>/sessions/<server-generated session_id>`。 |

若同时传入 `workspace` 与 `worktree: true`，维持现有含义：前者是 worktree 的源 workspace，而最终 session root 是 worktree 路径。`worktree: true` 的优先级高于 managed 空目录分配。

成功响应保持现有 session compact 结构；调用方通过已有的 `workspace` 字段获得最终目录。`workspace_mode` 是服务端 Session 元数据，不进入 HTTP 响应或 Session compact。

### Workspace 不变量

对 `workspace_mode: managed`：

1. `session.workspace` 在 session 创建后不可修改。
2. 所有聊天入口忽略缺失 workspace，并拒绝任何与 `session.workspace` 不相等的显式值，返回 409。
3. `/api/session/update` 不接受对 managed session 的 workspace 修改，返回 409。
4. Gateway 和本地流执行只能使用 session 已持久化的根；不得信任网关或浏览器回传的替代路径。
5. session root 由服务端生成的安全 session ID 组成，创建和使用均以该持久化字段为唯一权威来源。

对 `external` 与 `worktree` 保持当前可切换能力，仍经已有可信路径校验。禁止把“managed session 的不可变性”扩展到旧会话或显式 workspace，以避免破坏现有使用方式。

## 数据模型与目录所有权

`Session` 仅新增并持久化一个内部字段：

```text
workspace_mode: managed | external | worktree
```

现有的 `Session.workspace` 继续保存规范化后的会话根目录；`workspace_mode` 只用于服务重启后识别 managed root 的不可变性。`worktree_path`、`worktree_branch` 和 `worktree_repo_root` 继续使用现有字段。旧 session 缺少 `workspace_mode` 时一律按 legacy/external 处理，绝不从路径名称或目录结构猜测。

不保存 `workspace_base`、创建时间、nonce 或清理状态：本方案不做自动回收，也不需要目录所有权注册表。

创建目录需满足：

1. 在服务端生成 `session_id`，再构造 `base / "sessions" / session_id`；不能使用客户端提供的目录名。
2. 创建 helper 必须在 base 下以 anchored 操作创建并验证固定的 `sessions` 中间目录，再创建 session ID 叶目录；拒绝中间目录或叶目录的符号链接逃逸和竞争替换。
3. 创建 workspace 属于真实文件系统副作用，必须将 session 立即持久化，并写入 `workspace_mode: managed`。现有“零消息 session 仅驻内存”的规则不能用于此分支，否则服务重启后无法判断该 root 是否不可变。
4. 若 session 写入失败，不删除已创建目录；记录错误并返回失败。目录可能成为空的未使用目录，但本方案明确接受它长期保留，避免引入任何自动删除授权与竞态风险。

删除 session 同样不删除 managed workspace。会话记录和文件目录各自独立；用户如需清理目录，可通过系统文件管理或后续明确设计的手动操作完成。

## 端到端执行路径

```text
POST /api/session/new (无 workspace)
  -> 生成 session_id
  -> 验证 canonical workspace base
  -> anchored mkdir <base>/sessions/<session_id>
  -> new_session(session_id, workspace, workspace_mode=managed)
  -> 立即 save()
  -> 返回 session

POST /api/chat/start
  -> 加载 session
  -> resolve_workspace_for_session(session, request.workspace)
  -> managed：只返回已持久化 session.workspace
  -> external/worktree：保持现有 resolve_trusted_workspace 规则
  -> 创建 stream_turn_key 并持久化 pending state
  -> 执行端以相同 session root 运行
  -> 以相同 session root 归一化并结算 turn artifacts
```

引入一个共享的 `resolve_workspace_for_session(session, requested_workspace, *, operation)`，集中处理 chat、sync chat、goal、gateway 与 workspace update。不要在每个 route 中复制 `body.get("workspace") or s.workspace`。该 helper 返回规范化 path 和是否允许持久化更新，并在 managed 分支 fail closed。

`new_session()` 增加可选 `session_id` 和 `workspace_mode` 参数。ID 分配移动到创建编排层，普通调用仍可保持内部生成 ID，避免影响非 HTTP 的既有调用者。

## Turn Artifact 与 Manifest

### 为什么专属根不会破坏对齐

- `stream_turn_key` 在 session lock 中创建并写到当前 session 的 pending state；它不依赖 workspace 名称。
- 流完成时，artifact settlement 使用该 session 与该 turn key 的已绑定证据。
- Manifest 的路径归一化以 `Path(session.workspace)` 为根，将 workspace 内文件存为相对路径。

因此，对于两个 session 都写入 `report.md` 的情况：

```text
session A: /base/A/report.md -> A 的 turn_key
session B: /base/B/report.md -> B 的 turn_key
```

只要每个 session root 固定，重建 Manifest 时仍会解析到同一物理文件；不会产生跨 session 对齐。

### 必须修复的伴随问题

1. **workspace 根不可变**：这是历史 artifact 可重放的前提。不得在聊天前、Gateway worker 中或 session update 后改写 managed session root。
2. **持久化索引完整身份**：`session_manifest_records` 的 artifact identity 或跨会话 profile 查询不能只用相对 `path`。用于 workspace 文件浏览的索引键至少应包含 canonical `workspace_root`（或 managed session ID）和 `path`；`lineage_key + profile + turn_key + record_kind + path` 继续承担 turn 归属，workspace root 用于文件存在性与跨 workspace 查询隔离。
3. **历史兼容**：本部署已确认旧 manifest 行统一以默认 workspace 为根。空 `workspace_root` 仅在运行时逻辑映射为 canonical default workspace，数据库原值保持不变，绝不映射为当前 session workspace；历史 wire path 保持 `report.md` 等默认根相对路径，不能追加 `sessions/<session_id>`。不能确认该部署事实时保留空根并禁止预览。
4. **预览与下载**：持久化 artifact 必须通过其记录的 canonical `workspace_root` 解析，不能用当前 session root 覆盖；仅尚未持久化的 transcript 临时派生行才使用当前 session root。文件预览继续使用既有的 `/api/integration/workspace/file?path=...`，不新增接口或请求参数。只有记录根位于 canonical workspace base 内时，才把 artifact path 投影为相对 base 的 wire path：历史默认根为 `report.md`，managed 根为 `sessions/<session_id>/report.md`，base 子目录 external root 为 `project-a/report.md`。默认 base 外的 external/worktree artifact 仍保存归属记录，但不生成 `preview=file` wire row，不能以裸相对路径、绝对路径或放宽接口根目录的方式绕过该限制。
5. **artifact 证据**：绝不扫描整个 base 目录来“补齐”成果。仍只接受该 turn 的已验证工具事件、MEDIA 或最终 assistant prose，符合 Session Inspector Manifest 的派生索引语义。
6. **目录布局兼容**：新建 managed session 使用 `sessions/<session_id>`；已有 `<base>/<session_id>` managed root 和 external root 按已持久化 workspace 继续使用，不搬迁、不重写。

### 无会话 workspace 扫描

`/api/integration/workspace/files` 以 workspace base 为根递归扫描。因此只增加 `sessions/` 层级会让 managed 文件以 `sessions/<session_id>/...` 出现在扫描结果中，并不会自动减少扫描量。

这是一项独立的 UI/产品决策：

1. 若全量扫描要继续展示 managed 文件，则保留 `sessions/` 递归扫描；路径有明确命名空间，可与根目录历史共享文件区分。
2. 若全量扫描只面向历史共享 workspace，则在该扫描器中跳过 `sessions/`；按 profile 的 manifest 成果查询仍须使用完整的 `sessions/<session_id>/...` 精确路径，保证 artifact 预览可用。

无论选择哪一种，不能扫描 `sessions/` 来补齐或推断 turn artifact；目录扫描仅用于文件浏览，manifest 仍是 artifact 归属的唯一派生索引。扫描也不能使默认 base 外的 external/worktree artifact 变为可预览文件；该类记录仍按预览边界 fail-closed。

## 前端与接口调用方

### 浏览器

本阶段不修改 `newSession()`。它会继续继承并传递 `S.session.workspace`，后端因此按 `external` 创建新会话，行为与当前版本一致。

这意味着浏览器端的每会话目录分配不属于本次交付。后续若要启用，需另起一个 UI/API 变更：普通“新对话”省略 `workspace`，而“选择已有工作区”流程继续传显式路径并创建 `external` session。该后续变更需要 UI 设计、桌面/窄屏/移动端截图和独立回归测试。

所有现有聊天请求可继续带 `S.session.workspace`；managed session 下后端只接受完全相等的值。后续可考虑让聊天请求不再传 workspace，由后端从 session 读取，减少客户端可变输入，但这不在本阶段范围。

### Workspace 文件预览边界

Session Inspector 的 `preview=file` 与左侧 Workspace 文件浏览均继续使用既有接口：

```text
GET /api/integration/workspace/file?path=<workspace-base-relative-path>
```

该接口的根固定为 canonical workspace base，因而不接受默认 base 之外的绝对路径，也不根据裸
`report.md` 猜测 external root。实现不得新增 route、query 参数或以符号链接/宽松根校验规避这一边界。
默认 base 外的 artifact 可保留其 turn、lineage 和 profile 归属，但不提供文件预览；UI 不应把它显示为
可打开的 `file` artifact。

### 外部客户端

外部调用者若省略 `workspace`，将获得 managed workspace；若依赖共享默认目录，必须显式传 workspace。这是行为变更，须在 API 文档与 release note 中说明。

更新 `/api/session/new` 的 Swagger：请求字段增加 `workspace`、`worktree`，并记载 omission 会创建会话专属目录的语义。响应结构保持不变。不会新增 integration HTTP 路径。

## 会话类型决策矩阵

| 创建路径 | 默认处理 | 原因 |
| --- | --- | --- |
| API `POST /api/session/new`，无 workspace、无 worktree | 新 managed root | 本阶段目标。 |
| 非 Docker 远程 terminal profile，API `POST /api/session/new` 无 workspace | 保留远端 cwd，`external` | WebUI 主机不能为远端 Agent 创建可用的本机目录。 |
| Docker terminal profile，API `POST /api/session/new` 无 workspace | 新 managed root | Docker 容器必须以相同绝对路径挂载 workspace base，才能访问 WebUI 创建的 `<base>/sessions/<session_id>`。 |
| 现有浏览器“新对话” | `external` | 前端继承并发送 workspace，保持当前语义。 |
| WebUI 新会话，显式 workspace | `external` | 用户明确选择目录。 |
| 默认 workspace base 外的 external/worktree artifact | 保留记录，不提供 file 预览 | 现有 integration workspace 文件接口不能安全解析该根。 |
| WebUI 新会话，`worktree: true` | `worktree` | 源项目与 Git 隔离必须保留。 |
| 复制会话 | 保留源 workspace，标记 external/worktree 语义 | 复制的是会话历史，不应隐式复制或丢失项目文件。可另设“复制到新 managed root”功能。 |
| 分叉/压缩恢复/重放 | 保留来源 root | 必须能解析既有历史 artifact。 |
| CLI 导入 | 保留 Agent/CLI 声明的 workspace | WebUI 不是该会话根的 owner。 |
| cron、webhook、后台临时/ephemeral session | 显式声明根，不默认 mkdir | 其生命周期与执行 owner 不同。 |
| profile 自动绑定或首次启动 | 保持 shared/external | 不应在页面加载时制造实体目录。 |

## Git 与项目行为

每会话空目录不包含 `.git`、项目源码或依赖。若用户希望 Agent 修改既有仓库，应：

1. 显式选择该仓库作为 external workspace；或
2. 选择“新 worktree 会话”，由现有 worktree 工厂从该仓库创建隔离副本。

不能在普通 managed 目录中自动复制仓库，因为复制策略、符号链接、文件权限、依赖目录、Git object 共享与清理授权都需要独立设计。文件面板应在空 managed root 正常工作，但 Git badge 显示非 Git 状态而非错误。

## 状态层与不变量

| 状态层 | owner | 本次变化 | 不变量 |
| --- | --- | --- | --- |
| 服务配置 | `api.config` | workspace base | base 在创建前已规范化且可写。 |
| Session JSON/内存 | `Session` | root 与 `workspace_mode` | managed root 写入后不变；缺少 mode 的旧 session 保持 legacy 行为。 |
| 文件系统 | workspace module | root 目录创建 | 只在 canonical base 下创建；本方案不自动删除。 |
| 流运行状态 | streaming/gateway | 使用已绑定 root | 同一 stream 从 start 到 settlement 使用同一 root。 |
| Manifest store | session manifest store | workspace-aware artifact index | 相对 path 不跨 root 合并；默认 base 外的 row 不投影为可预览 file。 |
| 最近 workspace | workspace module | 不记录 managed root 为通用默认 | 新会话不会从旧 managed root 派生嵌套路径。 |

对运行中 session，workspace update 与 worktree removal 都必须先检查 active stream / ACTIVE_RUNS。不得在 worker 运行时替换 session root。

## 实施阶段

### 阶段 1：后端创建与持久化（已完成）

1. 增加 `workspace_mode` 内部字段和 managed-root 创建 helper。
2. 在 `/api/session/new` 的普通无 workspace 分支预分配 server ID，创建目录，并立即保存 session。
3. 新增 unit/integration 测试。
4. 更新 Swagger、README 默认 workspace 说明和本方案状态。

完成门槛：无 workspace 的请求得到 `<base>/sessions/<sid>`，显式 workspace 与 worktree 行为不变，创建失败不会返回成功 session。

### 阶段 2：根固定与调用链收敛（已完成）

1. 引入 `resolve_workspace_for_session()`，替换所有聊天、goal、sync、gateway 和 update 入口的散落解析。
2. 对 managed session 拒绝根变更，并让所有执行路径使用 session 绑定根。
3. 确保 `set_last_workspace()` 不将 managed root 作为后续 API 会话分配的 base。

完成门槛：浏览器、直接 API、Gateway 和同步聊天均不能把 managed session 根改为其它路径。

### 阶段 3：Manifest 索引与预览隔离（已完成）

1. 为 manifest 存储增加 workspace-aware 查询和历史空根的运行时兼容解析，保留 legacy 行的保守读取。
2. 修复 integration workspace 文件浏览的 profile/artifact 索引，不按裸相对路径跨根合并；仅对位于 workspace base 内的 row 投影相对预览路径。
3. 覆盖相同 `path`、不同 root 与不同 profile 的 artifact/preview 场景，并验证默认 base 外的 row fail-closed。

完成门槛：两个 session 都产生 `report.md` 时，所有 turn chips、GET manifest 和 profile 过滤均保持所属根；位于 workspace base 内的文件预览读取所属文件，base 外的 row 不可预览且不会误读默认根同名文件。

### 后续独立变更：前端接入

在后端能力稳定后，再单独评审浏览器的新对话流程是否省略继承 workspace，以及如何让用户明确选择 external/worktree/managed。该变更不与本方案实现合并，以避免改变既有用户工作流。

## 测试矩阵

所有 pytest 使用 `./scripts/test.sh`。新测试必须先在现有代码上失败，再实现修复。

| 场景 | 可观察断言 |
| --- | --- |
| 无 workspace | 返回的 root 为 canonical `<base>/sessions/<sid>`，目录存在，session 以 `workspace_mode: managed` 落盘。 |
| 历史 managed root | 已持久化的 `<base>/<sid>` 继续可用，不移动、不按新目录规则重解释。 |
| 显式 workspace | 不创建 managed 目录，root 等于经验证目录。 |
| worktree | 从显式或默认 Git 源创建 worktree，不创建空 managed 根。 |
| 创建/持久化失败 | 不返回成功 session；已创建目录保留，不执行自动删除。 |
| 空会话重启 | managed session 与 root 可重新发现；未能持久化的空目录允许保留。 |
| 两个 base 内会话同名 artifact | `report.md` 分别归属各自 session/turn，预览读取不同物理文件。 |
| base 内 external artifact | `<base>/project-a/report.md` 投影为 `project-a/report.md`，通过现有 workspace 文件接口预览。 |
| base 外 external/worktree artifact | 记录仍保留，但不返回 `preview=file`，且默认根同名文件不能被打开。 |
| managed session chat body 带不同 workspace | 409，session root 与历史 manifest 不变。 |
| managed session update workspace | 409，且不改 `last_workspace`。 |
| Gateway/sync/goal | 每条路径使用持久化 root，不能覆盖它。 |
| 并发创建 | 两个请求目录不同；无竞态替换。 |
| path/symlink 对抗 | `../`、同名 symlink、base 替换均不能在 base 外创建目录。 |
| 删除 session | 仅删除会话记录，不删除对应 workspace。 |
| legacy session | 不增加 mode 时仍可切换其 external workspace；空 manifest root 在运行时逻辑映射为默认 workspace 后，历史 artifact 仍从默认根预览，wire path 不含 `sessions/`。 |
| 现有浏览器回归 | `newSession()` 继续传继承 workspace；该请求仍创建 external session。 |

建议的相邻回归范围：session 创建/删除、worktree、workspace 安全、上传、chat start、Gateway chat、session manifest、manifest artifact persistence、profile workspace handlers、浏览器会话生命周期。

## 风险与回滚

| 风险 | 控制措施 |
| --- | --- |
| API 调用方预期新会话继续操作已有项目 | 保留 external/worktree 入口，并在接口文档中说明省略 workspace 会创建专属目录。 |
| 空会话产生目录垃圾 | 明确接受；本方案不自动回收目录。 |
| 历史 artifact 换根失效 | managed 根不可变；旧 session 不迁移、不推断。 |
| worktree 与空根冲突 | worktree 优先，两个模式不叠加。 |
| 跨会话同名相对 artifact 被索引混淆 | workspace-aware 索引和空根运行时兼容解析完成后才宣称完整隔离。 |
| 默认 base 外 artifact 被误读为共享文件 | 仅投影 base 内 root；base 外 row fail-closed，不生成 file preview。 |

回滚需恢复未传 `workspace` 的旧回退逻辑；既有 managed session 继续使用已持久化的根，绝不自动合并、移动或删除其文件。

## 验收标准

本方案完成后，以下断言同时成立：

1. `POST /api/session/new` 没有显式 workspace 时得到一个唯一、存在并通过 `workspace_mode: managed` 关联到 session 的目录。
2. 该 session 的所有执行、上传、浏览和 artifact settlement 使用同一 canonical root。
3. 任何 API 或迟到 worker 都不能将 managed session 的 root 替换为其它路径。
4. 不同 session 的同名相对 artifact 不会在 Manifest、预览或 profile 过滤中串联；默认 base 外的 artifact 不会被错误预览为共享 workspace 文件。
5. 现有浏览器请求、显式 workspace、worktree、旧 session、CLI 导入和后台会话的既有语义有明确且经过测试的保留边界。
6. 创建、错误、取消、重启和删除各生命周期出口都不会自动删除 workspace。
