# 一次性定时任务重新启用后消失修复方案

- **状态：** Implemented locally — 已按最小接缝在 Agent 工作树实施
- **代码仓库：** Hermes Agent
- **代码改动范围：** `cron/jobs.py::update_job()`
- **测试改动范围：** `tests/cron/test_jobs.py`
- **WebUI：** 不修改，只做现有调用链的兼容性冒烟验证
- **不包含：** 数据迁移、前端交互、API 改造、调度器重构、Chronos provider 改造、历史任务自动重建

## 1. 结论

此次修复的最小权威接缝是 Hermes Agent 的 `cron/jobs.py::update_job()`。

此前方案同时计划修改 `resume_job()`、`update_job()`、`_get_due_jobs_locked()`，并新增共享
helper，范围偏大。代码复核后确认：`pause_job()`、`resume_job()`、`trigger_job()` 以及工具/API
提交的任务更新最终都通过 `update_job()` 持锁写入 `jobs.json`。因此只需在这一处识别并完成：

```text
已完成的一次性任务
+ 明确从 disabled 切换为 enabled
+ 已有可执行的 next_run_at
-> 重置本轮派发额度并进入 scheduled
```

这既覆盖现场的 `update(schedule) -> resume`，也覆盖其它通过正式 Agent API 重新启用任务的
入口，不需要在每个调用方分别打补丁。

本次不修改：

- `resume_job()`；
- `trigger_job()`；
- `claim_dispatch()`；
- `mark_job_run()`；
- `_get_due_jobs_locked()`；
- `cron/scheduler.py` 和 Chronos provider；
- Hermes WebUI 前端或后端。

## 2. 故障链路

一次性任务创建时默认持有一份派发额度：

```json
{"repeat": {"times": 1, "completed": 0}}
```

第一次执行前，`claim_dispatch()` 为保证 at-most-once，先把额度消耗为 `1/1`。执行完成后，
`mark_job_run()` 保留任务并写成：

```text
enabled=false
state=completed
next_run_at=null
repeat=1/1
```

用户随后修改到新的未来时间并恢复任务。当前代码会得到：

```text
enabled=true
state=scheduled
next_run_at=<future>
repeat=1/1
```

新的时间到达后，due scan 看到额度已经耗尽，为避免重复执行而删除 stale entry。任务消失是
上游写入了非法组合后的结果，不是前端删除。

## 3. 为什么 `update_job()` 是最小接缝

### 3.1 所有正式状态写入都汇入这里

当前调用关系为：

```text
resume_job()  ─┐
pause_job()   ─┼─> update_job() -> _jobs_lock() -> save_jobs()
trigger_job() ─┘

cronjob tool update ────────────> update_job()
Gateway/WebUI adapter update ───> update_job()
```

`update_job()` 已经负责：

- 合并用户更新；
- 规范化 schedule；
- 重新计算 `next_run_at`；
- 拒绝过期的一次性调度；
- 在 `_jobs_lock()` 内完成读、改、写。

把 rearm 转换放在它保存前，可以使用同一份旧记录和合并后的新记录进行判断，并在同一把锁
内完成额度重置。无需新锁、无需新的持久化 API，也不会产生 check-then-use 窗口。

### 3.2 为什么不只改 `resume_job()`

只改 `resume_job()` 能修复现场路径，但会漏掉：

- `trigger_job()` 对已完成一次性任务的重新触发；
- cronjob tool 更新 schedule 时同时传入 `enabled=true` 的路径；
- Gateway API 或其它正式调用方直接通过 `update_job()` 重新启用的路径。

这会变成入口级补丁，而不是状态写入层的类修复。

### 3.3 为什么不只改 due scan

把 due scan 的“删除”改成“保留并禁用”只能避免任务定义丢失，不能让重新安排的任务在新时间
执行。更危险的是，due scan 同时承担崩溃后 at-most-once 保护；在那里根据终态猜测是否应重置
额度，可能导致已产生副作用的任务重复执行。

正确位置是用户明确重新启用时，而不是任务已经到期以后。

## 4. 具体代码改动

### 4.1 修改位置

文件：Hermes Agent `cron/jobs.py`

函数：`update_job()`

位置：schedule 规范化和 `next_run_at` 计算完成之后、`jobs[i] = updated` 与
`save_jobs(jobs)` 之前。

### 4.2 只处理一个精确状态转换

保存前检测以下条件：

1. 旧记录是 `schedule.kind == "once"`；
2. 合并后的记录仍是 `schedule.kind == "once"`；
3. 旧记录是 `state == "completed"`；
4. 旧记录是 disabled；
5. 旧记录的默认单次额度恰好耗尽，即 `times == 1 && completed == 1`；
6. 本次 `updates` 明确包含 `enabled=True`；
7. 合并后的记录已有非空 `next_run_at`；
8. 旧记录不存在任何 `dispatch_claim`、`run_claim` 或 `fire_claim`；本次不尝试判断或清理陈旧 claim。

满足时只修改本轮生命周期字段：

```python
updated["repeat"] = {**updated["repeat"], "completed": 0}
updated["state"] = "scheduled"
updated["completed_at"] = None
```

保留以下历史字段：

- `last_run_at`；
- `last_status`；
- `last_error`；
- `last_delivery_error`；
- 已有输出文件和 session 历史。

### 4.3 建议实现形态

不新增公共函数、类、generation 字段或 schema。直接在 `update_job()` 内增加一个局部条件块：

```python
previous_repeat = job.get("repeat")
updated_repeat = updated.get("repeat")
re_enabled_completed_oneshot = (
    isinstance(job.get("schedule"), dict)
    and job["schedule"].get("kind") == "once"
    and isinstance(updated.get("schedule"), dict)
    and updated["schedule"].get("kind") == "once"
    and job.get("state") == "completed"
    and job.get("enabled") is False
    and isinstance(previous_repeat, dict)
    and previous_repeat.get("times") == 1
    and previous_repeat.get("completed") == 1
    and isinstance(updated_repeat, dict)
    and updated_repeat.get("times") == 1
    and updates.get("enabled") is True
    and bool(updated.get("next_run_at"))
)

if re_enabled_completed_oneshot:
    if any(job.get(field) is not None for field in (
        "dispatch_claim", "run_claim", "fire_claim"
    )):
        raise ValueError("Cannot re-enable a completed one-shot with a persisted claim")
    updated["repeat"] = {**updated_repeat, "completed": 0}
    updated["state"] = "scheduled"
    updated["completed_at"] = None
```

这是结构伪代码，实现时遵循当前文件的行宽与错误文案风格。

条件必须基于锁内加载的 `job` 与即将保存的 `updated`，不能基于 `resume_job()` 锁外读取的快照。

### 4.4 保存后的状态

现场链路修复后应为：

```text
update(schedule=<future>)
-> disabled/completed/1-of-1，next_run_at=<future>

resume
-> enabled/scheduled/0-of-1，next_run_at=<future>

到期 claim_dispatch
-> enabled/running/1-of-1

mark_job_run
-> disabled/completed/1-of-1，任务定义仍保留
```

如果 schedule 更新请求本身明确携带 `enabled=true`，rearm 会在同一次 `update_job()` 调用中完成；
后续 resume 再次调用不会重复重置，因为旧记录已不再是 disabled/completed。

## 5. 不应加入本次修复的改动

### 5.1 不新增 repeat helper

`claim_dispatch()`、`mark_job_run()` 和 due scan 对 repeat 的判断处于不同生命周期阶段，行为并不
完全相同。为了本次单一转换抽取通用 helper 会扩大改动面，并可能把损坏数据策略耦合到正常
派发路径。当前修复只需要一个局部谓词。

### 5.2 不重写 `resume_job()`

`update_job()` 已持有跨进程锁并重新读取最新记录。此次无需把名称解析、schedule 计算和保存全
部搬进新的 resume 状态机。`resume_job()` 的锁外 schedule 快照竞态是独立问题；没有证据表明
它参与本次故障，不应顺手重构。

### 5.3 不修改 `claim_dispatch()` 和 `mark_job_run()`

- `claim_dispatch()` 在副作用前消耗额度，是防止崩溃重复执行的既有安全机制；
- `mark_job_run()` 当前已经把达到上限的任务保留为 disabled/completed，而不是删除。

两者在正常生命周期中的行为正确。

### 5.4 不修改 due scan 的 stale 策略

当前 due scan 的删除分支确实具有数据丢失风险，但它原本用于清理旧版或异常写入形成的
“已耗尽但仍到期”记录，并保护 at-most-once。改变该策略需要单独确认旧任务、崩溃恢复和
Chronos 回调契约。

本次由 `update_job()` 保证所有正式写入入口不再生成该非法状态，已足以修复已复现问题。
“stale entry 改为保留并标记失败”可作为后续独立加固，不与当前最小修复捆绑。

### 5.5 不修改 Agent 文档契约

本次没有改变自动派发、最终完成或 Chronos 自动 re-arm 语义，只补齐用户明确重新启用时的
状态转换。`docs/chronos-managed-cron-contract.md` 中关于最终任务是否删除的既有描述与当前
实现存在偏差，但这是已存在的文档债务，应单独修正，避免扩大本 PR diff。

## 8. 风险与边界

### 8.1 不重复副作用

只在 `state=completed`、旧记录 disabled、额度恰为默认 `1/1`、调用方明确启用且没有 claim 时
重置额度。失败、abandoned、running 或 claim 不明确的任务不会自动重试。

### 8.2 不影响周期任务

条件同时要求旧 schedule 为 once 且 `times == 1`。interval/cron 以及用户配置的其它有限次数
不会进入该分支。

### 8.3 不做数据迁移

没有 schema 变化。已被旧代码从 `jobs.json` 删除的任务无法从输出历史安全重建，仍需用户
重新创建。

### 8.4 Chronos

任务更新/恢复后的 provider 通知机制保持不变。修复只改变 `jobs.json` 中 rearm 后的期望状态；
Chronos reconcile 仍读取现有 `enabled` 与 `next_run_at`。不新增 provider API。

1. 业务代码只改 `cron/jobs.py::update_job()` 的保存前状态转换。

5. 新时间到达时只执行一次。
