# 聊天流日志埋点说明

本文说明 Hermes WebUI 聊天流的 `stream_diag` 日志：阶段编号、耗时字段、并发关系与排障方法。

## 1. 启用方式

流式诊断日志由统一日志级别控制：

```bash
# 启用 stream_diag（INFO 及以上）
HERMES_WEBUI_LOG_LEVEL=INFO

# 额外输出 request_id、工作区哈希、Agent 来源等 debug 字段
HERMES_WEBUI_LOG_LEVEL=DEBUG
```

`WARNING` 及以上会关闭 stream_diag 输出。

日志仅输出到服务端控制台，不会写入聊天 SSE，也不会改变会话、run journal 或模型请求。

## 2. 一条日志如何阅读

示例：

```text
[stream_diag][agent][P3 S3.2.3][SLOW 3046.3ms] 工具注册表初始化完成。
| event=agent_init.tools_registry phase=P3 step=S3.2.3
  elapsed=5582.6ms duration=3046.3ms stream=da9e40a0
```

| 部分 | 含义 |
| --- | --- |
| `webui` / `agent` | 事件来源。`webui` 是 WebUI 服务端，`agent` 是 Hermes Agent 回调。 |
| `P3` | 父阶段编号。表示该事件属于 Agent 准备阶段。 |
| `S3.2.3` | 子阶段编号。表示 Agent 构造内的工具注册表初始化。 |
| `OK` / `SLOW` / `ERROR` | 状态。阶段自身耗时达到 1000ms 时标为 `SLOW`。 |
| `duration` | 当前步骤自身耗时。排查慢点时优先看此字段。 |
| `elapsed` | 从本次后台 Worker 启动到当前事件的累计耗时。用于还原关键路径。 |
| `stream` | 本次聊天流关联 ID。分析时应以此字段聚合同一轮对话。 |

## 3. 编号规则

- `P<n>` 是职责阶段，不代表所有日志的全局时间顺序。
- `S<n>.<m>` 是可独立计时的叶子步骤。
- `BEGIN` 仅表示该父阶段开始。
- `SUMMARY` 是父阶段或生命周期汇总，**包含**其下步骤，不能与子步骤相加。
- `S3.2.1` 这类三级编号表示嵌套步骤：`P3` → `S3.2` → `S3.2.1`。

## 4. 阶段目录

### P0：聊天启动

| 编号 | 事件 | 说明 |
| --- | --- | --- |
| `P0 S0.1` | `webui.chat_start.accepted` | 接收聊天启动请求并完成基础校验。 |
| `P0 S0.2` | `webui.chat_start.stream_created` | 创建流对象和初始状态。 |
| `P0 S0.3` | `webui.chat_start.worker_dispatched` | 后台 Worker 已派发。 |

### P1：浏览器 SSE 观察链路

| 编号 | 事件 | 说明 |
| --- | --- | --- |
| `P1 S1.1` | `webui.stream.open` | 浏览器已连接 SSE。 |
| `P1 S1.2` | `webui.stream.resolve` | 判定流来源是实时流、回放流或不存在。 |
| `P1 S1.3` | `webui.stream.first_event` | 浏览器收到第一个业务事件。 |

`P1` 运行在处理浏览器 SSE 的请求线程中，和后台 Worker 并发。因此日志中 `P1` 可以出现在 `P2`、`P3` 中间；这不是倒序，也不代表阶段被打断。

### P2：Worker 的 Agent 前置准备

| 编号 | 事件 | 说明 |
| --- | --- | --- |
| `P2 BEGIN` | `webui.worker.start` | 后台 Worker 开始。 |
| `P2 S2.1` | `webui.worker.pre_agent_journal` | 初始化 run journal 与实时流状态。 |
| `P2 S2.2` | `webui.worker.profile_context` | 获取会话、Profile、模型和 Provider 上下文。 |
| `P2 S2.3` | `webui.worker.profile_runtime` | 建立 Profile 运行环境并预热技能模块。 |
| `P2 S2.4` | `webui.worker.process_env` | 在进程环境锁内应用 Profile 环境变量。 |
| `P2 S2.5` | `webui.worker.mcp_discovery` | 发现并注册 MCP 服务。 |
| `P2 S2.6` | `webui.worker.callbacks_registered` | 注册审批和澄清回调。 |
| `P2 SUMMARY` | `webui.worker.pre_agent_setup` | P2 全程总计。 |

`P2 S2.4` 额外字段：

| 字段 | 含义 |
| --- | --- |
| `wait_ms` | 等待 `_ENV_LOCK` 的时长。 |
| `hold_ms` | 获取锁后、持有锁执行环境切换的时长。 |

排障优先级：若 `P2 S2.5` 慢，优先检查 MCP 配置、服务发现和连接；若 `wait_ms` 高，说明并发聊天之间存在环境锁竞争。

### P3：Agent 缓存和构造

| 编号 | 事件 | 说明 |
| --- | --- | --- |
| `P3 S3.0.1` | `webui.worker.agent_import` | 加载实际 Agent 类，并检查回调能力。 |
| `P3 S3.0.2` | `webui.worker.agent_kwargs_ready` | 准备 Agent 构造参数。 |
| `P3 S3.1` | `webui.worker.agent_cache_lookup_*` | 查找会话级 Agent 缓存。 |
| `P3 S3.2` | `webui.worker.agent_construct_*` | 构造新的 Agent。 |
| `P3 S3.2.1` | `agent_init.basic` | Agent 基础初始化、模型与 API 模式识别。 |
| `P3 S3.2.2` | `agent_init.provider_client` | 创建模型 Provider 客户端。 |
| `P3 S3.2.3` | `agent_init.tools_registry` | 初始化工具注册表。 |
| `P3 S3.2.4` | `agent_init.memory_provider` | 初始化记忆模块。 |
| `P3 S3.2.5` | `agent_init.config_model_metadata` | 解析模型元数据和压缩配置。 |
| `P3 S3.2.6` | `agent_init.context_engine` | 初始化上下文引擎。 |
| `P3 SUMMARY` | `webui.worker.agent_ready` | Agent 准备总计。 |

`P3 S3.2` 与 `P3 SUMMARY` 都是父级耗时，包含 `P3 S3.2.1` 至 `P3 S3.2.6`；不要将这些数字相加。

### P4：上下文和模型执行

| 编号 | 事件 | 说明 |
| --- | --- | --- |
| `P4 S4.1` | `webui.worker.context_prepared` | 读取历史、去重、处理附件并生成 API 输入。 |
| `P4 S4.2` | `agent.model_first_delta` | 模型请求发出到收到首个有效增量的 TTFT。 |
| `P4 S4.3` | `webui.stream.first_visible_token` | 首个模型增量到浏览器收到第一个可见文本（`token` 或 `reasoning`）的延迟。 |
| `P4 SUMMARY` | `webui.worker.run_conversation` | Agent 模型执行总计，包含首 token、后续输出和可能的工具循环。 |

关键字段：

| 字段 | 含义 |
| --- | --- |
| `duration`（`P4 S4.2`） | 真实模型 TTFT。 |
| `first_token` | 从 Worker 启动到首个有效模型增量的累计时间，包含 P2、P3、P4.1。 |
| `first_visible_token` | 从 Worker 启动到浏览器收到第一个可见文本（回答 `token` 或思考 `reasoning`）的累计时间。 |
| `wait`（`P4 S4.3`） | 从浏览器 SSE 打开到浏览器收到首个可见文本的时间。 |
| `event_type`（`P4 S4.3`） | 触发首可见的 SSE 事件类型：`token` 或 `reasoning`。 |

没有工具调用时不会出现预留的 `P4 S4.4` 工具轮次记录。

### P5：收尾和 Worker 汇总

| 编号 | 事件 | 说明 |
| --- | --- | --- |
| `P5 S5.1` | `webui.worker.finalize` | 合并结果、同步用量、保存会话。 |
| `P5 SUMMARY` | `webui.worker.cleanup_summary` | 从 Worker 启动到 Worker 完成的总耗时。 |

`P5 SUMMARY` 的 `total` 是 Worker 全程，不是 cleanup 自身耗时。

### P6：SSE 生命周期汇总

| 编号 | 事件 | 说明 |
| --- | --- | --- |
| `P6 SUMMARY` | `webui.stream.summary` | 从浏览器 SSE 连接打开到关闭的完整生命周期。 |

`P6 SUMMARY.duration` 包含 Worker 执行和浏览器连接尾部等待，不应视为单独的“结束投递”耗时。

## 5. 常用排障方法

### 用户等待首个文本过久

按顺序比较：

1. `P2 SUMMARY.duration`：前置环境、MCP、回调准备。
2. `P3 SUMMARY.duration`：缓存命中、Agent 构造和工具注册。
3. `P4 S4.1.duration`：上下文准备。
4. `P4 S4.2.duration`：模型 TTFT。
5. `P4 S4.3.duration`：模型首增量到浏览器可见文本（含思考）的处理延迟。思考模型若先吐 `reasoning`，S4.3 应在思考首字出现时触发，而不是等到最终回答 `token`。

### 模型看似慢，但实际是本地准备慢

若 `first_token` 大，而 `P4 S4.2.duration` 小，慢点在 P2、P3 或 P4 S4.1，而不是模型 Provider。

### Worker 已结束，但浏览器仍在等待

比较：

```text
P6 SUMMARY.duration - P5 SUMMARY.total
```

差值较大时，说明问题在 SSE 尾部事件、标题生成、浏览器消费或断开时机，而不是模型执行。

### MCP 或工具初始化慢

- `P2 S2.5.duration` 高：检查 MCP discovery。
- `P3 S3.2.3.duration` 高：检查工具注册表、技能导入和工具模块初始化。

## 6. 示例：如何得出结论

```text
P2 S2.5 duration=815ms
P3 S3.2.2 duration=1596ms
P3 S3.2.3 duration=3046ms
P4 S4.2 duration=7621ms
```

该轮的主要耗时依次是：模型首 token、工具注册表初始化、Provider 客户端初始化。MCP discovery 有一定耗时，但不是主要瓶颈。

## 7. 注意事项

- 用同一个 `stream` 聚合日志，不要按控制台行号跨流比较。
- `duration` 是单步耗时；`elapsed`、`total` 和 `SUMMARY` 是累计或汇总指标，不能直接相加。
- `P1` 与 `P2` 至 `P5` 并发，控制台输出顺序不等于业务依赖顺序。
- Provider、模型、Profile、工作区、请求 ID 等字段用于关联；日志对密钥、Token、Cookie、密码等敏感字段会自动脱敏。
