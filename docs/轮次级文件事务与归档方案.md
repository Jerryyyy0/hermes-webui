# 轮次级文件事务与归档方案

## 目标、范围与最终行为

目标是在 `/api/chat/stream` 会话中，为每个 `turn_id/stream_id` 生成权威文件 ChangeSet，不解析 assistant 文本、命令文本或工具结果。

权威口径如下：

- 记录 workspace 与 Profile 知识资产范围内，经过 include/exclude 规则筛选后的最终变化。
- 包含 `created`、`modified`、`metadata_changed`、`deleted`、`type_changed`。
- 创建后又删除的临时文件不记录；重命名按 `deleted + created` 表示。
- 新增和修改后的内容、修改和删除前的内容都归档到 SHA-256 CAS。
- workspace 的 `.git/**` 不进入文件 ChangeSet 或 CAS，但 shadow 中发生的 Git commit、分支、HEAD、index、stash 等状态变化不能随事务目录清理而丢失，必须通过独立的 Git 持久化协议安全写回真实仓库。
- 取消、模型错误和进程异常也尽力生成 ChangeSet；首版 capture 完整后默认自动应用非冲突路径，同时预留异常轮次 `pending_review` 策略。
- ChangeSet 固定按路径应用：冲突或单路径失败只阻塞对应路径，其他安全路径继续；部分成功必须显示为 `partially_applied`，不能伪装成完整成功。
- 新功能只在独立进程形式的 supervised runner 下提供严格保证，不静默降级到 WebUI 进程内推测。
- 部署只支持 WebUI/Runner 原生本地运行，或位于同一 Docker 部署。Runner 由 `server.py` 监督，其生命周期不跨越 WebUI 进程重启。
- Hermes Agent 的 `terminal.backend=local|docker` 是工具执行后端，与 WebUI 本地/Docker 部署方式是两个独立维度。strict 隔离边界是整轮 Agent Worker，不是单独 Terminal。

兼容矩阵：

| WebUI/Runner 部署 | Terminal backend | 产品状态 | 启用顺序与 strict 支持条件 |
| --- | --- | --- | --- |
| 原生 macOS | `local` | 支持 | 第一阶段与 Windows 同时开放；使用通过真实能力探测的系统 `sandbox-exec`，不依赖或启动 Docker |
| 原生 Windows | `local` | 支持 | 第一阶段与 macOS 同时开放；原生 Windows 基础运行先从实验状态提升为正式支持，再通过 AppContainer/Job/HANDLE/网络旁路验收 |
| 原生 Linux/WSL2 | `local` | 支持 | 不作为第一阶段发布门禁；Linux adapter 通过真实验收后独立开放 |
| 任一原生本地 | `docker` | 不支持 | preflight 返回 `unsupported_deployment_backend`，不启动 Agent，不静默改用 local |
| Docker 部署（Linux container） | `local` | 支持 | 后续独立开放；launcher 启动独立 UID/namespace Worker，无额外容器和 Docker socket |
| Docker 部署（Linux container） | `docker` | 支持 | 后续独立开放；Worker 仍是沙箱进程，仅 Terminal 按轮创建 `--network none` sibling |

约束与非目标：

- 第一阶段必须同时开放原生 macOS + `local` 与原生 Windows + `local`；任一平台未通过完整门禁时，两者都不对外宣称第一阶段可用。
- 原生 Linux/WSL2 + `local` 属于最终支持范围，但不作为第一阶段发布门禁；WSL2 按 Linux adapter 处理，不归入 Windows 原生 adapter。
- Docker 部署只支持 Linux container，并在第一阶段之后分别对 `local|docker` 通过门禁后开放。Windows/macOS 宿主使用 Docker Desktop Linux container 时仍按 Docker 部署处理。
- Docker + `local` 不需要 Docker daemon。Docker + `docker` 的可信 Runner 才访问 daemon 并转换 shadow 挂载；Agent Worker 进程和 Terminal 容器均不得持有 Docker socket。
- strict Worker 与 Terminal 不具有原始网络；模型调用只经 Provider gateway，普通工具流量只经 egress broker。WebUI/Runner/Gateway/Docker/metadata 地址永久拒绝。
- Gateway、SSH、Modal、Daytona 和 Windows container 后续通过相同 ChangeSet 协议接入；原生本地 + Docker Terminal 是唯一明确不支持的组合，不列入后续接入范围。
- 完整性口径限定为冻结 policy 纳入的 workspace 与 Profile 知识资产，不覆盖整个主机文件系统。
- CAS 内容在任一有效 ChangeSet 引用期间持续保留。删除、清空或截断会话后，相关归档立即不可查询/下载；失去全部引用的 blob 满 24 小时安全窗口后，才按步骤 7 的 tombstone 与 GC 协议从磁盘物理删除。
- 首版 CAS 使用应用层明文 `plain-v1` 格式，不提供加密开关。strict 保证访问控制和完整性，不承诺抵御磁盘、备份介质或宿主管理员读取；敏感部署必须由 FileVault、BitLocker、LUKS、加密云盘或等价加密卷保护整个 state 与备份。
- 默认排除规则属于产品口径；“无遗漏”指规则纳入范围内无遗漏。

## 步骤 0：关闭设计门禁

本方案的总体方向成立：以隔离的 shadow workspace 承载本轮执行，以 baseline/work 的最终状态生成 ChangeSet，以 SHA-256 CAS 保存前后版本，再通过逐路径 compare-and-swap 合并到真实目录。

以下问题不否定该方向，但当前文本尚未形成闭合契约；其中标记为“阻断”的事项在作出明确决策并同步修改后续章节前，不应进入真实聊天链路实现。

### 0.2 G1：已选定但仍需验收的严格隔离边界

G1 的产品范围和架构方向已确认，不在实施中改回 Worker 容器。G1 仍是阻断门禁：文件、进程、句柄和网络旁路全部通过真实 OS 敌对测试前，对应平台不得启用 strict。

#### 0.2.1 威胁模型与 strict 承诺

进程的当前目录和环境变量只是默认解析上下文，不是权限边界。local Worker 即使从 shadow 启动，仍可能使用真实绝对路径、外部链接、继承的文件描述符，或调用 WebUI/MCP 等代写通道。

strict 假定 Agent、工具、shell、依赖及其子进程可能执行敌对输入。它必须阻止这些执行单元读取或写入真实 workspace/Profile/state、其它轮次和 Runner 控制面，并保证纳入 policy 的本地文件变化只发生在 shadow。

该承诺不防御宿主内核漏洞，也不承诺对 Worker 合法可见的输入和短期 run capability 保密。Provider/OAuth 长期凭据不得交给 Worker 或进入 CAS；模型请求必须由 Runner 侧 Provider gateway 代理。

首版不为单轮设置 CPU、内存或 PID 数量硬上限。Worker 及其子进程复用 WebUI/Runner 所在宿主机、服务管理器或外层容器已有的部署级资源边界；原生部署未由外部机制限制时，边界就是宿主机可用资源。因此 strict 不防御单轮通过 CPU、内存或进程数量耗尽影响 Runner 和其它轮次的拒绝服务攻击。现有 Worker 并发数、磁盘、执行超时和网络配额仍然有效，但不能把它们描述成 CPU、内存或 PID 隔离。

父级 OOM、进程表耗尽或类似资源压力可能中断 Worker、Runner，甚至整个 WebUI。恢复流程只有在能够重新证明 quiesce 和 capture 完整时才允许 apply；无法证明时必须标记 `interrupted`/`capture_status=failed` 并保持真实目录不变，不能把父级资源耗尽报告成隔离健康或完整捕获。

原生本地固定使用平台 adapter：macOS 使用经能力探测验证的系统 `sandbox-exec` profile，Linux/WSL2 使用 mount namespace/bubblewrap，Windows 使用 AppContainer + restricted token + Job Object。这些 adapter 提供文件、网络、身份或进程生命周期边界，不代表存在每轮 CPU、内存或 PID 配额。

平台开放按 adapter 独立验收，但第一阶段是一个联合发布门禁：macOS 与 Windows 必须同时通过才开放。Linux/WSL2 和两种 Docker 组合后续各自通过门禁后独立开放，不反向阻塞已经验收的平台。唯一不进入最终支持范围的是原生本地 + Docker Terminal。

本地部署遇到 `terminal.backend=docker` 时必须在 prepare 前拒绝，不创建 run 目录，不回退 local 或 best-effort。

#### 0.2.2 Docker 内的 Worker 进程和最小特权 launcher

Docker 部署不启动 Worker 容器。WebUI/Runner 继续以普通运行用户执行；外层容器启动时额外保留一个最小 `isolation launcher`，只负责为每轮分配独立 UID/GID、建立 namespace、启动 Worker 和在终止后回收身份。

launcher 只保留完成 UID/GID、所有权和进程创建所需的最小 capability，不持有 Docker socket、真实 workspace/Profile FD、Bearer 或 Provider 凭据。它只接受带 `stream_id` 执行身份的固定操作，不接受 shell、任意命令、绝对路径或 Worker 提供的 mount source。

launcher 只能通过预打开的 `turn_files/runs` 根目录句柄访问本轮目录。每个并发 run 从有界 UID/GID 池取得独立身份；回收前必须确认进程清零、shadow 所有权安全交还 Runner 并完成 journal，失败身份不得复用。

启动协议固定为 `launch_worker(stream_id, run_dir_generation, manifest_sha256)`、`terminate_worker(stream_id, run_dir_generation)` 和 `reclaim(stream_id, run_dir_generation)`。其中只有 `stream_id` 是执行身份，后两项只证明 launcher 操作的是登记过的同一目录实例。launcher 只执行镜像内只读的固定 Worker 入口，不执行请求方传入的命令或可执行路径。

Runner 先在本轮 `backend/` 写入只含相对路径、资源 ID 和冻结参数的 launch manifest。launcher 通过根目录 fd 打开并校验 owner、mode、普通文件类型、`run_dir_generation`、`manifest_sha256` 和 schema；任何绝对路径、`..`、软链接、未知字段或非白名单 runtime ID 都拒绝。

Worker 使用 bubblewrap/user + mount + PID namespace、最小 `/proc`、`no_new_privs`、capability 清零、seccomp 和 Landlock。真实根、Runner state、其它轮次、控制 socket 与 Docker socket 在其视图中不可见。

Docker Worker 继承外层执行容器的部署级 cgroup 约束，不创建每轮 CPU、内存或 PID 子配额。PID namespace 只隔离进程视图和辅助进程收敛，不能当作 PID 数量上限。

禁止使用 `--privileged`、`CAP_SYS_ADMIN`、宿主 PID namespace 或全局放宽 seccomp。独立 UID、user namespace、bubblewrap、seccomp/Landlock 或安全所有权交还无法证明时，Docker strict 必须拒绝启动。

外层容器的 PID 1 必须监控 launcher。launcher 非预期退出时，PID 1 立即停止接收新 run 并退出外层容器，由部署运行时杀死其中全部 Worker；不得让无特权 Runner 猜测并接管残留 root-owned 进程。

容器重启后，新 launcher 先扫描 root-owned 身份账本和各轮 `backend/` 状态，确认对应 UID 已无进程、Terminal 已停止且 shadow 可安全交还后才释放 UID。状态不确定时隔离该 run 和 UID，并将 strict 标记为 degraded。

#### 0.2.3 POSIX FD 与 Windows HANDLE 白名单

mount namespace 和路径 ACL 不能撤销启动前已经打开的文件、目录、数据库或 Unix socket。所有平台必须先构造显式继承白名单，再创建 Worker；只允许标准输入输出、当轮控制通道和 egress 通道。

POSIX launcher 使用 `close_range(CLOSE_RANGE_UNSHARE)`、`closefrom` 或经 capability probe 证明等价的 `close_fds + pass_fds` 路径，并要求所有非白名单 FD 为 `CLOEXEC`。无法枚举和关闭时拒绝 strict。

Windows 使用 `STARTUPINFOEX` handle list，禁止继承 Runner 已打开的真实文件、数据库、日志、进程和 token handle。敌对测试必须从 Runner 预先打开真实文件/目录后再启动 Worker，证明路径隐藏不能被 FD/HANDLE 绕过。

#### 0.2.4 网络、控制面与 MCP 旁路

文件系统沙箱不能阻止 Worker 通过 HTTP 调用 WebUI 文件接口。Worker、local Terminal 和 Docker Terminal 默认没有原始网络路由，也不能访问 WebUI、Runner HTTP、Gateway 管理面、Docker daemon、宿主/Compose 内网和云 metadata 地址。

每轮只暴露一个不含 Bearer 和长期凭据的 egress IPC。沙箱内 proxy shim 把两类协议送到相互隔离的 Runner 侧子进程；两者都不继承 workspace、Profile、CAS、Runner controls 或 Docker socket。

Provider gateway 只得到冻结 Provider 配置和该轮必需秘密；普通 egress broker 只得到目标策略与资源上限，永远不接收 Provider 凭据。任一子进程崩溃只终止本轮网络能力，并触发该轮收敛。

该通道分成两类协议，不能用一个透明 HTTPS CONNECT 同时承担：

1. Provider gateway 是应用层代理。Worker 的 Provider base URL 改写到本地 shim，并只携带按轮不可复用的 capability；gateway 校验 provider、模型、方法和路径后，在建立上游 TLS 时注入 Runner 持有的 Provider/OAuth 凭据。
2. 普通 egress proxy 只为允许的 HTTP(S) 工具流量建立受限隧道，不注入 Provider 凭据，也不能接受客户端自选 Unix socket、named pipe 或控制面目标。

Provider 适配器若不能在 Runner 侧完成协议转换、流式回传、错误映射和 OAuth 刷新，就不得进入 strict 支持矩阵。不能把长期 API key 临时复制给 Worker 作为兼容回退。

首版按“实际出站协议 + 认证方式 + endpoint 类型”维护版本化 adapter registry，不按模型名称或 Provider 品牌前缀猜测。每轮 prepare 冻结解析后的 adapter identity；模型切换导致 identity 改变时必须重新 preflight。

| Provider 能力 | 首版 strict 规则 |
| --- | --- |
| `chat_completions` | 支持，包括通过该协议调用的 OpenRouter、DeepSeek 等 OpenAI-compatible Provider |
| `codex_responses` | 支持，包括 OpenAI API 和 OpenAI Codex 的 Responses API 路径 |
| `anthropic_messages` | 支持，包括 Anthropic 及使用该协议的兼容 Provider |
| API key / OAuth | 均可支持，但 Runner 必须能解析、注入和按需刷新凭据；Worker 只得到当轮 capability |
| 自定义或本地/LAN endpoint | 当前选中 Provider 的 Profile `base_url` 即精确批准；只有协议属于上述三类且 gateway adapter 通过验收时支持 |
| `bedrock_converse` | 首版不支持；需要独立的 AWS SDK、SigV4 和身份隔离 adapter |
| `codex_app_server` / `copilot-acp` | 首版不支持；二者会委托额外外部进程，不能当作普通 HTTP Provider 放行 |
| Gemini native、Vertex/ADC 等特殊路径 | 首版不支持，直到各自完成独立 gateway adapter、凭据边界和流式验收 |

`api_mode` 名称相同不等于实际协议相同。例如 Hermes Agent 的 Gemini native 路径可能仍保留 `chat_completions` 名称，但内部改走 Gemini 原生客户端；registry 必须依据最终 transport/adapter 判定，不能只检查字符串。
不在 registry 或任一能力未知时，strict 在 Worker 启动前返回稳定的 `unsupported_provider_adapter`，不得把凭据传给 Worker、改走普通 egress 或退回非隔离执行。

broker 默认采用 `restricted_public`：除 Provider gateway 对应的冻结 endpoint 外，允许普通工具经受控代理访问公共 HTTP(S) endpoint，以支持联网搜索、依赖下载和公开代码仓库访问。
管理员可将部署收紧为 `provider_only`；项目内 policy 只能缩小权限，不能把 `provider_only` 扩大为公网访问。当前选中 Provider 的 Profile `base_url` 是本轮唯一 endpoint 批准来源，不再要求第二份管理员白名单。
WebUI、Runner、Gateway、Docker API、metadata 和除已冻结 Provider/远程 MCP 外的私网目标始终禁止。Profile Provider 配置只授权 Provider gateway，不授权普通 egress broker 或 Worker 直连。

Runner 必须调用 WebUI/Hermes Agent 既有的权威 Provider resolver，从当前模型解析最终 provider、`api_mode`、认证来源和 `base_url`，不能由 gateway 另写一套猜测规则。prepare 将规范化的 `{scheme, host, effective_port, base_path, adapter_id, config_hash}` 冻结到非秘密 run 元数据；拒绝 URL userinfo、fragment、通配符、CIDR、端口范围和含歧义的编码路径。Profile 配置在运行中变化只影响后续轮次。

Provider gateway 只允许冻结 base path 加对应 adapter 声明的方法与固定 API 后缀，例如 Chat Completions、Responses 或 Anthropic Messages 路径，不能把 `base_url` 当作任意同源代理。每次解析和连接都重验 DNS/IP；精确配置的 loopback/LAN Provider 可以访问其冻结端口，但若实际目标命中 WebUI、Runner、Gateway、Docker API 或 metadata 的保留地址与端口则拒绝。redirect 只有在 origin 不变且最终路径仍属于 adapter 白名单时才允许，跨 origin redirect 一律拒绝。

普通 egress broker 对 DNS 解析、每次连接和重定向重新校验目标并固定实际 IP，拒绝 DNS rebinding、环回、link-local、multicast 和未授权私网。上述 Profile Provider 例外只存在于独立 Provider gateway，代理协议不得提供任意本地文件、Unix socket、named pipe 或 Runner 控制调用。

Docker Terminal 使用 `--network none`，通过只读挂载的 proxy shim 和当轮 egress socket 使用普通 egress proxy。shim 或目标校验不可用时拒绝需要网络的工具，不得临时接入默认 Compose bridge。

strict 下仅允许两类 MCP：在同一 Worker 沙箱内按轮启动并继承全部限制的 MCP，或通过 egress broker 访问的已冻结远程 endpoint。常驻本地 MCP、任意 IPC MCP 和不能证明写入边界的工具必须禁用，不能“排除保证后继续运行”。

远程 MCP 的批准来源固定为当前会话绑定 Profile 中已启用的 `mcp_servers` 配置，不增加管理员 MCP 白名单，也不逐轮弹出确认。换言之，能够通过 WebUI 或本地配置修改该 Profile MCP 配置的主体，就拥有远程 MCP 批准权；这是首版明确接受的运维边界。workspace 项目文件和 Agent Worker 不能增加、修改或启用真实 Profile MCP。

Runner 在 prepare 时读取并冻结启用的 HTTP Streamable/SSE MCP：规范化 server name、transport、精确 URL、认证类型、非秘密 header 名称和配置 hash。Profile 在运行中修改只影响后续轮次；本轮 endpoint、transport 或认证来源变化时终止对应 MCP capability，不能热切换到新目标。Profile 中配置的精确 URL 同时构成该远程或私网 MCP 目标的批准，但 WebUI、Runner、Gateway、Docker API、云 metadata 和其它永久 deny 仍优先，不能通过 Profile 配置覆盖。

全局 egress 模式仍可收窄该批准：默认 `restricted_public` 允许冻结的 Profile 远程 MCP；管理员切换为 `provider_only` 时禁用全部远程 MCP，只保留 Provider gateway 和可在 Worker 沙箱内按轮启动的 stdio MCP。Profile 配置不能把 `provider_only` 重新扩大。

静态 header 值和 OAuth 2.1 token/refresh 状态只由 Runner 从真实 Profile 配置或既有 OAuth 存储读取，并在每轮独立 MCP transport 上注入；不得进入 Worker、runtime Profile、run.json、policy snapshot、CAS、错误详情或日志。跨 origin redirect 必须拒绝，DNS 和实际连接 IP 每次重验；本轮 MCP transport/session 不跨 `stream_id` 复用。

远程 MCP 对外部系统的写入不属于本方案 ChangeSet，也无法由本地文件事务回滚。strict 只保证它不能绕过 broker 读写真实本地根或控制面；UI 和文档必须明确远程工具仍可能产生外部副作用。

#### 0.2.5 macOS 原生 strict 的附加门禁

第一阶段接受使用 macOS 系统现有的 `/usr/bin/sandbox-exec`，但不把“命令存在”或 macOS 版本号当作安全证明。该工具属于 Apple 已废弃且未承诺长期兼容的系统能力；本方案不假定它会永久存在。

每次 WebUI/Runner 启动以及系统能力指纹变化后，macOS adapter 必须运行真实隔离探针，至少证明 shadow/runtime 可写，真实 workspace/Profile/WebUI state 不可读写，子进程继承限制，原始网络和 WebUI/Runner/Gateway 控制面不可达，且非白名单 FD 不可继承。探针只能使用隔离的临时根，不能触碰真实用户状态。

任一探针失败、系统移除 `sandbox-exec` 或 profile 行为无法验证时，返回稳定的 `strict_platform_unavailable`，不启动 Agent，也不退回仅依赖 cwd/env 的执行。首版不安装特权 helper、不要求 Docker；未来若改用签名 helper、App Sandbox 或其它机制，必须作为新的 adapter 契约单独验收。


#### 0.2.6 Windows 原生 strict 的附加门禁

当前仓库仍把原生 Windows bootstrap 标记为实验性，自动安装和部分 Terminal 能力也存在已知限制。第一阶段不能只增加 AppContainer 隔离后继续沿用“community/unsupported”口径；必须先把原生 Windows 的安装、启动、升级、Hermes Agent local Terminal、Provider、允许的 MCP、取消和退出清理提升为正式支持，并用端到端测试证明。该基础支持门禁与 Windows strict 同批完成。

Windows adapter 为每轮创建独立 AppContainer identity/SID，只向 shadow、runtime 和必需的只读程序文件授权。不得把用户 SID 的普通写权当作隔离证明。

AppContainer profile name/SID、DACL 变更、Job name、Worker PID 和分配状态写入 `backend/` 与 transaction journal。Job HANDLE 只在 Runner 进程内持有，不序列化为可恢复引用。

正常、错误和取消路径必须关闭 Job HANDLE、移除当轮 ACE 并删除临时 profile。Runner 崩溃时由 `KILL_ON_JOB_CLOSE` 收敛 Worker；新 Runner 依据落盘的 PID/profile/ACE 状态完成核验与清理，不完时保持 degraded。

Worker 使用受限 token 启动，不继承 Runner 句柄，并在启动前加入设置 `KILL_ON_JOB_CLOSE` 的 Job Object。Job 在首版只承担子进程归属、生命周期收敛和防逃逸，不设置每轮 CPU、内存或 active-process 硬上限。子进程逃离 Job、嵌套 Job 不兼容或句柄白名单无法证明时拒绝 strict。

Windows 路径检查覆盖盘符、UNC、junction、reparse point、保留设备名、大小写别名和长路径。apply 使用 Windows HANDLE 实现，不把 POSIX `dir_fd/O_NOFOLLOW` 降级分支当作同等证明。

Windows 不向 Worker 开放宽泛 `internetClient`、`privateNetworkClientServer` 或 loopback exemption。Provider 和允许的远程工具通过 0.2.4 的 egress 通道访问；平台无法只授权该 IPC 时保持 unsupported。

控制管道、egress 通道、临时文件和可执行文件分别按当轮 SID 授权。原型或敌对测试未通过时，Windows strict 必须保持 unsupported。


### 0.3 G2：已选定 WebUI 重启中断 Agent

现有 Runner RFC 的关键验收条件是：只重启 WebUI 时，Runner 继续执行，新的 WebUI 能重新发现、回放并控制原 run。本方案首版明确不实现该语义。

Runner 由 `server.py` 创建并监督，Bearer key、端口和 Runner 进程都从属于一次 WebUI 生命周期。WebUI 正常停止时必须 drain；异常退出后由新进程恢复文件事务。


所有重启前仍活跃的 run 统一设置 `outcome=interrupted`。能够完成终止屏障并证明 capture 完整时按首版默认策略自动应用非冲突路径；不能证明完整时设置 `capture_status=failed`，禁止 apply。

浏览器可以从 journal 回放重启前已经持久化的事件和中断结果，但不能重新连接继续执行原 Agent。取消、审批、澄清和排队控制在旧 Runner 终止后全部失效。

仅 WebUI 进程重启时，外部 supervisor 重启 WebUI/Runner 进程组并执行事务恢复。Docker 外层容器重启时，部署运行时收敛容器内全部进程；新容器执行相同恢复流程。

实施前必须修改 `docs/rfcs/hermes-run-adapter-contract.md`：将“执行跨 WebUI 重启存活”从本方案首版验收项移出，并保留为未来独立 Runner 服务的后续能力。


### 0.4 G3：已选定首版异常轮次自动应用

捕获和应用是两个不同决策。

异常轮次仍应先收敛子进程、稳定扫描 work、写入 CAS 并生成可审计 ChangeSet。首版选择减少人工操作：只要 capture 完整，就自动应用通过 compare-and-swap 的路径。

默认规则固定为：

| outcome | capture | 默认 apply |
| --- | --- | --- |
| `completed` | 完整捕获 | 自动应用非冲突路径 |
| `cancelled` | 能证明完整 | 自动应用非冲突路径 |
| `errored` | 能证明完整 | 自动应用非冲突路径 |
| `interrupted` | 恢复后能证明完整 | 自动应用非冲突路径 |
| capture 不完整 | 标记失败并保留诊断目录 | 禁止 apply |

`abnormal_apply_policy` 预留 `auto|review` 两个版本化值，首版默认 `auto` 并写入 `run.json/change_sets`。以后切换为 `review` 时，异常 outcome 进入 `pending_review`；不能改变已经开始的 run。

自动应用不是强制覆盖：任一路径与 baseline 不一致仍标记冲突。手工接口继续用于冲突解决和预留 review 策略，并始终执行 expected hash compare-and-swap。

### 0.5 G4：已选定四组正交状态

状态固定拆分如下，避免用一个枚举同时表达四种含义：

```text
run_phase:
  queued -> preparing -> prepared -> running -> quiescing
         -> quiesced -> capturing -> captured -> terminal

outcome:
  unknown | completed | cancelled | errored | interrupted

capture_status:
  not_started | in_progress | complete | failed

apply_status:
  not_started | pending_review | applying | applied
  | partially_applied | conflicted | failed
```

`run_phase` 只表示整轮编排位置，不再放入 `applying` 或 `pending_review`。自动 apply 期间可以是 `run_phase=captured + apply_status=applying`；待确认时可以是 `run_phase=terminal + apply_status=pending_review`。

字段权威来源固定为：

| 字段 | 权威来源 | 其它层的角色 |
| --- | --- | --- |
| `run_phase/outcome` | Runner execution journal | `turn_files.db` 和浏览器 Run Journal 只保存查询/展示投影 |
| `capture_status/apply_status` | `turn_files.db` | `transaction.jsonl` 保存文件系统 intent 和屏障证据，不直接覆盖状态 |
| 浏览器事件与 cursor | 浏览器 Run Journal | 从权威状态生成事件，不能反向改写执行或文件状态 |
| 已发生的文件系统操作 | 真实路径状态 + `transaction.jsonl` intent | recovery 核验后推进 `turn_files.db`，不能只信任内存标记 |

必须为正常完成、用户取消、Provider 错误、Worker/Runner SIGKILL、WebUI 重启、锁超时、磁盘不足、会话删除和手工 resolve 分别列出转换表，并按上表修复派生状态。


### 0.6 G5：已选定首版 Provider adapter 范围

首版范围以 0.2.4 的版本化 adapter registry 为准。API key 与 OAuth 都可以进入支持矩阵，但 Runner 必须完整拥有凭据解析、注入和刷新；Worker 不得直接取得长期凭据。

普通 HTTP 的 `chat_completions`、`codex_responses` 和 `anthropic_messages` 可以逐 adapter 验收后启用。`bedrock_converse`、`codex_app_server`、`copilot-acp`、Gemini native、Vertex/ADC 及未知 transport 首版 fail closed。


### 0.7 G6：已选定 Profile 白名单权限模型

Profile 默认只捕获 `memories/**`、普通技能资产和 `SOUL.md`。管理员可以增加 `plans/**`、`skins/**` 或自定义知识目录，也可以缩小默认范围；项目配置和 Agent 只能进一步排除，不能扩大管理员冻结的上限。

`.env`、`auth.json`、`config.yaml`、`sessions/**`、`logs/**`、`cron/**`、数据库、WebUI/Runner state 和 Profile 自带的 `workspace/**` 是不可覆盖的固定拒绝。配置在每轮 prepare 时冻结，本轮内的配置修改只能影响下一轮。

配置来源已选定如下：未设置 `HERMES_WEBUI_TURN_FILES_POLICY_FILE` 时使用产品内置 Profile 白名单；设置后必须指向管理员持有的绝对 JSON 文件，该文件以完整 `profile_allow`/`profile_exclude` 替换内置 Profile 列表。Docker 部署将它只读挂载到外层执行容器，原生部署使用 Worker 不可写的管理员本地文件。

workspace 根的 `.hermes-turn-files.json` 继续用 `include`/`exclude` 控制 workspace，并且只允许用 `profile_exclude` 收窄 Profile 上限，不提供 `profile_allow`。显式管理员文件缺失、不可安全读取、JSON/schema/glob 无效，或文件可被 Worker/项目/非信任主体修改时，strict 必须在启动 Worker 前失败。


### 0.8 G7：Git 状态必须持久化，但协议仍是阻断项

已确认的产品行为如下：

- `.git/**` 在 shadow workspace 中对 Agent 和 Git 命令可读写；`git commit`、分支切换、index/staging 和 stash 等操作不能因轮次结束或事务目录清理而消失。
- `.git/**` 不进入文件 ChangeSet、文件 CAS、Session Manifest artifact 或普通文件 action 计数。
- 真实 workspace 的文件内容仍由文件 ChangeSet 逐路径 compare-and-swap；Git 元数据必须使用独立状态、journal 和恢复边界，不能借“不进入 ChangeSet”绕过审计和冲突检测。
- Git 状态事务只持久化可观察的语义结果：commit 产生的 objects、refs/分支变化、当前 HEAD、index/staging 和 stash。普通仓库与 WebUI 管理的 linked worktree 都必须遵守同一语义契约。
- hooks、仓库 config、凭据与 credential helper、lock 文件、socket、日志和缓存不属于可持久化 Git 状态，不得从 shadow 原样回写。这些内部文件在 shadow 中的变化不能作为轮次成功的产物。

状态集合和永久拒绝项已确认，但具体写回协议仍未闭合，因此 G7 保持阻断。实现前至少还必须决定并固化：objects/refs/HEAD/index/stash 的表达方式、外部 Git 并发修改的 expected-state 比较、Git 状态与工作树文件 ChangeSet 的应用顺序、部分失败语义、worktree/submodule/bare repository 边界以及崩溃恢复。

在该契约关闭前，禁止使用 `copytree`、`rsync` 或逐文件 replace 把 shadow `.git/**` 原样覆盖到真实仓库，也不能清理包含唯一 Git 状态的事务目录后报告成功。

## 步骤 1：确定身份、状态与 Runner 契约

### 1.1 进程职责和调用边界

严格模式下，WebUI 不再直接持有 Agent 执行过程。

WebUI 负责 `/api/chat/start`、`/api/chat/stream`、SSE 转发、会话元数据和 Session Inspector；Runner 是 Agent 执行、事务工作区、文件捕获、CAS 归档和合并的唯一入口。


```text
WebUI /api/chat/stream
        |
        | Runner HTTP API + Bearer
        v
Hermes Runner
        |-- 本轮 Agent/Terminal/MCP 子进程
        |-- baseline/work 事务目录
        |-- ChangeSet + SHA-256 CAS
        `-- 非冲突文件合并到真实目录
```

### 1.2 如何理解 `Runner HTTP API + Bearer`

这条箭头表示 WebUI 与 Runner 之间的**内部控制通道**：浏览器仍然只访问 WebUI 的 `/api/chat/*`，WebUI 再作为 HTTP 客户端调用受信 Runner 的 `/v1/*` 接口。

Runner HTTP API 不是另一套面向用户的聊天接口，也不应直接暴露到局域网或公网；它用于把“启动一轮、读取事件、查询状态、取消、提交审批/澄清”等运行控制从 WebUI 进程传给 Runner。


`Bearer` 是这条内部通道的临时访问凭证。WebUI 调用受保护的 Runner 接口时，在 HTTP 请求头携带：

```http
Authorization: Bearer <当前 Runner 控制会话的 key>
```

Runner 收到请求后先校验 key，匹配才处理；缺失或错误则返回 `401/403`。

可以把它理解为 WebUI 进入 Runner 控制面的临时门禁，但它只证明“请求来自持有本次 key 的调用方”，不能替代 session/path 授权、run 标识校验和参数校验。


一次典型调用链如下：

1. 浏览器请求 WebUI 开始对话，WebUI 完成用户认证、会话授权并生成 `session_id`、`turn_id`、`stream_id`。
2. WebUI 携带 Bearer key 调用 Runner 的 `POST /v1/runs`；Runner 幂等创建对应 run 和独立 Worker。
3. WebUI 携带同一 key 按 cursor 读取 `/v1/runs/<stream_id>/events`，再把允许公开的事件转换为浏览器 SSE；浏览器不会看到 Runner 地址或 key。
4. 用户点击取消时，浏览器仍请求 WebUI；WebUI 校验会话归属后，携带 key 调用 Runner cancel。Runner 只终止该 `stream_id` 的 POSIX 进程组/namespace 或 Windows Job；若使用 Docker Terminal，再停止对应的 Terminal sibling 容器。

这个 Bearer key 与三类凭证必须严格区分：它不是用户登录 cookie，不是模型 Provider API Key，也不是 Agent 工具凭据。

`server.py` 每次启动都随机生成新的 key，只保存在 WebUI/Runner 内存或受控子进程环境中。WebUI 重启后旧 Runner 被终止、旧 key 自然失效；新进程不得复用旧 key 或旧控制连接。

key 不得写入日志或命令行、返回浏览器，也不得传给 Agent Worker、Terminal、MCP 或普通工具。

即使 Runner 只监听 `127.0.0.1`，仍要求 Bearer 校验，以防同机其它进程直接调用取消、审批、读取事件或启动 run 等控制接口。


- WebUI 创建并传递 `session_id`、`turn_id`、`stream_id`，Runner 不重新生成这些标识。首版不定义或持久化 `run_id` 字段，Runner、事件、控制接口、事务目录、journal 和数据库统一使用 `stream_id` 作为唯一执行身份。
- Runner 复用现有 `runner-local` HTTP 契约：创建 run、事件游标、状态、取消、审批、澄清和追加消息。
- Runner 的运行文件只写 `STATE_DIR/turn_files/`、`STATE_DIR/runner/` 和 CAS；WebUI 继续独占认证、设置和会话数据库。`turn_files.db` 的所有读写统一经过 store 模块，避免两个进程直接修改同一 JSON 或复制状态。
- 开启 `HERMES_WEBUI_TURN_FILES=strict` 后，所有会改变文件的 Agent 执行必须经过 Runner，不允许回退到 `legacy-direct`。

### 1.3 身份与幂等规则

- `session_id` 标识会话，`turn_id` 标识一次用户提交，`stream_id` 标识一次执行及其事件流，`turn_key` 标识 Manifest 中的轮次投影。`run` 仍可作为“运行”的业务名词，但不得再派生第二个 `run_id` 字段。
- `POST /v1/runs` 以 `stream_id` 为幂等键。相同 payload hash 重试返回原 run；相同标识但 payload 不同返回 `409 idempotency_conflict`。
- Runner 的每个状态、事件、控制请求、事务目录和 ChangeSet 都必须携带并校验同一个 `stream_id`，不能同时保存值相等的 `run_id` 别名，也不能依赖字符串前缀推断归属。
- 内部不得再保存 `isolation_id`、`task_id` 等同值别名。若 Hermes Agent 或 Docker 的既有调用签名必须使用其它参数名，只允许 adapter 在调用边界把 `stream_id` 临时填入该参数；返回后仍以 `stream_id` 关联，别名不进入数据库、manifest、journal 或 API 响应。
- Runner execution journal 是 `run_phase/outcome` 的权威来源；浏览器 Run Journal 是事件/cursor 的权威来源；`transaction.jsonl` 保存文件系统 intent；`turn_files.db` 权威保存 ChangeSet 与 capture/apply 状态。

## 步骤 2：启动并监督 Runner

### 2.1 Runner 启动与监督拓扑

现有 `bootstrap.py --foreground` 会通过 `os.execv` 将自身替换为 `server.py`。本方案固定由 `server.py` 创建并监督 Runner，Runner 不跨 WebUI 生命周期存活。

`server.py` 创建 `RunnerSupervisor`：

```text
ctl.sh / launchd / systemd
            |
            v
        server.py
            |
            `-- runner_service
                    `-- 每轮平台隔离的 Agent Worker
```

该分支的启动流程为：

1. `server.py` 检测到 strict 模式后，使用 `secrets.token_urlsafe(32)` 生成仅本次 WebUI 生命周期有效的 256-bit Bearer key。
2. 使用与 WebUI 相同的 Python 解释器启动 `integration.turn_files.runner_service`。POSIX 将 Runner 置于独立进程组；Windows 使用明确的进程创建标志和 supervisor handle。
3. Bearer key 仅通过子进程环境或继承控制管道传递，不写入命令行、全局环境、配置文件或日志。
4. Runner 绑定系统分配的随机端口，通过 readiness pipe 返回 `port`、`pid`、`instance_id` 和 `protocol_version`。
5. WebUI 在限定时间内携带 Bearer key 探测 `/v1/health`，校验协议版本和 `instance_id` 后，在内存中创建 `HttpRunnerClient`。
6. Runner 未按时就绪时，WebUI 仍可提供设置和诊断页面，但新的 strict 会话返回结构化 `503 runner_unavailable`。

Runner 只监听 loopback，通过一次性 readiness pipe 把随机端口和实例标识返回 WebUI；不创建跨进程重启复用的 discovery 文件，也不发布局域网或宿主端口。

原生本地和 Docker 共置拓扑都要求 Bearer，并限制控制面不直接暴露到局域网或公网。

除最小存活探针外，run、events、status、cancel、approval、clarify 和深度健康接口全部要求 `Authorization: Bearer <key>`。

日志必须过滤 Authorization、请求中的凭据、完整环境和 key；每次 WebUI 重启自然轮换 key。


`RunnerSupervisor` 持续监控 Runner，异常退出后按 `1、2、5、10、30` 秒退避重启；超过上限后进入 degraded。Runner 意外退出时，恢复流程按已持久化的进程组、Job 和可选 Terminal container ID 收敛本轮资源。

Runner 重启后扫描非终态 journal，清理残留进程，再继续 capture 或标记失败。WebUI 必须校验新的 `instance_id`，不能复用旧连接状态。

WebUI 停止时先拒绝新 run，再请求 Runner drain，最后按超时执行 `TERM/KILL`。所有活跃 run 记录为 `interrupted`；capture 完整后按冻结的异常 apply 策略处理，首版默认自动应用。

### 2.2 Docker 部署

Docker 部署中，WebUI/Runner 属于可信控制面，能读取真实 workspace/Profile 并创建 snapshot。这里的“外层执行容器”固定是现有 WebUI Linux 容器，不是每轮新建的容器。

Runner 是该容器内由 WebUI 监督的独立进程。Agent 始终在同一容器内以按轮 Linux 沙箱 Worker 进程执行，不创建 Worker sibling 容器，也不新增独立 Runner service。

```text
Docker / Compose
  |-- WebUI execution container
  |     |-- WebUI + supervised Runner (unprivileged)
  |     |-- minimal isolation launcher (restricted root)
  |     |     `-- per-turn sandboxed Agent process
  |     |-- per-turn egress broker / Provider gateway
  |     `-- Docker daemon API (仅 terminal.backend=docker)
  |           `-- per-turn Terminal sibling
  `-- persistent state/workspace/profile mounts
```

外层执行容器的 root `docker_init.bash` 先启动最小 isolation launcher，再把 Runner 降为普通运行用户。Runner 通过受限 Unix socket 和固定 run manifest 请求 launcher 创建 Worker；launcher 不复用 WebUI Python 对象或接收任意命令。

launcher 通过 bubblewrap 为 Worker 构造新的 user/mount/PID/network namespace。视图只包含当轮 shadow、runtime、受控 temp、必需只读程序、显式只读输入、控制通道和 egress 通道。

真实 workspace/Profile、Runner state、CAS、session DB、Runner FD、控制端口和 Docker socket 必须不可见。Worker 使用与 Runner 不同的 OS identity，不得向控制面发送信号、ptrace，或通过 `/proc`、继承 FD 和网络读取其环境/句柄。

`terminal.backend=local` 时 Terminal 在同一进程与网络沙箱中执行。`terminal.backend=docker` 时 Runner 使用冻结 mount spec 创建 `--network none` 的 Terminal sibling；Terminal 只挂载 shadow/runtime 和受控 egress socket。

WebUI 容器挂载真实根和持久 state；仅 `terminal.backend=docker` 时配置 Docker socket。Runner 与 WebUI 使用相同逻辑根解析结果，不得为 strict 新建一个遮蔽历史 Hermes home 的空 volume。

Docker + `local` 必须在没有 Docker socket 的默认 Compose 配置中工作。Docker + `docker` 通过显式 Compose override/profile 把 socket 只授权给 Runner，deep health 在创建 run 前验证 daemon、mount broker 和 Terminal sentinel。

Bearer 不进入 Compose 明文、公共环境、Worker 进程环境、Terminal 容器环境或日志，只通过 WebUI 内存和受控继承管道传给本次 Runner。

Worker 和 Terminal 不能直连 Runner/WebUI/Gateway。egress 通道与 Runner HTTP 控制面使用不同协议、socket 和授权；broker 只能代理冻结目标，Provider gateway 只能处理受支持模型协议，两者都不能调用 run controls 或代写真实文件。

本方案不改变现有 Gateway 职责。Gateway 不拥有文件事务、Worker 进程或 Docker socket。


### 2.3 健康状态、故障语义和可观测性

- `/health?deep=1` 增加 Runner readiness、PID、`instance_id`、协议版本、重启次数、活跃 run 数、事件 cursor 延迟、事务恢复次数和最后错误，不返回 key。
- Docker deep health 报告 launcher、UID 池、namespace、FD 白名单、`no_new_privs`、capability、seccomp/Landlock、Provider adapter、egress broker 和进程收敛探针。
- 仅 `terminal.backend=docker` 额外报告 daemon/socket 权限、外层 inspect、state mount 转换、Terminal 镜像、`--network none`、UID/GID、proxy shim 和 sentinel。
- Runner 日志写入 `STATE_DIR/logs/runner.log`，按大小和保留数量轮转；不得记录 Authorization、CAS 文件内容或 Agent 凭据。
- 新轮次开始前 Runner 不可用时返回 `503 runner_unavailable`；运行中断连时 WebUI 按事件 cursor 重连，不能直接宣布成功。
- Runner 无法恢复 Agent 时仍要收敛残留进程，并尝试从现有 work 目录生成最终 ChangeSet；捕获不完整则标记 `capture_status=failed`，禁止合并和正常 `done`。
- 取消、模型错误和 Runner 异常采用同一收敛与捕获流程；capture 完整后按冻结策略进入 apply 或 `pending_review`，首版默认自动应用非冲突路径。
- strict 模式绝不静默切换到正则、工具结果解析或旧进程内执行；诊断信息必须明确区分 unavailable、degraded、capture failed 和 apply conflict。

## 步骤 3：确定捕获根和策略

### 3.1 模块和数据结构

新增 `integration/turn_files/policy.py` 和 `integration/turn_files/roots.py`：

- `roots.py` 调用现有 `resolve_trusted_workspace()` 获取 workspace，调用 `get_hermes_home_for_profile()` 获取该会话绑定的 Profile home；所有路径在 Runner 内再次 `resolve()`，不能信任 WebUI 直接传来的绝对路径。
- `policy.py` 定义版本化 `CapturePolicyV1`，负责读取固定规则、可选的管理员 JSON 策略和 workspace 根目录的 `.hermes-turn-files.json`，将 glob 规范化为 POSIX 相对路径规则。
- Runner 在创建事务前生成不可变 policy snapshot，将完整 JSON 和 `policy_hash=sha256(canonical_json)` 同时写入 `run.json` 和 `change_sets`。

policy snapshot 固定为以下结构：

```json
{
  "version": 1,
  "sources": {
    "administrator": {"kind": "builtin", "sha256": null},
    "workspace": {"present": true, "sha256": "<sha256>"}
  },
  "roots": [
    {
      "kind": "workspace",
      "logical_root": "/workspace",
      "include": ["**/*"],
      "exclude": ["coverage/**"]
    },
    {
      "kind": "profile",
      "allow": ["memories/**", "skills/**", "SOUL.md"],
      "exclude": [
        "skills/.hub/**",
        "skills/.archive/**",
        "skills/.curator_backups/**",
        "skills/.usage.json"
      ]
    }
  ],
  "default_exclude": [".git/**", "node_modules/**", ".venv/**", "dist/**", "build/**", "**/__pycache__/**"],
  "hard_deny_version": 1,
  "metadata": ["type", "posix_mode", "windows_attributes", "link_target", "reparse_tag"]
}
```

`sources` 只保存来源类型、是否存在和内容哈希，不保存管理员文件的宿主绝对路径。若配置了管理员文件，`administrator.kind` 为 `file` 且 `sha256` 为已校验内容的哈希。

### 3.2 规则优先级

每个候选路径只执行一次统一判定，优先级从高到低为：

1. 固定安全拒绝：出根路径、解析后进入 `STATE_DIR`/事务目录、Profile 非白名单资产、凭据和认证状态；任何项目配置都不能覆盖。
2. 管理员 Profile 上限与排除：管理员文件存在时完整替换内置 Profile allow/exclude；不存在时使用内置默认值。
3. 项目收窄：workspace 的 `exclude` 控制 workspace，`profile_exclude` 只能从管理员 Profile 上限中排除；同时命中 allow 和 exclude 时，以 exclude 为准。
4. workspace `include`：可以重新纳入依赖、缓存和构建输出等默认降噪目录，但不能影响 Profile、越过固定安全拒绝或把 `.git/**` 纳入文件 ChangeSet；`.git/**` 始终由 G7 的独立 Git 状态协议处理。
5. 产品默认排除：VCS 元数据、依赖、缓存和构建输出；其中 `.git/**` 只是不进入文件 ChangeSet，不能据此丢弃其状态，必须遵守 G7 的独立 Git 持久化契约。
6. workspace 其余路径默认纳入；Profile 其余路径默认拒绝。

固定安全规则至少覆盖 Profile 的 `.env`、`auth.json`、`config.yaml`、数据库、日志、sessions、WebUI state 和 Runner state。

Profile 默认采用最小白名单：只纳入 `memories/**`、普通技能资产和 `SOUL.md`。`skills/.hub/**`、`skills/.archive/**`、`skills/.curator_backups/**`、`skills/.usage.json` 属于审计、备份、归档或使用统计，不进入首版 ChangeSet。

Profile 白名单和排除规则必须支持配置，并在每轮 prepare 时解析、校验和冻结到 policy snapshot。管理员可以增加 `plans/**`、`skins/**` 或自定义知识目录；项目配置和 Agent 只能通过 `profile_exclude` 缩小管理员允许的范围。

任何配置都不能重新纳入 `.env`、`auth.json`、`config.yaml`、`sessions/**`、`logs/**`、`cron/**`、数据库、WebUI/Runner state、Profile 自带的 `workspace/**` 或其它固定安全拒绝项。

workspace 根仍按独立 workspace policy 捕获。Profile 自带的 `workspace/**` 被排除不代表当前会话选择的项目 workspace 被排除；两者必须按 canonical root identity 去重并拒绝危险重叠。

workspace 的凭据规则单独维护并允许安全样例文件例外，例如 `.env.example`；规则列表必须有单元测试，不能散落在多个模块中。


### 3.3 路径、目录和文件类型语义

- 数据库只保存 `{root_kind, relative_path}`；`relative_path` 使用 `/`，禁止空路径、NUL、绝对路径和 `..`。
- POSIX 遍历使用 `lstat()`；Windows 使用不跟随 reparse point 的 HANDLE 查询。link target/tag 作为元数据保存；指向根外也只记链接本身，不读目标内容。
- 首版处理可稳定序列化路径下的普通文件、链接和内部目录。POSIX 的 FIFO/socket/device 与 Windows 的未知 reparse type 标记 `unsupported`，并使对应路径捕获失败。
- 权威元数据按平台记录：POSIX 保存 mode bits 和 symlink target；Windows 保存约定的 file attributes、link target 和 reparse tag。不支持的字段为 `null`，不用伪 POSIX mode 填充。
- mtime、ctime、uid/gid 和 owner SID 不属于首版权威 ChangeSet：它们只用于稳定性检查或诊断，不参与重放。POSIX mode bits 和约定的 Windows file attributes 仍按上一条保真。
- 首版不能完整归档和重放非平凡 ACL、xattr（包括 macOS resource fork）、Windows 非空 alternate data stream（ADS）或 hardlink 关系。这里的非平凡 ACL 指无法由已支持模型等价重建的额外权限：POSIX 中超出 owner/group/other mode 的 ACL 条目，Windows 中非继承 ACE 或不能由目标父目录继承规则重建的 DACL；基础 mode 和可证明等价的纯继承 DACL 不因此失败。任一纳入路径在 prepare 时存在这些扩展语义，整轮返回 `unsupported_file_semantics`，不启动 Worker；项目可显式排除无须捕获的路径后重试。
- capture/apply 为目录建立 `DirectoryPathState`，记录存在性和平台元数据，用于空目录、目录删除、节点类型互换及父子依赖排序。
- 目录变化与文件变化一样持久化为权威 `file_changes`，详细 ChangeSet 必须展示空目录创建、目录删除、目录元数据和节点类型互换。聊天 Session Manifest/Artifact chips 默认不为纯目录变化生成 artifact；创建后删除且最终不存在的临时节点不记录。
- snapshot 启动时探测根文件系统的大小写和 Unicode normalization 语义。不同相对字符串若指向同一节点，必须规范化为唯一键或 fail closed。
- Worker 若在 work 中新建非平凡 ACL、xattr、非空 ADS 或 hardlink 关系，capture 以同一错误码失败，`capture_status=failed`，不生成可应用的完整 ChangeSet，也不修改真实目录。失败详情只返回有上限的 `{root_kind, relative_path, semantic_type}`；`semantic_type` 固定为 `acl|xattr|resource_fork|ads|hardlink`，不读取或返回 xattr/ADS 内容；事务目录按步骤 7 进入异常 quarantine，等待管理员处理。

### 3.4 配置校验和失败处理

未设置 `HERMES_WEBUI_TURN_FILES_POLICY_FILE` 时，Runner 使用版本化内置管理员策略：

```json
{
  "version": 1,
  "profile_allow": ["memories/**", "skills/**", "SOUL.md"],
  "profile_exclude": [
    "skills/.hub/**",
    "skills/.archive/**",
    "skills/.curator_backups/**",
    "skills/.usage.json"
  ]
}
```

设置 `HERMES_WEBUI_TURN_FILES_POLICY_FILE` 时，其值必须是管理员提供的绝对路径。JSON 只允许并要求 `version`、`profile_allow`、`profile_exclude`；它表示完整上限而不是对内置默认值的增量补丁，避免“省略字段究竟继承还是清空”的歧义。Docker 通过只读 bind/secret/config mount 提供该文件；原生部署使用管理员拥有且 Worker、项目和非信任主体不可写的普通文件。

Runner 在 prepare 中通过不跟随 symlink/reparse point 的句柄读取管理员文件，并校验 canonical path 不位于 workspace、任一 Profile home、`STATE_DIR` 或事务目录。POSIX 拒绝 group/other 可写文件；Windows 校验 owner/DACL，不允许 Worker SID、普通用户组或项目执行身份拥有写权限。无法证明来源和权限安全时返回 `invalid_turn_files_admin_policy`。

workspace 的 `.hermes-turn-files.json` 只允许 `version`、`include`、`exclude`、`profile_exclude`。其中 `include`/`exclude` 只作用于 workspace 根，`profile_exclude` 只做集合减法；出现 `profile_allow` 或其它未知字段必须拒绝，不能静默忽略。

任一策略出现未知字段、非字符串数组、绝对 pattern、`..` 或超过数量/长度限制时，strict 模式在 Agent 启动前返回稳定错误；管理员来源使用 `invalid_turn_files_admin_policy`，workspace 来源使用 `invalid_turn_files_policy`，不能忽略错误继续执行。显式配置的管理员文件缺失、不是普通文件或读取失败也属于管理员策略错误，不回退内置默认值。

Runner 先读取并验证管理员策略，再读取 workspace 策略，合并固定拒绝并生成 canonical JSON/hash，最后才允许创建 Worker。策略文件在一轮开始后即使被修改，也不改变本轮 snapshot；workspace 策略本身若被 Agent 修改，只影响后续轮次。

## 步骤 4：创建 baseline、work 和隔离环境

### 4.1 事务目录布局

新增 `integration/turn_files/snapshot.py` 和 `integration/turn_files/run_layout.py`。每轮先在 `STATE_DIR/turn_files/runs/.tmp-<stream_id>` 准备，全部元数据落盘后原子 rename 为：

```text
STATE_DIR/turn_files/runs/<stream_id>/
  run.json
  transaction.jsonl
  state
  roots/
    workspace/baseline/
    workspace/work/
    profile/baseline/
    profile/work/
  runtime_home/
  backend/
  apply/
  errors/
```

全局 CAS 不放在单轮目录内，而是位于 `STATE_DIR/turn_files/blobs/<前两位>/<sha256>`。

异常或身份无法确认的事务目录统一移入 `STATE_DIR/turn_files/quarantine/`。该目录是 Runner 控制的内部隔离区，不是用户可访问的回收站，也不能由普通 GC 直接清空。

只有 Runner 通过受控 `runs` 根创建、在数据库登记并通过目录身份校验的直接子目录，才可视为可清理的事务目录。真实 workspace 或 Profile 中即使存在名为 `tmp`、`baseline`、`work`、`.tmp-<stream_id>` 或 `<stream_id>` 的目录，也永远不能据此认定为事务目录或进入本清理流程。

`run.json` 保存真实根/shadow 路径、轮次标识、policy hash、部署模式、隔离 adapter、Terminal backend、`abnormal_apply_policy`、Runner instance 和状态。

`backend/` 保存 capability proof、sandbox identity、POSIX PID/PGID/namespace identity、Windows Job name/Worker PID/分配状态、`run_dir_generation`/UID 租约和 broker identity，以及可选 Terminal container ID/sentinel。

这些是恢复元数据，不包含不能跨进程复用的 fd/HANDLE。Docker + `local` 不得产生 Terminal container ID、mount spec 或 daemon 恢复状态。

POSIX 权限为目录 `0700`、元数据和 blob `0600`。Windows 使用显式 DACL：Runner 完全控制，当轮 AppContainer SID 只能读写 work/runtime，不继承宽泛写 ACE。


### 4.2 创建顺序

1. 通过已锚定的 `runs` 根句柄排他创建 `.tmp-<stream_id>`，生成只表示本次目录实例的 `run_dir_generation`；它不是第二个执行身份，所有运行接口仍只使用 `stream_id`。
2. 在临时目录中写入并刷盘 `create_intent`、`run.json` 和 manifest；manifest 至少覆盖目录版本、`stream_id`、`run_dir_generation` 和受控布局，并计算 `manifest_sha256`。
3. 在数据库登记同一组 `stream_id/run_dir_generation/manifest_sha256`，再把临时目录原子 rename 为 `runs/<stream_id>`，最后写入并刷盘 `create_committed`。任一步崩溃后都由 recovery 根据 intent、数据库和 manifest 补完或隔离，禁止只看目录名猜测归属。
4. 校验根路径、policy、磁盘空间和根重叠关系，对 workspace/Profile 加共享 snapshot lock，防止另一个 apply 正在替换文件。
5. 若 `STATE_DIR`、事务目录、CAS、真实 Profile 与 workspace 存在危险父子重叠，直接拒绝 strict，不能依赖普通 exclude 避免递归复制。
6. 使用独立的 `runtime-copy deny` 排除事务状态、socket、device、凭据和不能安全复制的节点。该规则与 capture policy 分离，用户配置不能覆盖。
7. 为 workspace 构造运行副本，使 `.git`、依赖和默认排除目录仍可被构建命令读取；shadow `.git/**` 必须可写，使 commit、分支、index 和 stash 等 Git 操作正常执行，但其最终持久化走 G7 的独立协议，不进入文件 ChangeSet。为 Profile 构造 Agent 所需的隔离运行副本。
8. policy 只控制 `baseline.index`、diff、CAS 和 merge，不控制普通依赖是否出现在运行视图。
9. 每个源文件执行 `lstat -> clone/copy -> lstat`，确认类型、size、mtime/ctime 等稳定性标记未变化；变化时有限重试，仍不稳定则 snapshot 失败。
10. macOS 优先 `clonefile(2)`，Linux 优先 `FICLONE`；Windows 首版使用 `CopyFile2/CopyFileEx` 全量复制。单文件不支持 CoW 时回退安全全量复制，所有平台禁止硬链接。
11. baseline 完成后遍历纳入路径并写 `baseline.index`，记录 hash 与平台元数据；再从 baseline 克隆 work。
12. baseline 不能作为 cwd。POSIX 移除写 mode，Windows 用 DACL 拒绝 Worker 写入。diff 使用 index 原始元数据；capture 前重新验证 baseline hash。
13. 数据库进入 `prepared` 后才启动 Agent。准备错误必须按步骤 7 将临时目录补完登记后隔离，或在能够证明它仍是本次未提交创建的前提下清理；不能启动不完整 run，也不能按名称批量删除未知临时目录。

本方案首版承诺“每条 PathState 来自一个经过稳定性校验的源版本”，不承诺整个目录是文件系统级同一时点快照。

需要全目录原子快照时，必须依赖 APFS/Btrfs/ZFS 等明确能力并另行扩展契约。


### 4.3 Agent 运行环境重定向

- workspace cwd、File Tool 根目录和 Terminal cwd 指向 `roots/workspace/work`。
- 创建 `runtime_home`，设置 `HOME=<run>/runtime_home`、`HERMES_HOME=<run>/runtime_home/.hermes`；Profile work 映射到该 `.hermes`，使 shell 对 `~/.hermes` 的写入也落入事务视图。
- Profile 复制到 shadow 前拆分配置与秘密：普通配置进入 runtime Profile；Provider 凭据只进入 Provider gateway，远程 MCP 静态 header/OAuth 只进入 `mcp_runtime`。Worker 只得到本地 shim endpoint 和按轮 capability，不得到真实上游认证；runtime Profile 中的远程 MCP URL/headers 必须替换为当轮代理配置或移除。
- 普通工具确需秘密时，只能由独立 secret policy 注入最小、短期、按轮值。secret 节点不在 shadow/capture 根内，不进入进程环境转储、diff、CAS、日志或最终合并；不支持短期化的秘密默认拒绝 strict 工具调用。
- `HERMES_WEBUI_STATE_DIR`、Runner journal/CAS 路径和控制面 Bearer key 只保留在 Runner 自身环境，不传给 Agent Worker、Terminal、沙箱内 MCP 客户端/进程和普通工具。远程 MCP 服务端只收到其自身配置要求且由 Runner 注入的认证，不接触其它秘密。
- attachment 使用显式只读输入路径，不自动归入 ChangeSet；Agent 将其复制或转换到 work 后，目标文件按正常规则记录。
- Runner 为每轮启动独立 Worker 进程，不在线程中修改全局 `os.environ`。每轮只用 `stream_id` 关联 execution owner：POSIX 进程组/namespace 或 Windows Job Object；`terminal.backend=docker` 再关联 Terminal container ID。
- 所有 Agent 子进程与 Terminal 继承同一事务环境并归属该 owner。禁止复用 `SESSION_AGENT_CACHE` 中绑定真实 workspace/Profile 或前一轮 owner 的 Agent。
- POSIX 通过专用 launcher 和显式 FD 白名单创建 Worker；Windows 使用 `STARTUPINFOEX` handle list。仅标准流、当轮控制与 egress 通道可继承，Runner 已打开的真实文件、目录、数据库、日志和 socket 不得泄漏。
- Worker 没有原始网络路由。Provider SDK 的 base URL 指向 shim 的 Provider gateway；`HTTP_PROXY/HTTPS_PROXY` 仅供普通工具流量，并清空会绕过代理的 `NO_PROXY`。不使用 shim 的直连由 OS 网络边界拒绝。
- 根内相对 link 自然解析到 work。指向真实根内部的绝对 symlink/junction 在 work 中改写为 shadow target，`baseline.index` 保存逻辑 target/tag，diff 时归一化回原值。无法等价改写时 fail closed。

### 4.4 Terminal backend 适配

新增 `integration/turn_files/isolation/` 和 `terminal_backend.py`。前者用操作系统沙箱隔离整轮 Worker 进程，后者只选择沙箱内 local Terminal 或 Runner 代理的 Docker Terminal。

部署模式、OS adapter、Terminal backend 和 capability proof 必须在 prepare 前解析，作为 `run.json` 冻结字段保存，不能在一轮中途切换。


#### 4.4.1 Local Terminal backend

- 原生本地由 `NativeIsolationAdapter` 按平台启动 Worker。capability probe 需在真实轮次前证明默认禁止写入且子进程继承隔离；仅设置 cwd/env 时拒绝 strict。
- macOS adapter 默认拒绝文件与原始网络访问，只开放 shadow/runtime/系统程序及库/只读输入/temp/控制与 egress 通道。必须测试 shell、Python、子进程、绝对路径、FD 和 HTTP 旁路；系统移除该能力时 strict 不可用。
- Linux/WSL2 adapter 使用 mount/PID/network namespace 和 bubblewrap 构造受限视图。user namespace、网络直连阻断、FD 白名单、seccomp 或 Landlock 任一能力不足时拒绝 strict。
- Windows adapter 按 0.2.6 使用 AppContainer/restricted token 启动 Worker，将 Worker 加入当轮 Job，并以 DACL 只授权 shadow/runtime/控制与 egress 通道。
- Docker 部署由 isolation launcher 按固定 manifest 调用 Linux adapter，使用独立 UID/GID、user/mount/PID/network namespace、最小 `/proc`、FD 白名单、`no_new_privs`、capability 清零、seccomp 和 Landlock。
- Docker 进程沙箱只暴露 shadow/runtime、temp、必需只读 runtime、显式只读输入和两条受控通道。真实根、Runner state/CAS、其它轮次、Runner `/proc`、控制端口、socket 或原始网络任一可达时拒绝 strict。
- Docker 外层执行容器必须以默认非 privileged 配置完成上述隔离。不得通过 `--privileged`、`CAP_SYS_ADMIN`、宿主 PID namespace 或放宽全局 seccomp 开启 strict。
- POSIX 轮次结束使用进程组/namespace `TERM -> wait -> KILL`；Windows 先请求协作退出，超时后终止 Job。全部子进程、broker/gateway 和 Terminal 收敛，且 launcher 完成所有权交还后才能 capture。
- macOS sandbox、Linux/Docker PID namespace 和 Windows Job 只证明访问边界与进程生命周期，不证明每轮 CPU、内存或 PID 配额。Worker 复用父级可用资源；父级资源耗尽时按中断和捕获失败闭合处理。

#### 4.4.2 Docker Terminal backend

`terminal.backend=docker` 只在 Docker 部署中支持。原生本地遇到该配置时返回 `unsupported_deployment_backend`。

沙箱 Worker 进程不持有 Docker socket；它通过当轮受权控制管道请求 Runner 启动 Terminal sibling。Runner 只接受结构化命令和冻结的 `stream_id`，不接受 Worker 提供的宿主机 mount source。

Docker Terminal backend 不能使用 Hermes Agent 默认的独立 `/workspace` tmpfs、sandbox workspace 或跨进程持久容器。strict 模式固定为：

```text
canonical execution identity = stream_id
Terminal adapter task_id     <- stream_id  # 仅调用边界映射，不持久化 task_id
shadow workspace work  -> terminal container /workspace:rw
turn runtime_home      -> terminal container /root:rw
shadow profile work    -> terminal container /root/.hermes:rw
container_persistent   = false
persist_across_processes = false
```

- 一轮只创建一个 Terminal 容器并在本轮工具调用之间复用；下一轮必须创建新容器，禁止使用 Hermes 默认的跨会话/跨进程容器复用。
- 进程沙箱内的 File Tool、Agent 内置写入与 Terminal sibling 必须读写同一 `roots/workspace/work`；不能通过事后解析命令或 `docker cp` 猜测变化。
- Terminal 容器使用本轮 Worker 的数值 UID/GID，不使用 Runner 身份。终止后由 launcher 按安全 fd walk 将 shadow 所有权交还 Runner；`0600` 文件、异常退出和 UID 池耗尽任一验证失败时拒绝本轮。
- Terminal 使用固定 digest 镜像、只读 rootfs、受控 tmpfs、`--network none`、`--cap-drop ALL`、`no-new-privileges`、固定 seccomp 和空 device allowlist，不加入默认 Compose 网络。首版不设置每轮 `--memory`、`--cpus` 或 `--pids-limit`。
- Terminal sibling 必须通过 `--cgroup-parent` 或运行时等价机制加入与外层执行容器相同的部署级 cgroup 预算，复用父级 CPU、内存和 PID 边界，不能落入宿主机未受约束的其它资源树。Runner 若不能从 daemon/inspect 结果证明两者受同一部署级父约束，`Docker + docker` strict 在启动 Agent 前返回 unavailable；不能用进程内资源票据代替该证明。
- Terminal 只读挂载 proxy shim，并只读写当轮 egress socket。shim 在容器 loopback 提供普通 HTTP(S) proxy；broker 在连接与重定向时执行目标校验，Terminal 不能借此访问 Runner controls、Provider 凭据或真实文件。
- 用户 `docker_volumes`、`docker_extra_args` 不得覆盖 `/workspace`、`/root`、`/root/.hermes` 或暴露真实 workspace/Profile；冲突配置返回 `400 strict_docker_volume_conflict`。额外只读输入挂载可保留。
- Terminal sibling 容器增加 `hermes-turn-files=1`、`hermes-stream-id=<stream_id>` 和 profile 标签；container ID 和最终 mount spec 写入 `transaction.jsonl`，供取消、崩溃恢复和孤儿清理。
- 轮次终止时先停止调度工具，再执行 `docker stop -> bounded wait -> docker kill -> docker rm`；确认容器不再运行且 bind mount 已可稳定读取后，才写 `quiesced` 并进入 diff。

启动 Agent 前执行进程沙箱敌对探针：必需路径可用，真实根、Runner state、其它轮次、继承 FD、控制端口和原始网络均不可达。`terminal.backend=docker` 再验证容器安全选项、proxy shim 和双向 sentinel。


### 4.5 Docker Terminal mount broker

本节只适用于 Docker 部署 + Docker Terminal。Docker + local 不启动 sibling、不访问 daemon，也不进入 mount broker。

Runner 通过 `/var/run/docker.sock` 启动 Terminal sibling 时，容器内 shadow 路径不能直接作为 daemon 的宿主机 bind source。

新增 `integration/turn_files/docker_mount_broker.py`：

1. 读取当前外层执行容器 ID，必要时允许使用受控配置显式指定；通过 Docker API/CLI inspect 获取该容器 `Mounts[]`。
2. 找到覆盖 `HERMES_WEBUI_STATE_DIR` 中 shadow 路径的最长 `Destination`，计算其相对 subpath。
3. 外层挂载为 bind 时，转换为 `host Source + relative subpath`，再挂载到 Terminal 目标路径。
4. 外层挂载为 named volume 时，优先使用 volume name + `volume-subpath`；Docker/Podman 版本不支持安全 subpath 时拒绝 strict Docker Terminal backend，不退化为挂载整个 Hermes home。
5. 对转换结果做 canonical path、允许根和 mount type 校验；不得根据请求中的任意路径拼接 Docker mount 参数。
6. 启动最小探针容器执行双向 sentinel，确认 sibling 和 Runner 互相观察到创建、更新、rename 与删除；不要求 Docker Desktop 返回相同 inode。结果按 mount identity 缓存，每轮仍验证目标 subpath。
7. inspect、路径转换、Docker socket 权限、UID/GID 或 sentinel 任一失败时，在 Agent 启动前返回 `503 strict_docker_terminal_mount_unavailable`，绝不改用 Docker 自有 workspace。

Docker daemon API 只是 Docker Terminal 的前提，不是 Docker 部署或 local backend 的通用前提。

Docker socket 具备近似宿主机 root 的控制能力，必须在部署文档和 deep health 中明确展示。socket 只授权给可信 Runner，并从 Worker 进程 namespace 和 Terminal sibling 容器中隐藏。


### 4.6 一致性边界

snapshot 不是全主机快照。strict Worker 必须无法通过路径、继承 FD、网络 API、MCP 或 Terminal mount 写入真实根。外部编辑器在 baseline 后修改真实 workspace 不进入 work，并在步骤 8 被识别为冲突。

步骤 4 完成标准：第一阶段原生 macOS + local 与原生 Windows + local 同时通过隔离门禁；后续原生 Linux/WSL2 + local、Docker + local、Docker + docker 分别通过自身门禁后独立开放；原生本地 + Docker Terminal 在产生任何运行状态前被拒绝。

Agent、File Tool、Terminal、execute_code 和允许的 MCP 对 policy 根只能写 shadow；真实根在执行阶段不可写。受控 temp 不归入 ChangeSet，snapshot 对不稳定源文件 fail closed。

## 步骤 5：运行 Agent、处理并发并完成进程收敛

每轮进入 `running` 前必须已经完成步骤 4。Runner 只调度绑定本轮 `stream_id` 的 Worker、工具进程和可选 Terminal sibling 容器，不复用上一轮执行环境。

### 5.1 多会话并发模型与锁协议

多会话可以同时执行，但并发单位是“隔离的 run”，不是让多个 Agent 直接写同一真实目录。

每轮都拥有独立的 baseline、work、runtime home 和 execution owner。owner 在 POSIX（包括 Docker 外层执行容器）为进程组/namespace，Windows 为 Job Object；Docker Terminal 再包含 container ID。

`session_id`、`turn_id` 与唯一执行身份 `stream_id` 必须绑定到同一 run，任何控制操作都先校验该绑定关系；execution owner 和可选 Terminal container 作为资源引用挂在该 `stream_id` 下，不再各自复制执行身份字段。


并发行为固定为：

| 场景 | 执行阶段 | 应用阶段 | 预期结果 |
|---|---|---|---|
| 不同 workspace，且不共享 Profile 根 | 可并行 | 不同真实根可并行 | 各自独立完成；共享父级 CPU/内存容量，并竞争应用级磁盘和 Docker 票据 |
| 同一 workspace，修改不同路径 | 可基于各自 baseline 并行 | 同一 workspace 的 apply 串行 | 通常均成功；后应用者仍逐路径校验 baseline |
| 同一 workspace，修改同一路径 | 可基于各自 baseline 并行 | 同一 workspace 的 apply 串行 | 先应用者成功；后应用者发现真实 PathState 已偏离 baseline，标记 `conflict`，不得覆盖 |
| 不同 workspace，但共享同一 Profile | workspace 部分可并行 | Profile 根的 apply 串行 | workspace 变化互不阻塞；同一 Profile 文件按 baseline 规则成功或冲突 |
| workspace 或 Profile 正被外部程序修改 | 不阻塞 Agent 在 shadow 中运行 | apply 时重新校验 | 外部变化保留，本轮对应路径标记冲突 |

锁协议如下：

1. 每个真实 workspace/Profile 根以 `volume identity + canonical path` 的 hash 映射跨进程读写锁。Windows 键使用规范化盘符/UNC 与大小写语义，不按原始请求字符串建锁。
2. snapshot 对本轮涉及的真实根获取共享锁，只持有到 baseline 副本及 `baseline.index` 完成；apply 对会被写入的真实根获取独占锁，只持有到该批路径写入、状态落盘和目录 `fsync` 完成。
3. 一个阶段涉及 workspace 与 Profile 两个根时，先按 canonical root path 的字节序排序，再依次取锁，释放时逆序执行；所有恢复、手工 resolve 和 GC 中会触碰真实根的流程都遵循同一顺序，避免死锁。
4. Agent 在 shadow work 中运行以及 capture/CAS 写入期间不持有真实根锁。长时间工具调用不能阻塞其它会话 snapshot 或 apply；capture 只读本轮已收敛的 shadow。
5. 同一真实根的 apply 即使修改路径集合互不相交也保持串行，首版不做路径级锁。冲突判断仍逐路径执行，锁只消除 apply 之间的检查后写入竞态，不能替代 baseline 比较。
6. 锁等待必须有超时、取消检查和可观测指标；超时返回可重试状态并保留已捕获 ChangeSet，不能绕过锁直接写入。进程异常退出后锁由操作系统释放，恢复流程依据 apply intent 判断继续、回滚单路径或标记冲突。
7. POSIX 锁 adapter 使用可验证的文件锁；Windows 使用 `LockFileEx` 或带完整 root identity 的 named synchronization object。底层不支持所需共享/独占语义时拒绝 strict。

取消和故障必须按 run 隔离：只终止该 `stream_id` 的 POSIX 进程组/namespace 或 Windows Job Object；`terminal.backend=docker` 再停止带对应 label 的 Terminal sibling 容器。

不得按 profile、workspace、AppContainer profile 名前缀或容器镜像批量停止。

一个 run 的捕获、应用或恢复失败不能取消同 workspace 的其它 run，也不能释放其它 run 持有的锁。


Runner 必须执行步骤 10 定义的背压和资源上限。达到并发上限时 run 进入有界 `queued` 状态；达到单轮安全上限或磁盘余量不足时 fail closed，不能跳过文件后声称 ChangeSet 完整。

### 5.2 终止屏障

新增 `integration/turn_files/capture.py`、`diff.py` 和 `cas.py`。

`capture.py` 负责终止屏障和稳定遍历，`diff.py` 负责 PathState 比较，`cas.py` 只负责 blob 校验、原子写入和读取。

收到最终回答、取消或错误后，Runner 按以下顺序执行：

1. 将 run 状态从 `running` 原子更新为 `quiescing`，拒绝新的 tool/approval/message 控制。
2. 通知 Agent 停止调度新工具，等待当前工具限定时间完成。
3. 先撤销该轮 egress capability，停止 Provider gateway/broker 接受新请求，并等待在途连接于上限内结束；超时强制关闭连接。
4. `terminal.backend=docker` 根据 journal 的精确 Terminal container ID 执行 `stop -> bounded wait -> kill -> rm`，并重新确认 mount identity。Docker + `local` 不执行 daemon 操作。
5. POSIX（包括 Docker 外层执行容器）对本轮进程组/namespace 执行 `TERM -> wait -> KILL`；Windows 先通知协作退出，再终止当轮 Job。
6. Runner 先持久化 Terminal 已删除的 daemon 证据；Docker launcher 只核验 Worker namespace 已空，再以根 fd 安全遍历交还 shadow 所有权并提交 UID 租约。Windows 确认 Job 为空后移除当轮 ACE/profile。
7. 等待所有 PID/HANDLE、broker/gateway、可选 Terminal 和 launcher lease 被回收。任一状态不确定都保持 `quiescing` 或标记恢复失败，不能扫描或复用 UID。
8. 写入 `quiesced` transaction journal 并 fsync；只有到达该屏障后才允许扫描 work。

如果仍检测到 work 文件持续变化，读取采用“`lstat -> 流式读取/hash -> lstat`”校验并最多重试三次；仍不稳定则整轮 `capture_status=failed`，不能把不一致快照标记为完整。

### 5.3 确定 outcome 与后续动作

- 正常完成设置 `outcome=completed`，进入步骤 6；capture 完整后自动进入步骤 8。
- 用户取消设置 `outcome=cancelled`，模型或工具错误设置 `outcome=errored`，Runner/Worker 非预期退出设置 `outcome=interrupted`；三者完成终止屏障后仍进入步骤 6。
- 异常 outcome 在 capture 完整后按本轮冻结的 `abnormal_apply_policy` 处理：`auto` 进入步骤 8，`review` 进入 `pending_review`；首版默认 `auto`。
- capture 无法证明完整时设置 `capture_status=failed`，禁止 apply，并保留受限诊断目录供恢复或人工检查。

步骤 5 完成标准：本轮 execution owner、子进程和可选 Terminal sibling 容器均已收敛，work 可稳定读取；取消只影响目标 run；同根 snapshot/apply 遵守锁顺序；每种退出都有唯一 outcome。

## 步骤 6：计算 diff 并写入 CAS

### 6.1 PathState 和 diff 矩阵

对 baseline 与 work 分别完整遍历纳入范围，构造：

```text
PathState(root_kind, relative_path, file_type, sha256, size,
          posix_mode, windows_attributes, link_target, reparse_tag)
```

比较规则固定为：

| baseline | work | action |
| --- | --- | --- |
| 不存在 | 普通文件或受支持 link/reparse node | `created` |
| 存在 | 不存在 | `deleted` |
| 类型不同 | 存在 | `type_changed` |
| 类型相同、内容或链接目标不同 | 存在 | `modified` |
| 内容相同、平台元数据不同 | 存在 | `metadata_changed` |
| 全部相同 | 存在 | 不生成记录 |

目录使用步骤 3 定义的 `DirectoryPathState` 参与同一矩阵并持久化为 `file_changes`。目录创建、删除、平台权限元数据和 file/directory/link type change 必须进入依赖排序；目录没有 before/after blob，不能用空内容 hash 伪装普通文件。

不做 rename 猜测，因此重命名稳定表示为 `deleted + created`。普通文件必须完整读取并计算 SHA-256；mtime/size 只能用于展示和稳定性校验，不能跳过最终 hash。

### 6.2 CAS 写入与完整性校验

- 首版 blob 存储格式固定为 `plain-v1`：文件正文原样保存，SHA-256 作为地址和完整性校验，不执行应用层加密。`cas_storage_format=plain-v1` 写入 schema/run capability，未知格式必须拒绝读取，给未来迁移留出显式版本边界但首版不实现第二条读写路径。
- `created/modified/type_changed` 的新普通文件写 after blob；`modified/deleted/type_changed` 的旧普通文件写 before blob；metadata-only 可让 before/after 引用同一 hash。
- blob 写入同一 CAS 目录的随机临时文件并边读边 hash。POSIX 执行 `fsync(file) -> chmod -> rename -> fsync(parent)`；Windows 使用 DACL、`FlushFileBuffers` 和带 write-through 语义的原子替换。
- 目标 hash 已存在时必须重新计算现有 blob 的 SHA-256，不能只校验类型和大小。复用、下载和 apply 时校验失败均应隔离损坏 blob 并 fail closed。
- CAS 可增加后台 scrub，定期验证 blob 文件名、内容 hash、权限和数据库引用；scrub 不能与在途 capture/GC 竞态。
- link/reparse node 不读取目标，target 和 tag 保存在 `file_changes`；内容接口返回结构化元数据，不返回目标文件内容。
- capture 重新扫描 work 的非平凡 ACL、xattr/resource fork、ADS 和 hardlink 关系；发现 Worker 新建的首版不支持语义时使用 `unsupported_file_semantics` 使整轮 capture 失败，不能只跳过该路径或降级成警告。
- 单个文件读取失败、磁盘不足、CAS rename 失败或遍历错误都会让整轮 capture 失败。事务目录和错误码保留供恢复，不能进入步骤 8。

步骤 6 完成标准：相同 baseline/work 得到相同 ChangeSet；临时节点和同内容重写不出现；目录、平台元数据、删除和 type change 准确归类；损坏或不完整 blob 永不用于 apply。

## 步骤 7：持久化账本、恢复和 GC

### 7.1 Store 所有权和连接策略

新增 `integration/turn_files/store.py`、`recovery.py` 和 `gc.py`。

数据库固定为 `STATE_DIR/turn_files.db`。`recovery.py` 处理非终态事务、apply intent、broker/gateway、launcher UID 租约、遗留进程组、Job/AppContainer 授权和可选 Terminal 容器；`gc.py` 只处理无引用 blob 与 complete 事务目录。

所有进程只能通过 store 模块访问数据库，连接启用 `journal_mode=WAL`、`foreign_keys=ON`、`busy_timeout=5000`；Runner 是运行期主写入方，WebUI 只执行查询以及会话删除/截断产生的生命周期事务。


state volume 必须是支持 SQLite 文件锁的本地 bind/named volume；NFS、SMB 等不能可靠提供锁语义的目录不属于 strict 首版支持范围，启动 deep health 必须检测并明确报错。

### 7.2 数据表

`change_sets` 至少包含：

| 字段 | 作用 |
| --- | --- |
| `id` | 随机不可猜测 ChangeSet ID，主键 |

| `workspace_root/profile_name` | 恢复和授权校验，不直接返回前端 |

`cas_gc_candidates` 至少包含 `sha256` 和 `first_unreferenced_at`。它不充当手工 refcount，只记录 GC 首次确认 blob 没有数据库引用的时间；blob 再次出现有效引用时必须删除对应 candidate。

`run_dir_status` 只描述 baseline/work 事务目录的保管和清理阶段，不表示 Agent 执行、capture 或 apply 是否成功，也不能代替步骤 0.5 的四组状态。

外键删除采用 cascade；按 `session_id+turn_id`、`stream_id` 和 CAS hash 建索引。


### 7.3 状态机与事务边界

数据库权威持久化 `capture_status/apply_status`，并保存 `run_phase/outcome` 的查询投影。四组字段使用相同枚举：

```text
run_phase:
  queued -> preparing -> prepared -> running -> quiescing
         -> quiesced -> capturing -> captured -> terminal

outcome:
  unknown | completed | cancelled | errored | interrupted

capture_status:
  not_started | in_progress | complete | failed

apply_status:
  not_started | pending_review | applying | applied
  | partially_applied | conflicted | failed
```

- Runner execution journal 的 `run_phase` 只能向前；`outcome` 一旦离开 `unknown` 不得被普通重试改写。store 投影使用 journal sequence 做 compare-and-set，旧事件不能回退状态。
- `captured` 必须在全部 `file_changes` 和 CAS 文件持久化后，用一个 SQLite transaction 提交。
- 每条 apply 前先写 `apply_state=applying` 和 intent；文件系统操作完成后再写 `applied/conflict/failed`。崩溃恢复根据真实文件 hash 判断 intent 是否已完成。
- 完整 ChangeSet 查询只读取 `captured` 之后的记录；`preparing/running` 只能返回状态摘要，不能伪装成空变更集。
- 账本分歧时，`run_phase/outcome` 从 Runner execution journal 修复，capture/apply 从数据库与文件系统 intent 核验，浏览器 Run Journal 只重建展示事件；任何投影不能覆盖权威事实。

### 7.4 会话删除、CAS 租约和 GC

CAS 引用通过 `file_changes.before_sha256/after_sha256` 查询派生，不维护手工 refcount。只要至少一个未 tombstone 的 ChangeSet 仍引用 blob，就不设置删除期限。prepare/capture、下载和 scrub 中的 blob 使用有期限租约，GC 必须忽略有效租约对象。

删除采用“立即逻辑删除、延迟物理回收”：会话删除、清空或按 turn 截断的生命周期事务一旦提交，相关 ChangeSet、Manifest 投影和内容 API 立即不可查询或下载；24 小时窗口不是撤销期，也不允许用户继续访问。只有 CAS 确认失去全部有效引用满 24 小时后，GC 才能删除磁盘 blob。

会话删除、清空或按 turn 截断时，固定执行：

1. 在 store 中写 session/turn tombstone，并拒绝对应范围的新 run 和新 CAS 引用。
2. 取消或明确终结活跃 run，等待 capture/apply 到达允许删除的状态。
3. 在同一生命周期事务中删除对应 ChangeSet 和 Manifest 投影。
4. Runner 恢复流程看到 tombstone 时不得重新提交引用或恢复 apply。
5. 最后唤醒 GC；请求不等待 blob 物理删除完成即可返回删除成功。

GC 执行顺序：

1. 获取 GC lock，并创建当前被引用 hash 的临时集合。
2. 对首次确认无引用的 blob，在 `cas_gc_candidates` 写入 `first_unreferenced_at`；若 blob 恢复有效引用，则删除 candidate 并重新开始未来的安全窗口。
3. 合并有效租约，只删除持续无引用、无租约且 `first_unreferenced_at` 已满 24 小时的 blob。不得使用 blob 创建时间或文件 mtime 代替无引用起点。
4. blob 删除并 fsync 所在目录后删除 candidate；删除失败保留 candidate 供幂等重试，空 prefix 目录可清理。
5. 对 `capture_status=complete` 且 run 已终结的 baseline/work，从终结时间起计算独立的 24 小时保留窗口；到期后才进入下述事务目录两阶段清理。非终态、捕获失败、身份不一致或状态无法确认的目录永不由普通 GC 物理删除。CAS 的 24 小时从“持续无引用”开始计算，与事务目录保留窗口互不替代。

事务目录清理固定执行：

1. 清理器通过已锚定的 `runs` 根句柄定位直接子项，并确认目标不是 symlink、junction 或出根 reparse point；不得把用户 workspace/Profile 中的同名目录作为候选。
2. 重新校验 `run.json`、数据库和 `transaction.jsonl` 中的 `stream_id`、`run_dir_generation`、`manifest_sha256` 完全一致，并确认 owner、mode 或 Windows DACL、所在 volume identity 未发生变化。
3. 确认 Worker、Terminal、capture、apply、lease 和未完成 intent 均不存在；任何未知都按不允许删除处理。
4. 先持久化 `quarantine_intent` 并把 `run_dir_status` 置为 `cleanup_pending`，再原子 rename 到 `quarantine/<stream_id>.<run_dir_generation>`，随后记录 `quarantined`。崩溃恢复必须能判断移动尚未发生、已经完成或需要人工处理。
5. 只有上述完整捕获且身份验证通过的正常目录，才由 GC 在隔离后物理删除；删除完成并刷盘父目录后记录 `deleted`。删除失败保留在 quarantine 并幂等重试。
6. 捕获失败、三方身份不一致、权限或 volume 变化、状态无法确认的目录只进入 quarantine，不设自动物理删除期限；必须由管理员明确确认后，重新执行同样的身份和在途资源检查再删除，并提示其中可能含有尚未进入 CAS 的唯一文件。
7. 无法安全原子移动时原地保留，标记 strict degraded 并告警；禁止使用通配符、递归扫描名称或“清空未知目录”作为恢复手段。
8. 磁盘不足时暂停接受新的 strict run 并告警，允许已启动 run 优先收敛；不得静默删除异常目录或缩短保留窗口腾空间。

步骤 7 完成标准：Runner 在任一非终态以及事务目录 create/quarantine/delete 任一阶段被 SIGKILL 后可幂等恢复；异常 outcome 按冻结策略 apply 或待确认；删除/截断提交后归档立即不可访问且不会复活引用；GC 只回收持续无引用满 24 小时且无租约的 blob，并只物理删除完整捕获、已终结满 24 小时且身份验证通过的正常事务目录。

## 步骤 8：应用文件、检测冲突和人工确认

### 8.1 自动应用门槛、锁和冲突判断

新增 `integration/turn_files/apply.py` 和 `safe_fs.py`。

`safe_fs.py` 只定义平台无关的安全操作契约，实现分别放在 `safe_fs_posix.py` 和 `safe_fs_windows.py`。handler 不得直接使用 `Path.write_*`。

POSIX 实现使用 anchored directory fd 和 `O_NOFOLLOW`。Windows 实现使用 `CreateFileW` HANDLE、`FILE_FLAG_OPEN_REPARSE_POINT`、`GetFinalPathNameByHandleW` 和 volume identity，每一级父路径都在使用点验证。

`apply.py` 按 `volume identity + canonical root` 的 hash 获取跨进程独占 apply lock，使同一 workspace/Profile 一次只合并一个 ChangeSet，不同 root 可并行。


`capture_status=complete` 是所有自动 apply 的硬门槛。`completed` 固定自动 apply；`cancelled/errored/interrupted` 读取本轮冻结的 `abnormal_apply_policy`，首版默认 `auto`，预留 `review` 进入 `pending_review`。

即使策略为 `auto`，每条路径仍必须通过 baseline compare-and-swap；冲突路径不覆盖，安全路径继续应用。capture 不完整、事务已 tombstone 或安全校验不确定时，任何策略都不能启动 apply。

每条变化应用前重新读取真实路径并与 baseline `PathState` 比较：

- `created`：真实路径仍不存在才可应用。
- `modified/metadata_changed/deleted`：真实类型、内容 hash、平台元数据、link target/tag 与 baseline 完全一致才可应用。
- `type_changed`：真实旧类型和旧内容仍与 baseline 一致才可替换。
- 路径任一父级变为 symlink/junction/reparse point、最终 HANDLE 出根、无法读取或已被外部修改，一律冲突，不覆盖当前文件。

### 8.2 已选定按路径部分应用

1. 先按深度从深到浅处理删除，避免父目录影响子路径检查。
2. 再创建所需父目录，按浅到深处理 created/modified/type_changed。
3. POSIX 普通文件从 CAS 写入同目录临时文件，执行 `fsync -> os.replace -> fsync(parent)`。Windows 使用同 volume 临时文件、`FlushFileBuffers` 和 `ReplaceFileW/MoveFileExW(MOVEFILE_WRITE_THROUGH)`。
4. POSIX symlink 在同目录创建临时链接后原子替换。Windows junction/reparse 只在白名单 type/tag 与 target 可完整重建时支持，否则该路径不可 apply。
5. metadata-only 调用平台 adapter。POSIX 使用 fd 操作 mode；Windows 通过已验证 HANDLE 修改约定 attributes。删除始终针对已验证的节点且不跟随链接。
6. type change 先写 apply intent，再安全移除旧节点并原子放入新节点；恢复时依据 before/after 状态决定继续或标记冲突。

本方案已选定按路径部分应用，不承诺整个 ChangeSet 全有或全无。检测到冲突后只跳过该路径，不回滚或阻塞已经验证安全的其它路径。

单路径 IO 失败标记 `failed`，继续处理其它安全路径。全部成功为 `applied`；至少一条成功且另有冲突/失败为 `partially_applied`；零成功且存在冲突为 `conflicted`；零成功且只有 IO/安全失败为 `failed`。

后续 resolve 只处理尚未应用的路径，不能重新执行已经 `applied` 的条目。多文件之间存在业务依赖时，首版不推断依赖关系，UI 必须逐路径展示真实结果。


### 8.3 人工确认和解决冲突

人工接口同时支持 ChangeSet 级确认和单路径 resolve。单路径请求包含 `session_id`、`turn_id`、`root_kind`、`path`、`resolution=apply_archived|keep_current` 和可选 `expected_current_sha256`：

- `apply_archived` 必须重新授权会话和路径，并使用 expected hash 做 compare-and-swap；当前文件再次变化返回 `409 current_file_changed`。
- `keep_current` 只更新该条 `apply_state=kept_current`，不修改磁盘。
- 已解决请求按相同参数重试返回原结果；不同决策再次提交返回 `409 already_resolved`。

当异常策略为 `review` 时，用户确认仍执行完整锁、授权和 compare-and-swap。确认只改变 apply 门槛，不能绕过冲突检测，也不能覆盖 tombstone 会话。

步骤 8 完成标准：外部修改不被覆盖；同路径后应用者冲突；异常轮次遵循冻结策略；capture 不完整不应用；apply 崩溃可依据 intent 恢复且不重复覆盖或删除。

## 步骤 9：接入 SSE、API、Manifest 和 UI

### 9.1 Runner 与 WebUI 路由

在 `api/routes.py` 中保留现有浏览器响应白名单，但完善 runner SSE bridge：

- `POST /api/chat/start` 在 strict 模式执行步骤 1、2 的预检、标识预分配和幂等提交，成功响应仍只暴露现有 `stream_id/session_id/turn_id/title` 等字段。
- `GET /api/chat/stream?stream_id=` 使用 Runner events cursor 转发事件，不创建新的 WebUI `STREAMS/CANCEL_FLAGS/Agent cache` 替代物。
- Runner 终态集合统一为 `done`、`cancel`、`apperror`、`error`、`stream_end`；SSE bridge 遇到任一终态都结束，避免当前只识别部分事件导致连接悬挂。
- Runner 必须在 ChangeSet 数据库提交和 apply 状态提交后发送 `turn_files`，随后才能发送 `done/cancel/apperror`；该顺序写入 Runner journal，重连时保持不变。

`turn_files` SSE 使用版本化小载荷：

```json
{
  "version": 1,
  "session_id": "s1",
  "turn_id": "t1",
  "stream_id": "r1",
  "turn_key": "turn:42",
  "change_set_id": "cs_...",
  "outcome": "completed",
  "capture_status": "complete",
  "apply_status": "partially_applied",
  "counts": {"created": 2, "modified": 1, "deleted": 1, "conflict": 1},
  "query_url": "/api/session/turn_files?session_id=s1&turn_id=t1"
}
```

`counts` 按 action 统计全部受支持节点类型，包含普通文件、link/reparse node 和目录；它不是 Artifact chip 数量。客户端不得用 chip 数量反推 ChangeSet 总数。

### 9.2 查询、内容和冲突接口

新增 `integration/turn_files/handlers.py`，并从 `api/routes.py` 注册：

- `GET /api/session/turn_files?session_id=&turn_id=`：返回 ChangeSet、排序后的 `file_changes` 和状态；每项以 `before_type/after_type` 明确普通文件、目录或 link/reparse node；先通过现有 session/profile 授权，不能只凭 ChangeSet ID 查询。
- `GET /api/session/turn_files/content?session_id=&turn_id=&root_kind=&path=&version=before|after`：先定位授权的 `file_changes`，再读取其 hash；目录请求返回 `409 no_file_content`，禁止把目录当空文件，也禁止 `/blobs/<hash>` 形式的直接访问。
- `POST /api/session/turn_files/resolve`：WebUI 完成授权后调用 Runner 的 `POST /v1/change_sets/<id>/resolve`，由 Runner 执行步骤 8；Runner 不可用时返回 `503`，WebUI 不自行写 workspace。
- 所有响应包含稳定英文 `error_code` 和可本地化 `message`；路径不存在、版本为空、会话越权、CAS 损坏分别返回明确的 404/403/409/500。
- 下载普通文件时设置安全的 `Content-Type`、`Content-Disposition` 和 `X-Content-Type-Options: nosniff`；HTML/SVG 等内容默认 attachment，不能在 WebUI origin 内直接执行。

所有 integration 路径段使用 snake_case。JSON 响应统一通过 `j()`/`bad()`；调用方可读错误说明使用中文；接口、状态码和 schema 同步更新 `integration/swagger/openapi.json` 与 `integration/README.md`。

### 9.3 Manifest 投影

新增 `integration/turn_files/manifest_projection.py`，只把 ChangeSet 投影到现有 `session_manifest.db`：

- 只有至少一侧是非目录节点的 `created/modified/metadata_changed/type_changed` 才按既有规则生成 artifact；纯目录创建、删除和目录元数据变化不生成 Session Manifest artifact，`deleted` 仍只保留在详细 ChangeSet。file-to-directory 或 directory-to-file 的 `type_changed` 在详细 ChangeSet 始终完整展示，只有存在可预览非目录版本时才允许生成对应 chip。
- workspace path 保存 workspace 相对路径。Profile artifact 的 `path` 保存 Profile 根内相对路径，并使用现有独立 `profile` 字段，禁止编码成 `profile:<path>`。
- 已应用且仍存在的 workspace 文件可继续使用 `preview=file`。Profile、冲突、删除和归档版本使用新增 `preview=turn_file`，由 ChangeSet 内容接口预览。
- `source_tool` 固定为 `turn_files`，不伪造具体写入工具。新增可选 `turn_file` 元数据包含 `change_set_id`、`root_kind`、`apply_state`，不得把内部真实根或 CAS hash 返回前端。
- `preview=turn_file` 和 `turn_file` 属于版本化 Manifest wire contract 扩展，必须先同步修改 `docs/session-manifest-api.md`、artifact RFC、后端 projection 和前端 preview gate，不能宣称旧 schema 原样兼容。
- strict 新轮次以 ChangeSet 为唯一 artifact 权威来源，关闭 `_extract_turn_artifact_entries`、assistant prose 和 diff 正则回填；历史轮次及 off 模式继续使用原 backfill。
- ChangeSet 即使包含零条变化，也作为该 strict 轮次的 authority marker；Manifest 构建看到该标记后必须返回空 artifacts，不能因为 store 中没有 artifact 行而触发旧 backfill。
- 投影失败不能反向改变已提交 ChangeSet；记录 repair-needed，`GET /api/session/manifest` 可从 ChangeSet 幂等修复缺失 artifact。

### 9.4 前端接入

- `static/messages.js` 监听 `turn_files`，按 `stream_id + change_set_id` 去重，保存状态摘要，并在终态后拉取权威查询接口。
- `static/workspace.js` 的 Session Inspector 使用 ChangeSet 投影结果；轮次 chip 只展示非目录 artifact 的 path 和 created/modified/conflict 状态，点击普通已合并文件打开 workspace，点击删除或冲突文件打开 CAS before/after 视图。
- ChangeSet 详情按权威排序展示全部节点，并为目录使用目录图标及 `created/deleted/metadata_changed/type_changed` 状态；空目录和目录删除只能在详情中查看，不生成聊天 chip。详情顶部的 action 计数必须与包含目录的 SSE/GET `counts` 一致。
- `static/style.css` 只补充状态图标和冲突样式，保持现有 chip 尺寸与换行行为；所有新增文案进入 i18n，不在 JS 中硬编码。
- SSE 仅作即时提示；页面刷新、SSE 重放或切换会话后始终以 GET 结果覆盖本地缓存。

步骤 9 完成标准：新 strict 轮次的 artifact 与 ChangeSet 投影一致；Profile 不污染 path 语义；冲突和历史版本通过授权接口读取；旧会话、旧 Manifest schema 和 off 模式不回归。

## 步骤 10：部署、配置、观测和安全限制

### 10.1 功能开关与部署配置

- 增加 `HERMES_WEBUI_TURN_FILES=off|strict`，初始默认 `off`；`strict` 强制使用 runner，不允许 best-effort fallback。
- 首版不增加 CAS 应用层加密环境变量或运行时开关，统一使用 `plain-v1`。部署说明必须要求敏感环境对 `STATE_DIR`、Docker state volume 和备份启用宿主/存储层加密，并说明应用无法可靠自动证明 FileVault、BitLocker、LUKS 或云盘加密状态，因此该项不伪装成 strict preflight 成功证明。
- 增加 `HERMES_WEBUI_TURN_FILES_ABNORMAL_APPLY=auto|review`，首版默认 `auto`。Runner 在 prepare 时冻结到 run；项目配置和 Worker 均不能修改。
- strict 模式下若 `HERMES_WEBUI_RUNTIME_ADAPTER` 未设置，则内部按 `runner-local` 处理；若操作者显式设置为 `legacy-direct` 或 `legacy-journal`，启动健康检查报配置冲突并拒绝 strict 新会话，不能由配置优先级意外绕过捕获。
- strict 固定使用 `server.py` 监督的共置 Runner，由 `server.py` 注入内存 base URL/key。禁止配置跨 WebUI 存活的 discovery 或 key 交接。
- 操作者显式设置外部 `HERMES_WEBUI_RUNNER_BASE_URL` 时，若不满足当前 strict 拓扑和协议校验，应拒绝新会话；off 模式保留既有外部 Runner 兼容行为。
- Bearer 不得进入 Compose 明文、持久 key 文件、日志或 Worker 环境。每次 WebUI 启动生成新 key，旧 key 不可恢复或复用。
- 增加 `HERMES_WEBUI_TURN_FILES_DEPLOYMENT=native|docker`。Docker Compose 显式写 `docker`；原生启动默认 `native`。检测结果与显式值冲突时拒绝 strict，不靠 `/.dockerenv` 单点猜测。
- 每轮 Worker 从 Profile 冻结 `TERMINAL_ENV=local|docker`。`native + docker` 返回 `unsupported_deployment_backend`；`docker + docker` 强制关闭持久 Terminal 容器和跨轮复用。
- 原生 strict 运行 OS adapter capability probe。macOS/Linux/Windows 任一关键能力不可验证时拒绝新 run，deep health 返回稳定错误码和脱敏证据。
- Windows 原生 strict 不得继续复用“实验性/社区支持”作为产品前提。第一阶段必须同步完成并文档化正式的原生 Windows 安装、启动和升级路径；`bootstrap.py`、`start.ps1`、Hermes Agent local Terminal、Provider、允许的 MCP、取消和退出清理都必须通过真实 Windows 验收。它不依赖当前不支持 Windows 的 `api/terminal.py` 内嵌 PTY。
- Docker + `local` 的默认 Compose 不挂载 Docker socket，也不要求 outer-container ID。Docker + `docker` 才通过显式 override/profile 增加 `/var/run/docker.sock` 和可选 `HERMES_WEBUI_OUTER_CONTAINER_ID`。
- Docker socket 只对可信 Runner 可见。Worker 进程的 mount namespace 必须隐藏 socket，Terminal sibling 也不挂载 socket。
- Provider/OAuth 长期凭据只由 Runner 侧 Provider gateway 读取。首版 registry 只接纳实际使用 `chat_completions`、`codex_responses` 或 `anthropic_messages`，且凭据注入/刷新已验收的 adapter。
  `bedrock_converse`、`codex_app_server`、`copilot-acp`、Gemini native、Vertex/ADC 和其它特殊或未知 transport 在 strict preflight 中拒绝，不能回退为向 Worker 注入凭据。
- 增加 `HERMES_WEBUI_TURN_FILES_EGRESS=provider_only|restricted_public`，默认 `restricted_public`。Provider gateway endpoint 从本轮 Profile 冻结；`restricted_public` 只允许普通工具经 broker 访问重验后的公共 HTTP(S) endpoint，不赋予 Worker 原始网络。
  管理员可全局收紧为 `provider_only`，项目内 policy 只能进一步缩小网络权限。
- 远程 MCP 不使用单独管理员白名单：Runner 直接信任会话绑定 Profile 中已启用的 HTTP/SSE `mcp_servers` 项，并在 prepare 时冻结。严格模式下 WebUI 的既有 MCP CRUD 权限即批准权限；静态 headers/OAuth 只保留在 Runner 侧，每轮 transport 不复用。默认 `restricted_public` 允许这些冻结目标；`provider_only` 禁用远程 MCP。stdio MCP 不是远程 MCP，只有按轮在 Worker 沙箱内启动时才允许。
- 增加可选的 `HERMES_WEBUI_TURN_FILES_POLICY_FILE`。未设置时使用内置 Profile 白名单；显式设置时只接受管理员策略文件的绝对路径，且缺失、权限不安全或内容无效不得回退默认值。
- Docker 部署把管理员策略文件只读挂载到外层执行容器，并给环境变量填写容器内绝对路径；不得把宿主路径写入 policy snapshot、日志或 API。原生部署直接读取管理员拥有的本地文件，但 Worker 视图必须隐藏该文件。
- 本地/LAN Provider 不维护第二份管理员白名单。当前选中模型经权威 resolver 得到的 Profile `model.base_url` 或匹配 `custom_providers[].base_url` 即本轮批准事实；Runner 冻结规范化 scheme、host、effective port、base path 和 adapter，只允许 adapter 固定后缀。通配符/CIDR/端口范围、跨 origin redirect，以及命中 WebUI、Runner、Gateway、Docker API 或 metadata 保留目标时始终拒绝。
- strict preflight 固化并验证 OS/内核、sandbox、FD/HANDLE、网络 deny、proxy shim、Provider adapter、egress broker、Docker launcher capability 和 UID 池；任一项未知都按不支持处理。
- 增加有界参数 `HERMES_WEBUI_RUNNER_START_TIMEOUT`、`HERMES_WEBUI_RUNNER_DRAIN_TIMEOUT`，默认分别为 `30` 秒和 `60` 秒，允许范围分别为 `5..300` 秒和 `10..600` 秒；重启退避和失败窗口使用代码常量，首版不暴露无限可调配置。
- `.hermes-turn-files.json` 只接受 `version`、workspace `include/exclude` 和只能收窄的 `profile_exclude`；规则在轮次开始时冻结。
- `turn_files` SSE 和查询响应均带 `capture_status`、`apply_status`、`outcome`，调用方不得将 `failed/degraded` 展示为完整结果。
- 新增接口同步更新 integration Swagger、路由表和运行架构文档。

### 10.2 背压与资源上限

Runner 必须为首版纳入配额的资源提供有界安全默认值，并允许管理员在受控范围内配置：

- 全局活跃 Worker 进程数、同时 prepare/snapshot 数、同时 capture/hash 数和同时启动 Terminal sibling 容器数。
- 队列长度、排队超时、单轮执行超时、锁等待超时和 drain 超时。
- 单轮文件数、单文件大小、总捕获字节数、事务目录空间和最低磁盘余量。
- 每轮 Provider/egress 连接数、请求数、上传/下载字节、连接/空闲/总超时和 DNS/redirect 次数；launcher UID 池大小固定覆盖最大活跃 Worker 数。

首版不提供每轮 CPU、内存或 PID 上限配置，也不定义相应环境变量。全局活跃 Worker 限制的是 Runner 接受的顶层轮次进程数，不限制单个 Worker 可创建的子进程数量；执行超时限制运行时长，不限制瞬时 CPU 或内存使用。这一取舍必须作为 strict 的已知拒绝服务风险公开说明，不能由部署探针推断出不存在的每轮资源隔离。

| 单请求总超时 | `HERMES_WEBUI_TURN_FILES_NETWORK_REQUEST_TIMEOUT_SECONDS` | `1200`（20 分钟） |
| 单请求重定向 | `HERMES_WEBUI_TURN_FILES_NETWORK_MAX_REDIRECTS` | `5`；每一跳重新授权 |
| DNS 解析次数 | `HERMES_WEBUI_TURN_FILES_NETWORK_MAX_DNS_RESOLUTIONS` | `4096` |
| 单次 DNS 返回地址数 | `HERMES_WEBUI_TURN_FILES_NETWORK_MAX_DNS_RESULTS` | `16` |

Provider 配额只统计模型 gateway；远程 HTTP/SSE MCP 与普通工具共享 egress 配额；`provider_only` 下 egress 配额存在但远程 MCP/普通公网请求不可用。请求、连接和字节按 `stream_id` 从零累计，重试和 redirect 每次都计数，不能通过新建 shim、切换工具或复用连接重置。上传/下载至少统计实际传输 payload；broker 若解压响应，还必须同时限制解压后字节，任一口径先到上限即终止本轮网络 capability 并返回稳定的 `network_quota_exceeded`。

网络覆盖同样有代码硬上限：Provider/egress 并发连接分别为 `1..32`/`1..128`，请求数 `10..10000`/`10..100000`，单向总量 `1 MiB..100 GiB`，连接超时 `1..120` 秒，空闲超时 `10..1800` 秒，单请求总超时 `30..3600` 秒，redirect `0..10`，DNS 解析 `16..100000`，单次返回地址 `1..64`。未配置使用默认值；显式 `0` 只有 redirect 可表示禁止重定向，其它字段均为非法而不是无限。

所有 Worker 复用 WebUI/Runner 所在主机或外层容器的物理 CPU、内存、网络和 state volume，不为每轮预留独立机器或 Worker 容器。宿主进程、systemd/Windows 服务或外层容器存在 CPU、内存、PID 约束时，Worker 继承该部署级约束；没有外部约束时就共享宿主机可用资源。复用只发生在物理容量层；进程身份、cwd/HOME/env、FD/HANDLE、事务目录、网络 session/凭据和已实现的配额计数仍按 `stream_id` 隔离。

Runner 是共享资源池中应用级票据的唯一所有者。每个 run 在进入 prepare、running、capture、Docker Terminal 和网络阶段前取得对应资源票据，退出、取消、错误、替换和恢复时必须归还；新进程、shim、MCP、Terminal sibling 或重试继承原 `stream_id` 的计数，不能创建第二份额度。WebUI 只查询资源状态，不在进程内另建并发计数器。票据只约束 Worker 数、阶段并发、磁盘和网络等已定义项目，不是操作系统级 CPU、内存或 PID 限制。

高配档位增加 `HERMES_WEBUI_TURN_FILES_MAX_TOTAL_RUN_DIR_BYTES=107374182400`（100 GiB）全局事务目录上限，允许范围 `1 GiB..2 TiB`。实际可用上限始终为 `min(配置的全局上限, state volume 当前可用空间减去最低保留量)`；它不是启动时预分配。单轮仍受 50 GiB 限制，因此 4 个 Worker 不能仅凭各自未超限就合计使用 200 GiB。

全局 Provider/egress 并发票据默认分别从 `4 Worker x 每轮 4 = 16` 和 `4 Worker x 每轮 16 = 64` 派生；prepare、capture、Terminal 启动沿用已确认的全局 `2/2/2`。管理员降低 Worker 上限时派生值同步降低；显式提高单轮网络上限不能自动扩大全局票据池。

CAS 是跨轮共享存储，不计入某个 run 的事务目录额度，但所有 CAS 新写入仍受 capture 并发、单轮逻辑捕获量、state volume 最低余量和 GC/lease 规则约束。Docker Terminal sibling 仍携带同一 `stream_id` 的应用级票据，但不设置每轮 `--memory`、`--cpus` 或 `--pids-limit`；它必须加入与外层执行容器相同的部署级 cgroup 预算。无法证明父级 cgroup 一致时只禁用 `Docker + docker` strict，不影响 `Docker + local`。

CPU、内存或 PID 资源耗尽时，Runner 若仍存活，应停止接受新 run、取消受影响轮次并优先收敛；若 Runner/WebUI 被 OOM 或系统级压力终止，新实例按中断恢复。无论哪条路径，只有能够证明 capture 完整的轮次才可继续自动 apply，否则设置 `capture_status=failed` 并保留诊断目录。恢复不能声称已阻止该资源攻击。

达到单轮或共享池并发上限时进入可取消的 `queued`；队列满返回稳定错误码。达到单轮/全局配额或磁盘门槛时 fail closed，保留可诊断状态，不得跳过内容后报告完整。

prepare 已超过源节点/文件上限时不启动 Worker；运行中事务目录越界时发起取消和进程收敛；capture 才发现节点、单文件或逻辑字节超限时设置 `capture_status=failed`，不 apply。空闲空间低于绝对值/比例任一门槛时拒绝新 strict run；已启动 run 仍优先收敛，但任何写入失败都按磁盘错误失败闭合。

quarantine、无法确认的异常目录或待清理目录占用达到安全阈值时，Runner 拒绝新的 strict run 并报告稳定错误码；已启动 run 优先完成进程收敛、capture 和安全隔离。磁盘压力不能触发异常目录自动删除，也不能绕过管理员确认。

队列由当前 Runner 拥有并持久化排队事实，但 WebUI 重启会把旧 Runner 的 `queued` run 明确终结为 `interrupted`，不会在新 Runner 中自动继续排队或启动。

### 10.3 可观测性和安全检查

- 指标至少包含 prepare/queue/hash/apply、锁等待、冲突、恢复、GC、每类资源票据已用/上限/等待数、全局与单轮事务目录字节、`cleanup_pending` 数量、quarantine 目录数量与字节、目录身份不一致次数、磁盘阻断 strict run 次数、UID 池占用、FD/HANDLE probe、egress allow/deny/bytes 和目标分类；不得记录完整 URL query/header/body。
- deep health 报告 Runner、协议、部署/backend、OS proof、FD/网络 proof、Provider adapter、launcher/UID 池、egress broker、磁盘、`cas_storage_format=plain-v1` 和固定的 `resource_isolation=parent_only`。该值明确表示没有每轮 CPU、内存或 PID 硬限制；即使检测到父级 cgroup/Job/service 限制，也不能提升成 per-run isolated。仅 Docker Terminal 额外报告 daemon/mount/proxy/sentinel 和部署级 cgroup 归属证明；不得把无法可靠检测的宿主/卷加密状态报告为已验证，不返回 SID、Bearer、凭据或完整目标。
- 日志对 Authorization、Provider 凭据、session cookie、路径中的敏感片段和错误详情执行集中脱敏。

步骤 10 完成标准：所有纳入首版配额的资源都有所有者、上限、超时、取消和清理路径；CPU、内存和 PID 明确标记为只继承父级而非每轮隔离；不支持的部署在启动前明确失败；运维指标能区分 unavailable、degraded、capture failed、pending review 和 apply conflict。

## 步骤 11：测试、灰度、回滚和验收

### 11.1 实施批次和灰度

1. **基础存储批次**：先落 `models/policy/snapshot/diff/cas/store/apply` 及纯临时目录测试，不接真实聊天路由。该批次可独立验证文件 ChangeSet 准确性。
2. **Git 状态契约批次**：先评审并关闭 G7，固化 Git 状态集合、冲突、应用顺序、恢复和仓库类型边界；该批次先写 RFC/原型，不把 `.git/**` 原样同步到真实仓库。
3. **Runner 契约批次**：实现共置 runner、幂等 start、journal/cursor、WebUI 重启中断旧 run 和文件事务恢复测试，并先修订冲突的 Runner RFC。
4. **macOS 隔离批次**：实现 `sandbox-exec` profile、FD 白名单、无原始网络、Provider gateway 和 egress broker，并在真实 macOS 上完成能力探测和敌对测试。
5. **Windows 正式支持与隔离批次**：先完成原生 Windows 正式安装/启动/升级与 Agent local Terminal 验收，再在真实 Windows 验证 AppContainer/DACL、handle list、Job、egress IPC、无宽泛网络 capability 和 reparse 逃逸。
6. **API/UI 批次**：接入 turn_files SSE、查询/内容/冲突接口和 Manifest authority marker，再增加 Session Inspector 展示。
7. **第一阶段联合灰度**：只有 macOS + local 与 Windows + local 同时通过全部门禁，才一起开放第一阶段 strict；任一失败都不能只对外宣称另一端已完成第一阶段。
8. **原生 Linux/WSL2 批次**：实现并验收 mount/PID/network namespace、bubblewrap、seccomp/Landlock，完成后独立开放，不阻塞第一阶段。
9. **Docker 进程沙箱批次**：仅面向 Linux container，在默认无 socket Compose 中实现最小 launcher、UID 池、namespace、FD 白名单、capability/seccomp/Landlock 和 egress，打通 Docker + local。
10. **Docker Terminal 批次**：仅面向 Linux container，增加显式 Compose override、按轮 Terminal、固定 shadow mounts、每轮 UID、只读 rootfs、无 capability、`--network none`、proxy shim、禁止复用和 volume 冲突检查。
11. **后续灰度批次**：保持默认 `off`，分别灰度原生 Linux/WSL2 + local、Docker + local、Docker + docker；持续确认唯一不支持的原生 + docker 稳定拒绝。

### 11.2 回滚

回滚将 `HERMES_WEBUI_TURN_FILES` 设为 `off` 并恢复 `legacy-direct`，但不删除 `turn_files.db`、CAS 或历史 ChangeSet。

已产生的 strict 历史轮次继续可读。回滚不能对这些轮次重新启用正则 artifact 回填；人工 resolve 在 Runner 不可用时明确返回不可用状态，不能由 WebUI 直接写 workspace。

- 单元测试覆盖 CoW/full-copy 回退、规则优先级、安全 deny、symlink/junction/reparse 逃逸、内容 hash、CAS 去重和原子写入。
- 差异测试覆盖新增、覆盖、同内容重写、权限变化、删除、类型变化、重命名、Unicode 路径、二进制和大文件。
- 特殊文件语义测试在 macOS/Linux/Windows 真机分别覆盖：源路径已有非平凡 ACL、xattr/resource fork、ADS、hardlink 时 prepare 返回 `unsupported_file_semantics` 且不启动 Worker；Worker 在 work 中新建上述语义时 capture 失败、真实目录不变、错误响应不泄露扩展内容；被 policy 排除的路径不误阻断。
- 集成测试分别通过 `write_file`、shell 重定向、Python 脚本、构建命令、MCP 和 Docker 创建文件，断言 policy 纳入的普通文件 ChangeSet 与磁盘最终状态完全一致；`.git/**` 单独按 G7 验收，不能混入文件 action 计数。

- 事务目录生命周期测试覆盖：完整捕获且 run 终结满 24 小时后两阶段清理；create/quarantine/delete 各持久化阶段崩溃恢复；`run.json`、数据库和 journal 身份不一致时只隔离；用户 workspace 中同名 `tmp/baseline/work/<stream_id>` 不被清理；symlink/junction/reparse 出根拒绝；异常目录必须人工确认；磁盘不足阻止新 strict run 但允许活跃 run 收敛；任何路径都不允许按名称批量删除未知目录。
- 生命周期测试覆盖成功、取消、模型错误、POSIX SIGKILL/Windows Job 终止、Runner/launcher/broker 崩溃、apply 崩溃、WebUI-only 重启、外层执行容器/Terminal 容器重启和 tombstone 竞态。

- API 安全测试覆盖越权 session、路径穿越、直接 hash 猜测、已删除会话、截断轮次和凭据文件不入 CAS。

## 附录：特殊名词与缩写

本节解释方案中反复出现的工程术语。这里有两个容易混淆的“CAS”：单独写作 **CAS 存储**时指内容寻址存储；写作 **compare-and-swap** 时指比较后再更新。两者不是同一概念。

### 文件事务与归档

- **ChangeSet（变更集）**：一轮 Agent 执行结束后，由 `baseline` 与 `work` 的最终状态比较得到的权威文件变更清单。它记录路径、变更类型、变更前后内容引用、合并结果和冲突原因；`.git/**` 明确不属于文件 ChangeSet。
- **文件事务**：先在隔离副本中执行文件操作，结束后统一捕获差异并尝试合并到真实目录的过程。本方案不承诺整个 ChangeSet 全有或全无，而是逐路径安全应用。
- **Git 状态事务**：与文件 ChangeSet 分离、负责把 shadow 中有效 Git 状态安全持久化到真实仓库的事务边界。其具体状态模型、冲突和恢复协议由 G7 的独立 RFC 决定；它不等于复制整个 `.git/**`。
- **baseline（基线）**：本轮开始时 workspace 或 Profile 资产的冻结副本，用来判断本轮改了什么，以及合并时真实文件是否已被外部程序修改。
- **work / shadow workspace（工作副本 / 影子工作区）**：Agent、File Tool、Terminal 和 MCP 在本轮实际读写的隔离目录。执行期间产生的文件先留在这里，不直接写入真实 workspace。
- **PathState（路径状态）**：某个相对路径的结构化状态，包括类型、内容哈希、大小、POSIX mode 或 Windows attributes、link target 与 reparse tag。diff 和冲突判断都以它为输入。
- **DirectoryPathState（目录路径状态）**：目录专用的 PathState，记录存在性和受支持的平台元数据，不包含 CAS 内容 hash。它保证空目录、目录删除和 file/directory 类型互换可被应用与恢复；首版只在 ChangeSet 详情展示纯目录变化，不生成聊天 Artifact chip。
- **diff（差异计算）**：比较 baseline 与 work 的最终 PathState，生成 `created`、`modified`、`metadata_changed`、`deleted` 或 `type_changed` 记录。
- **CAS（Content-Addressed Storage，内容寻址存储）**：以内容的 SHA-256 哈希作为存储地址的归档区。相同内容只保存一份，ChangeSet 通过哈希引用变更前后的文件内容。首版 `plain-v1` 在应用层保存明文，静态保密依赖宿主磁盘、volume 和备份加密。
- **SHA-256**：一种密码学哈希算法，把任意长度内容映射为固定长度摘要。本方案用它标识文件内容、校验 CAS blob，并判断内容是否相同；它不是加密，不能隐藏内容。
- **blob（二进制大对象）**：CAS 中保存的一份原始文件内容。blob 名称来自内容哈希，不包含原文件名；读取前仍须通过 session、turn 和 path 做授权。
- **应用层加密 / 磁盘加密**：应用层加密由程序在写 CAS 前加密正文；磁盘或卷加密由 FileVault、BitLocker、LUKS、云盘等在存储层保护全部文件。首版只采用后者，Runner 仍需用 `0600`/DACL 和 API 授权阻止普通进程读取。
- **GC（Garbage Collection，垃圾回收）**：删除已不再被任何 ChangeSet 引用的 CAS blob 和过期事务目录。本方案对 CAS 采用立即禁止访问、持续无引用满 24 小时后物理回收的规则；GC 必须避开仍在捕获、下载、校验或尚未提交引用的在途数据。
- **CAS GC candidate（CAS 回收候选）**：GC 首次确认某个 blob 没有有效引用时写入的候选记录，用于准确计算 24 小时安全窗口。blob 重新获得引用时删除该记录，不能沿用旧倒计时。
- **quarantine（隔离区）**：`STATE_DIR/turn_files/quarantine/` 下由 Runner 控制的事务目录暂存位置。正常目录在物理删除前先移入这里；捕获失败、身份不一致或状态不明的目录也只隔离并等待管理员确认。它不是用户可访问的回收站，普通 GC 不得清空其中的异常目录。
- **policy snapshot（策略快照）**：本轮开始时冻结的管理员 Profile 上限、项目侧收窄规则、workspace include/exclude 和固定安全规则。执行期间即使配置文件变化，本轮仍使用原快照，以保证捕获口径稳定。
- **hard deny（固定安全拒绝）**：无论项目配置如何都不能捕获或归档的路径规则，例如凭据、认证状态和 WebUI 内部状态。它的优先级高于用户 include。
- **管理员策略文件**：由 `HERMES_WEBUI_TURN_FILES_POLICY_FILE` 显式指定的可信 JSON 文件，用完整 `profile_allow`/`profile_exclude` 定义部署级 Profile 捕获上限。未配置时使用内置默认值；显式配置出错时不能回退。
- **项目策略文件**：workspace 根目录的 `.hermes-turn-files.json`。它可配置 workspace 的 include/exclude，并通过 `profile_exclude` 收窄 Profile，但不能增加 Profile 路径或覆盖 hard deny。

### 一致性、持久化与恢复

- **RFC（Request for Comments）**：用于评审重要设计和行为契约的设计文档。RFC 先说明目标、非目标、状态机、兼容性和验收条件，再由后续代码实现；它不是 HTTP 请求。
- **状态机**：只允许对象沿预先定义的状态和方向变化。本方案把 `run_phase`、`outcome`、`capture_status` 和 `apply_status` 分开持久化，非法转换应被拒绝。
- **幂等**：同一个请求或恢复步骤执行一次与重复执行多次，最终效果相同。例如相同 payload 的 `POST /v1/runs` 重试应返回原 run，而不是再启动一轮。
- **journal（事务日志）**：按顺序记录已经发生的关键 intent 和状态变化，用于进程崩溃后的判断与恢复。`transaction.jsonl` 服务于文件事务恢复，不等同于浏览器 SSE 事件流。
- **WAL（Write-Ahead Logging，预写日志）**：SQLite 的一种日志模式。数据库先把修改写入 WAL，再合并到主数据库文件，可改善并发读写和崩溃恢复，但仍要求底层文件系统提供可靠锁语义。
- **fsync / FlushFileBuffers**：POSIX 使用 fsync，Windows 使用 `FlushFileBuffers` 和 write-through replace，尽可能把关键修改刷新到持久存储。只调用 write/rename 不代表断电后一定可见。
- **原子 rename / replace**：文件系统对外只显示操作前或后的完整名字绑定。POSIX 使用 rename/replace，Windows 使用 `ReplaceFileW/MoveFileExW`；它们只在同一文件系统/volume 内承诺对应语义。
- **compare-and-swap（比较后更新）**：应用归档版本前，先确认真实文件仍等于预期 baseline 或 `expected_current_sha256`；只有比较成功才更新，否则返回冲突。
- **apply intent（应用意图）**：真正修改文件系统前先持久化的记录，说明准备对哪个路径执行什么操作。崩溃恢复据此判断操作未开始、已完成还是状态不确定。
- **capture / apply（捕获 / 应用）**：capture 从 baseline 与 work 生成 ChangeSet 并写入 CAS；apply 把 ChangeSet 中的非冲突结果合并到真实目录。两者状态必须分开记录。
- **fail closed（失败闭合）**：无法证明捕获完整、路径安全或当前文件未变化时，选择不合并并明确报错，而不是按成功或允许处理。
- **共享资源池 / 资源票据**：WebUI、Runner 和各轮 Worker 使用同一主机或外层容器的物理容量，但 Runner 在进入各阶段前按 `stream_id` 发放有界票据。票据限制 Worker 数、阶段并发、磁盘和网络等明确项目，不代表提前预留硬件，也不是每轮 CPU、内存或 PID 隔离；子进程、Terminal 或重试不能取得新身份来重置额度。
- **`resource_isolation=parent_only`**：诊断字段，表示 Worker/Terminal 只继承宿主服务或外层容器已有的部署级资源约束，应用没有设置每轮 CPU、内存和 PID 硬上限。它是能力边界说明，不是健康通过标记。
- **cgroup（control group，控制组）**：Linux 内核对一组进程统计和限制 CPU、内存、PID 等资源的机制。Docker 外层执行容器与 Terminal sibling 必须归入同一部署级父预算；本方案不为每轮再创建独立资源配额。
- **OOM（Out of Memory，内存耗尽）**：系统或 cgroup 无法满足内存分配时触发的失败，可能终止 Worker、Runner 或整个 WebUI。OOM 后只能依据持久状态恢复，不能假定 capture 完整。

### 文件系统安全

- **CoW（Copy-on-Write，写时复制）**：创建副本时先共享底层数据块，只有文件被修改时才复制相关内容。macOS `clonefile` 和 Linux `FICLONE` 可降低副本的时间与空间成本。
- **symlink（符号链接）**：保存另一个路径作为目标的特殊文件。遍历时使用 `lstat()` 读取链接本身，不跟随目标；否则可能越过 workspace 边界读取或覆盖其它位置。
- **anchored fd（锚定目录文件描述符）**：先安全打开可信目录，再用 `dir_fd` 相对操作子路径。它减少“检查路径安全后，父目录被替换成 symlink”的检查与使用时间差。
- **`O_NOFOLLOW`**：打开路径时拒绝跟随符号链接的操作系统标志。它与 anchored fd 配合，用于降低 symlink 调包和路径逃逸风险。
- **HANDLE（Windows 句柄）**：Windows 内核对已打开文件、目录、进程或 Job 的进程内引用。Windows apply 持有已验证 HANDLE 操作，避免检查后重新按字符串解析路径。HANDLE 不能序列化后供新 Runner 复用。
- **junction / reparse point（目录联接 / 重解析点）**：Windows 上能改变路径解析的文件系统节点。它们与 symlink 一样可导致出根，但需通过 reparse tag 识别，不能只检查 symlink。
- **TOCTOU（Time of Check to Time of Use）**：路径通过安全检查后、真正使用前被并发替换的竞态。合并逻辑应尽量持有已验证句柄，并在使用点再次校验。
- **mode bits / Windows attributes**：mode bits 是 POSIX 读写执行权限；Windows attributes 包含 readonly/hidden 等标志。ChangeSet 按平台记录支持项，不伪造跨平台等价语义。
- **ACL（Access Control List，访问控制列表）**：除普通 mode bits 之外，为具体用户或组设置的额外权限规则。首版允许基础 POSIX mode 和可证明由父目录等价继承的 Windows DACL；存在额外用户/组条目、非继承 ACE 或其它无法重建的非平凡 ACL 时 strict 失败闭合。
- **xattr / resource fork（扩展属性 / 资源分叉）**：附着在文件正文之外的键值元数据；macOS resource fork 通常通过扩展属性表示。它可能保存标签、安全信息或应用数据，首版检测到后不静默丢弃。
- **ADS（Alternate Data Stream，备用数据流）**：NTFS 文件除主内容外附带的命名数据流。普通复制或 CAS 归档可能遗漏它，因此 Windows 纳入路径存在非空 ADS 时 strict 失败闭合。
- **hardlink（硬链接）**：多个目录项共同指向同一个底层文件；修改任一名称可能影响其它名称。首版不能在 CAS 与逐路径 apply 中保留这种共同身份，检测到纳入路径的 hardlink 关系时拒绝 strict。

### Runner、容器与通信

- **Runner**：位于 WebUI 与 Hermes Agent 之间的独立执行进程，负责 run 生命周期、Agent Worker、事件、取消控制、事务目录、ChangeSet、CAS、文件合并，以及 G7 契约关闭后的 Git 状态持久化。
- **Supervisor（监督器）**：由 `server.py` 持有，负责启动 Runner、健康检查、监控退出、退避重启和关闭收敛。它不让 Runner 跨 WebUI 生命周期存活。
- **Worker**：Runner 为单轮启动的 Agent 进程执行单元，不是单独容器。macOS/Linux 使用沙箱进程组/namespace，Windows 使用 AppContainer/Job；Docker 部署仍在外层执行容器内启动该进程。独立 Worker 身份不等于独立 CPU、内存或 PID 配额。
- **外层执行容器**：Docker 部署中同时承载 WebUI 和受监督 Runner 的现有 Linux 容器。它不是按轮创建的 Worker 容器，也不是独立 Runner service。
- **isolation launcher（隔离启动器）**：外层执行容器内的最小 root 进程，只按固定 manifest 协议分配 Worker UID/GID、建立 namespace、启动/终止进程和交还 shadow 所有权。它不接受任意命令和路径。
- **NativeIsolationAdapter（原生隔离适配器）**：在不启动 Docker 的本地部署中，把统一 Worker 隔离契约映射到 macOS sandbox、Linux namespace/bubblewrap 或 Windows AppContainer/Job 的平台实现。
- **Docker 进程沙箱**：在外层执行容器内复用 Linux adapter，通过独立 identity/namespace、`no_new_privs`、capability 清零、seccomp 和 Landlock 隐藏真实根与控制面。它不是 Worker 容器，也不提供每轮 CPU、内存或 PID 配额。
- **AppContainer**：Windows 的低权限进程隔离边界，使用独立 SID 和 capability 控制文件、网络等访问。本方案每轮分配独立 identity，只授权 shadow 和 runtime。
- **SID / DACL**：SID 是 Windows 安全主体标识；DACL 是对谁允许或拒绝什么操作的访问控制列表。Runner 用当轮 AppContainer SID 给 shadow 授权，不修改真实根为全局可写。
- **Job Object**：Windows 用来统一跟踪、限制和终止一组进程的内核对象。本方案首版只用它归属进程和通过 `KILL_ON_JOB_CLOSE` 收敛当轮子进程，不启用每轮 CPU、内存或 active-process 限额。
- **TERM / KILL**：POSIX（包括 Docker 外层执行容器内 Worker）先用 TERM 请求退出，超时后用 KILL。Windows 协作取消后终止 Job；Docker Terminal 容器使用 stop/kill。
- **FD/HANDLE 白名单**：创建 Worker 时唯一允许继承的标准流、当轮控制与 egress 通道集合。mount namespace 或 ACL 不能撤销已打开句柄，因此其它文件、目录、数据库、日志和 socket 必须在 exec/CreateProcess 前关闭。
- **Provider gateway（模型服务网关）**：Runner 侧按轮运行的应用层代理。它校验受支持的 Provider 协议，在上游 TLS 连接中注入长期凭据，并把流式结果返回 Worker；透明 HTTPS 隧道不能替代它。
- **Provider adapter（模型服务适配器）**：Provider gateway 中针对一种实际传输协议、认证方式和 endpoint 类型的实现。它负责校验请求、注入或刷新凭据、转发流式响应并统一错误；Provider 品牌名本身不能证明适配器兼容。
- **Provider endpoint 批准来源**：首版直接以当前模型经权威 resolver 得到的 Profile `base_url` 作为唯一批准事实，不另设管理员 endpoint 白名单。Runner 按轮冻结精确 origin、base path 和 adapter 固定后缀；该批准只授予 Provider gateway，不授予 Worker 或普通 egress。
- **`api_mode` / transport**：Hermes Agent 选择模型请求格式和执行路径的标识。首版 strict 支持普通 HTTP 形式的 `chat_completions`、`codex_responses` 和 `anthropic_messages`；如果内部实际切换到原生 SDK 或外部进程，必须按真实 transport 重新判定。
- **`chat_completions`**：OpenAI Chat Completions 风格协议，常用于 OpenAI-compatible Provider。
- **`codex_responses`**：OpenAI Responses 风格协议，支持 Responses/Codex 路径所需的请求和流式事件。
- **`anthropic_messages`**：Anthropic Messages 风格协议，也可由兼容该请求格式的其它 Provider 提供。
- **Profile 白名单**：允许纳入轮次文件事务的 Profile 相对路径集合。默认只包含记忆、普通技能资产和 `SOUL.md`；它可以配置，但永远不能越过凭据、会话、日志和其它固定安全拒绝规则。
- **远程 MCP 批准来源**：首版直接以会话绑定 Profile 中已启用的 HTTP/SSE `mcp_servers` 配置作为批准事实，不另设管理员 allowlist 或逐轮确认。Runner 按轮冻结目标并持有认证；Worker 只能调用当轮代理。远程 MCP 修改外部系统属于外部副作用，不进入本地 ChangeSet。
- **egress broker（出口代理）**：Runner 侧按轮校验普通工具网络目标并建立受限隧道的组件。它重验 DNS/IP/redirect，永久拒绝 WebUI、Runner、Gateway、Docker 和 metadata，不注入 Provider 凭据。
- **`provider_only`**：严格网络策略。只允许通过 Provider gateway 调用本轮冻结的模型 endpoint；普通工具不能搜索公网、下载依赖或访问公开代码仓库。
- **`restricted_public`**：本方案默认的严格网络策略。普通工具可经 egress broker 访问公共 HTTP(S) endpoint，用于搜索和下载；Worker 仍无原始网络。
  内网、控制面、Docker API 和 metadata 等敏感目标仍被永久拒绝。
- **proxy shim（代理适配进程）**：Worker/Terminal 沙箱内的无长期凭据进程。它在 loopback 暴露 Provider gateway endpoint 和普通 HTTP(S) proxy，再通过唯一 egress 通道转发，不能访问 Runner controls。
- **loopback / 内部容器网络**：Runner 可绑定控制面 loopback 或内部 Compose 网络，但 Worker/Terminal 不能访问这些地址。它们自己的 loopback 只用于 proxy shim，不能作为访问 WebUI 或 Runner 的路径。
- **Bearer key**：WebUI 调用 Runner HTTP API 时携带的临时认证密钥。它只用于控制面认证，不应写入日志、命令行、持久配置或 Agent Worker 环境。
- **SSE（Server-Sent Events）**：服务器通过一个长期 HTTP 连接按顺序向浏览器推送事件的机制。这里用于 token、工具状态、终态和 `turn_files` 摘要，不承载完整文件内容。
- **cursor（事件游标）**：客户端已经消费到的事件位置。断线重连时从 cursor 之后继续读取，用于避免漏事件或重复投影 transcript。
- **mount broker（挂载转换器）**：仅当 Docker Terminal 需要 sibling 时，把 Runner 容器内 shadow 路径安全转换为 daemon 可识别的 bind 或 named-volume subpath。
- **sentinel（哨兵探针）**：为验证 Terminal 挂载确实指向同一 shadow 目录而临时创建的测试文件。Runner 与 Terminal 双向创建、修改、rename 和删除均可见后，才允许启动 Agent。
- **Docker socket**：Docker daemon 的控制接口，常见路径为 `/var/run/docker.sock`。只有 Docker Terminal 需要它；必须由管理员通过显式 Compose override 授权给 Runner，且不得传入 Worker 进程或 Terminal 容器。
- **sibling container（同级容器）**：本方案中仅指可信 Runner 通过宿主机 daemon 启动的 Terminal 容器。它不是 Worker，也不是 WebUI 容器的真正子容器。
- **deep health（深度健康检查）**：除“进程仍在”外，还检查 Runner 协议、Docker daemon、挂载转换、权限和最近一次 sentinel 等依赖是否可用的诊断接口。

### 状态标识与界面投影

- **`session_id`**：会话身份，关联 transcript、Profile、workspace 和授权范围。
- **`turn_id`**：一次用户提交及其 Agent 响应的持久身份，用于 turn journal、ChangeSet 和恢复关联。
- **`stream_id`**：一次 Agent 执行及其 SSE 事件流的唯一身份。WebUI 为每次新执行生成新值；同一次启动请求的网络重试复用该值实现幂等。首版不定义 `run_id` 字段，避免双字段不一致。
- **`turn_key`**：Session Manifest 中一轮消息的稳定键，通常形如 `turn:42`。它与 `turn_id` 用途不同，不能依赖字符串相等进行关联。
- **Session Manifest**：从会话活动派生的 Tasks、Artifacts、References 和 per-turn 轻量索引。它不是 transcript、运行 journal 或完整 ChangeSet。
- **projection（投影）**：把 ChangeSet 中适合界面消费的部分转换成 Session Manifest artifact 行。ChangeSet 是文件变更事实，Manifest 是面向 UI 的派生视图。
- **authority marker（权威标记）**：表示某个 strict turn 已由 ChangeSet 作出“有成果”或“零成果”决定。即使零变化也要保留标记，避免旧文本回填逻辑再次猜测 artifact。
- **backfill / read-repair（历史回填 / 读取修复）**：backfill 从旧会话证据补建缺失索引；read-repair 在读取时修复可确定的缺失派生数据。它们不能覆盖已有权威 ChangeSet 决定。
