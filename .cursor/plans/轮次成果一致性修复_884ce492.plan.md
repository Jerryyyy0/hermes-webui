# 轮次成果一致性修复

## 1. 已确认的故障链

同一轮 user message 有两个合理生产者：

```text
WebUI eager checkpoint              Hermes Agent result
user(turn:6, 无 Agent id)           user(id=103, 无 _turn_key)
                  \                /
                    display/context merge
```

当前 `_merge_display_messages_after_agent_result()` 只在 eager user 仍是 `merged[-1]` 时跳过 Agent 副本。如果中间出现 partial assistant、tool、compression/recovery marker 或 context backfill，两条 user 不再相邻，Agent 副本会被追加。

已复现的最小结果：

```text
merge 后：
  user("配色淡一点", turn:6)
  assistant(partial)
  user("配色淡一点", id=103, 无 key)
  assistant(done)

终态补号后：
  第一条 user = turn:6
  第二条 user = turn:7
```

随后 reconcile/去重可能只保留第二条，最终消息层显示 `turn:7`；stream 和 artifact persistence 始终使用 chat-start 绑定的 `turn:6`，于是产生 orphan store turn。

需要修正的归因：state.db reconciliation 本身不生成 `turn:7`。它可能保留无 key 的数据库/Agent 副本或丢失 sidecar metadata，真正的编号来自：

- `api/streaming.py` 正常结果、内部 retry、exception self-heal 三处 `_next_turn_key()` 终态扫描；
- `integration/session_manifest/manifest.py::_ensure_turn_keys()` 对混合“已有 key + 缺 key”消息的补标。

错误恢复还有一个独立放大器：`_materialize_pending_user_turn_before_error()` 在 `_db_persisted` 尾行无 timestamp 时，即使 `existing._turn_key != pending_turn_key` 也视为当前 checkpoint，保留冲突 key。现有 `tests/test_issue4283_recovered_context_replay.py` 明确把该行为写成了成功断言，必须同步更新。

## 2. 本次核心不变量

一次 chat-start 只生成一次 canonical `stream_turn_key`，并贯穿本次 worker：

```text
pending_turn_key
    = stream_turn_key
    = 当前最新真实 user._turn_key
    = artifact store turn_key
    = 前端 assistant turn data-turn-key
```

- `turn:N` 继续作为现有 Manifest/UI 轮次键；缺号本身不是错误。
- `stream_id` 继续作为 worker、SSE live manifest 与 stale-worker 判断的 owner；本次不把它新增为消息字段或 artifact store schema 字段。
- active turn 禁止在 merge、恢复或结算阶段调用 `_next_turn_key()` 猜测归属。
- 结算不一致时不写 artifact decision、不自动迁移记录；先保存 transcript 和结构化诊断，再释放 worker runtime ownership，不能永久阻塞会话。

## 3. Phase 1：修复新产生的错位

### 3.1 `api/routes.py`：保持 chat-start 单点绑定

涉及函数：

- `_checkpoint_user_message_for_eager_session_save()`
- `_turn_key_for_pending_user_message()`
- `_prepare_chat_start_session_for_stream()`
- `/api/chat/start` session-lock 分支

具体改动：

1. 在 session lock 内只计算一次 `prepared_turn_key`，保存到 `s.pending_turn_key`，再读取为 `stream_turn_key` 传给普通/gateway worker。保留现有 `turn:1-N` 分配方式，本次不新增 `next_turn_number`。
2. eager checkpoint 必须直接使用传入的 `turn_key`；active chat-start 缺 key 时 fail closed，不在 checkpoint 内调用 `_next_turn_key(existing)` 补救。
3. `_turn_key_for_pending_user_message()` 只允许返回已保存的 `pending_turn_key` 或当前 eager row 已有的同值 key；删除“最后一条同文本 user → 猜测 next key”的 active fallback。
4. eager 幂等仍限制在当前 chat-start 调用链，不引入 HTTP request idempotency、`client_submission_id` 或消息级 `_submission_id`。
5. cron preparation 继续满足其既有连续 key 契约；只调整为消费同一个 prepared key，不在 worker 内重新计算。

### 3.2 `api/streaming.py`：canonical key 进入 merge

涉及函数：

- `_merge_display_messages_after_agent_result()`
- `_dedupe_replayed_context_messages()` 及结果边界处理
- `_merged_transcript_lacks_final_assistant_answer()`
- `_run_agent_streaming()` 的正常、内部 retry、exception retry 写回点

具体改动：

1. `_merge_display_messages_after_agent_result()` 增加关键字参数 `canonical_turn_key`。
2. 在 result delta 中按现有 prefix/current-turn boundary 识别本次 Agent user candidate；识别完成后立即给该临时 candidate 写 `canonical_turn_key`，再进入 context/display dedupe。
3. 从 `previous_display` 反向查找 `_turn_key == canonical_turn_key` 的 eager user，不再要求它位于 `merged[-1]`。命中时：
   - 保留 eager row 的 content、attachments、source 和 `_turn_key`；
   - 可吸收 Agent candidate 的 stable `id` 等非归属 metadata；
   - 跳过 Agent 重复 user；
   - display 与 context 对当前 user 使用同一个 key/id。
4. deferred 分支主动构造 `current_user_msg` 时，在构造字典时直接写 `_turn_key = canonical_turn_key`，然后才插入 candidates。
5. 如果 result delta 无法定位当前 user：
   - 有 assistant/tool delta 时可按 deferred 规则构造当前 user；
   - 不得通过扫描全部历史同文本 user 选择归属；
   - canonical key 为空时记录错误并停止 artifact settlement。
6. 所有调用点完整传入 `stream_turn_key`，包括正常成功、内部 credential retry、exception self-heal、gateway 对等路径与 transcript evaluator。

### 3.3 删除 active turn 猜号

删除以下三处对所有无 key user 的终态扫描：

- 正常结果写回后的 `_ntk` 循环；
- 内部 retry 成功后的 `_ntk2` 循环；
- exception self-heal 成功后的 `_ntk3` 循环。

替换为窄验证 helper，例如：

```text
_validate_latest_user_turn_binding(session, expected_turn_key, expected_text)
```

它只检查最新非 compression-marker user，不修改历史消息。验证失败返回结构化原因：`missing_user`、`missing_key`、`turn_key_conflict` 或 `content_boundary_conflict`。

`integration/session_manifest/manifest.py::_ensure_turn_keys()` 也不得在正常 GET 构建中给混合 keyed/unkeyed active transcript 补新号：

- `build_session_manifest()` 使用拷贝，不能修改 session/message 原对象；
- 全 legacy、没有任何 `_turn_key` 的会话继续使用 `_message_turns()` 的索引 fallback；
- 混合 keyed/unkeyed 会话保留 missing-key 诊断，不能生成一个看似合法的新 `turn:N` 掩盖 active bug。

### 3.4 `api/models.py`：仅传播已确认 duplicate 的 key

涉及函数：

- `_merge_session_display_metadata()` 的调用位置
- `chronological_merge_session_messages_for_display()`
- `merge_session_messages_append_only()` 的各 duplicate/replay 分支
- `reconciled_state_db_messages_for_session()`

新增独立 helper，例如 `_merge_turn_binding_metadata(target, source)`：

- 仅在现有 merge/dedup 逻辑已经确认两行是 duplicate 后调用；
- 一侧有 `_turn_key`、另一侧为空时，把 key 传播到最终保留行；
- 两侧相同非空 key 时保持；
- 两侧不同非空 key 时不覆盖，记录 session/source/key 诊断；
- 不把 `_turn_key` 加入 `_session_message_merge_key()`，避免 keyed sidecar 与 unkeyed state.db 同轮永远无法去重。

state.db 层不负责生成、递增或重新编号 turn key。

### 3.5 error/cancel/recovery：canonical pending key 优先

涉及函数：

- `_materialize_pending_user_turn_before_error()`
- cancel recovery user 构造路径
- `api/models.py` stale journal/state.db recovery 路径

具体规则：

1. narrow optimistic checkpoint 已由尾部位置、pending text/source 和 `_db_persisted` 证明是当前 user 时，`pending_turn_key` 是 authority：尾行缺 key或携带不同 key时统一改为 pending key，并同步 context copy；不能保留冲突 key后继续清 pending。
2. 无法证明是同一当前 user 时，追加 recovery user 必须直接携带 `pending_turn_key`；pending key 为空则 fail closed，不调用 `_next_turn_key()`。
3. 清除 `pending_turn_key` 前执行最新 user binding 验证。失败时保存 `turn_key_conflict` journal/diagnostic 和可恢复 transcript，再清理已终止的 `active_stream_id`；不得伪造成功 artifact decision。
4. 修改 `tests/test_issue4283_recovered_context_replay.py` 中“pending turn:4、db row turn:5 仍保留 turn:5”的旧断言，改为最终 canonical row 使用 `turn:4`。

### 3.6 artifact settlement：普通 WebUI 也校验

当前 `_cron_followup_turn_key_matches()` 只保护 cron；普通 WebUI 在最终 `s.save()` 后直接调用 `_persist_turn_artifact_paths()`。

具体改动：

1. 将 cron-only 校验提炼为所有持久化会话共用的 `_latest_user_turn_key_matches()`；cron 可在调用前继续执行自己的 transcript normalization。
2. 正常完成、gateway、cancel 和 error settlement 在写 store 前必须满足：最新真实 user 的 `_turn_key == stream_turn_key`。
3. 不一致时：
   - `_persist_turn_artifact_paths()` 返回 `status=failed, stage=turn_key_conflict`；
   - 不调用 `upsert_manifest_records()`，也不创建 empty decision；
   - journal 记录 session、stream、expected key、actual key、terminal reason；
   - 不自动把 `turn:6` artifact 改绑到 `turn:7`。
4. 一致时仍使用现有 stream-owned live evidence + 当前 turn transcript reconcile，确保 `recolor.py` 归属 canonical turn。

## 4. Terminal `cp` 产物证据

当前 `_terminal_output_paths()` 只识别 `-o`、`--output`、`--print-to-pdf` 和 `md2word.py` 的受控位置参数；`cp recolor.html report.html` 返回空，所以文件权限调整无法让成果进入 Manifest。

在 `integration/session_manifest/manifest.py::_terminal_output_paths()` 的现有安全边界内增加窄 grammar：

```text
cp SOURCE DEST
cp -- SOURCE DEST
```

约束：

- terminal 事件必须与同 tool id 的 completed success result 配对；非零退出不采集；
- 仅接受单 source + 单 destination；拒绝 `-r/-R`、多 source、变量、命令替换、通配符和动态路径；
- 只把 destination 作为 artifact，不把 source 当成果；
- destination 必须在 workspace 内、命令完成后真实存在、是普通可预览文件；
- 继续支持受控 `cd DIR && cp SOURCE DEST`；
- 不扫描 stdout、目录或 workspace 快照。

`report.html`、`report.pdf` 若分别由成功的静态 `cp` 产生，将通过现有 tool event → live delta → turn settlement 流程进入同一个 canonical turn。

## 5. Orphan 投影与历史修复

`build_session_manifest()` 当前会把 store 中没有 user anchor 的 turn 直接追加到 `turns`。这不是改号根因，但会把 orphan 伪装成正常 per-turn row。

调整原则：

- 不删除、不丢弃 orphan artifact；仍保留在 Manifest 顶层 `artifacts`，Inspector 可见；
- 不把无 user anchor 的 store key追加为正常 `turns[]`；改为明确的 `diagnostics.orphan_turn_keys` 或 `unbound_artifacts` 投影；
- 前端 per-turn chips 只消费有 user anchor 的 `turns[]`；Inspector 可对 unbound 项显示“轮次归属待修复”；
- 新 active turn 修复后不应再产生 orphan；历史数据不会自动更改。

提供独立 repair 工具：

```text
dry-run: 列出 lineage/profile、旧 key、候选 user key、路径和证据
apply:   仅接受显式 old_key → new_key 映射，事务性 rebind
```

历史 store v1 没有持久化 `stream_id`，因此不能声称可以按 stream 自动迁移。没有 journal/tool-call/user 明确证据时只报告，不 apply。

## 6. 不进入本次范围

- 不新增 `Session.next_turn_number` 或 reservation ledger；retry/undo/truncate 后 key 复用另行用失败测试证明后再立项。
- 不新增消息级 `_submission_id`，不修改 artifact store schema 增加 `stream_id`。
- 不实现浏览器 HTTP 重放幂等或 `client_submission_id`。
- 不重写全局 `_session_message_merge_key()` / `_message_identity()`。
- 不解决所有历史 duplicate/compression/tool replay 问题，只修改会丢失或错误生成 current `_turn_key` 的 chokepoint。
- 不通过 chmod、改英文文件名或 workspace 全量扫描修复成果可见性。

## 7. 测试计划

### P0：真实故障

1. eager `turn:6` → partial/tool/marker/backfill → Agent current user 无 key/id=103 → merge 后 display/context 各只有一条当前 user，均为 `turn:6`，保留 id=103。
2. 同一路径执行原有终态写回，断言不存在 `turn:7`，三个 `_next_turn_key()` loop 不再运行。
3. `_ensure_turn_keys()` 面对 `turn:6 + 无 key current user` 不生成 `turn:7`，且不修改输入对象。
4. pending `turn:6` + `_db_persisted` current tail `turn:7` → error recovery 后只保留 canonical `turn:6`。
5. 最新 user 为 `turn:7`、stream key 为 `turn:6` → artifact settlement 返回 `turn_key_conflict`，store 无 `turn:6` decision，journal 可诊断。
6. 当前轮发生被动压缩并触发 `old_session → continuation` 旋转：压缩 marker 不生成轮次，Agent user 回显折叠到 eager `turn:6`；结算后 continuation Manifest 同时读取父段 artifact 与当前 `turn:6` artifact，且 `diagnostics.orphan_turn_keys=[]`。

### P0：终端成果

1. 成功 `cp recolor.py report.html`，destination 存在 → `report.html` 进入当前 canonical turn。
2. 成功 `cd out && cp source.pdf report.pdf` → 只采集 `out/report.pdf`。
3. 非零退出、workspace 外 destination、变量、glob、多 source、recursive cp → 不采集。

### P1：相邻生命周期

1. state.db 已确认 duplicate：keyed sidecar + unkeyed db row，无论到达顺序都保留 key。
2. 双非空不同 key：不覆盖，结算失败且有诊断。
3. normal、gateway、cron、cancel、error、internal retry、exception retry 都调用同一 binding/settlement helper。
4. 同文本两次独立提交保留两轮，不因文本相同误合并。
5. Manifest orphan 仍在顶层 artifacts/diagnostics 可见，但不进入正常 per-turn chips。

### P2：历史/UI

1. orphan repair dry-run 不写库；无显式 mapping 的 apply 拒绝。
2. 显式 rebind 后旧 key records 原子迁到目标 key，路径不丢失、不重复。
3. assistant turn DOM 写入正确 `data-turn-key`，GET Manifest 后 `recolor.py/report.html/report.pdf` chips 出现在对应轮次。
